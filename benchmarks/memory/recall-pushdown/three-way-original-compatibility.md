# Recall下推等价适配：三组对照与修复验证

更新日期：2026-11-19。**修复版保留PG内C RRF，不调整分数和权重；RRF及真实本地BGE两种模式各81/81题的完整业务响应与未修改原始版完全一致。两道时间题均接管，每题一次候选SQL、零后续补查。** 实验限定原109条world事实Bank、固定81题及CPython 3.11.15、`PYTHONHASHSEED=0`环境；尚未切换原服务。

## 1. 先看结论：改了什么，验证了什么

此前下推SQL给同分候选增加UUID排序，改变了进入RRF的名次，因此不满足“结果等价”的要求。此次修复恢复原始各路候选顺序，融合和Top-K继续在PG中完成。模型、最终评分和预算继续复用ContextBase原逻辑。

```text
既有 Recall HTTP 接口
        |
ContextBase：认证、配置、时间解析、查询向量
        |
        | 一次参数化候选SQL
        v
PG：原始四路检索顺序 -> C RRF / Top-K -> 候选正文与关联原文
        |
        | 完整候选包；释放PG连接
        v
ContextBase：原BGE重排 / 最终评分 / 预算 -> Recall响应
        |
既有LoCoMo客户端打包上下文；不再补查PG
```

**一次调用指候选检索阶段，不代表整个HTTP请求只有一条SQL。** API外层原有Bank/配置读取单独记录；PG函数内部执行多条SQL。本轮没有实现查询内并行、动态剪枝或新CustomScan。

## 2. 为什么必须做三组对照

| 组别 | 源码与实现 | 用途 |
| --- | --- | --- |
| 原始版 O | 改动前提交`0951c3664b3083a99268040c8c84113073a057b3`，默认Postgres store，产品源码未改 | 定义原有Recall行为 |
| 修改后关闭 U | 修改后源码，默认Postgres store | 检查共享后处理提取是否改变原行为 |
| 修改后开启 B | 修改后源码，下推store | 检查下推是否保持原行为 |

O/U在RRF和真实BGE两种模式中，均为81/81题完整响应一致；BGE有序模型输入也全部一致。这是回归保护，不是下推通过的替代证据。

三个版本使用同一原PG、同一Bank、同一81题、冻结真实查询向量、时间锚点和预算。O/U与修复版均固定哈希种子0，不给原始候选或响应额外排序。原始版是上述固定提交，不能与8892历史部署混为一谈。

先前`CanonicalPostgresMemories`对照额外规范化排序，也前移了时间解析；此前“81题一致”仅适用于该规范化对照。它不能证明与未修改原始版等价，旧报告现作为历史诊断保存。

## 3. 修复前：数据相同，名次已改变

| 比较项，81题 | O ↔ U，RRF | O ↔ 旧下推，RRF | O ↔ 旧下推，真实BGE |
| --- | ---: | ---: | ---: |
| 完整业务JSON响应相同 | 81 | 0 | 1 |
| 最终返回ID集合相同 | 81 | 81 | 81 |
| 最终返回ID顺序相同 | 81 | 0 | 80 |
| 原客户端打包后的reader正文相同 | 81 | 0 | 81 |
| 实际有序模型输入相同 | 不适用 | 不适用 | 0 |

旧BGE下推列复用已冻结的实际模型记录，旧进程哈希种子未记录；它用于追踪既有差异，不作为新的性能样本。原始版和修改关闭版的BGE均为本轮新跑。

旧BGE组q011只交换第99、100条返回结果，未进入最终客户端上下文；最大数值分差约`1.77e-6`。因此不能把“81题响应有差异”解读为81题答案错误；本轮未重新运行reader/judge。RRF组差异则实际改变了最终reader正文。

## 4. 根因：同分排序改变了RRF的输入

原始图检索合并多个Python字典的ID集合，再只按分数做稳定排序。同分候选继承集合迭代顺序；该顺序受解释器及哈希种子影响。原始全文和时间路也没有统一采用UUID作为最终并列键。旧下推改成`score DESC, id`，改变了单路名次。

| 检索路 | 候选集合相同的题数 | 顺序不同的题数 | 变化位置 |
| --- | ---: | ---: | --- |
| 向量 | 81 | 0 | 无 |
| 全文 | 81 | 80 | 同分候选 |
| 图 | 81 | 80 | 同分候选 |
| 时间 | 81 | 2 | 同分候选 |

例如q000，两个全文候选分数均为`0.800000011920929`，原始版排第2、第3，旧下推版排第3、第2。RRF按`1 / (60 + rank)`计分，交换名次会改变贡献，进而影响融合、重排输入和预算。

**直接排除C RRF计算错误的证据：** 将原始版实际记录的各路ID及名次直接传入已安装的`recall_probe.rrf_topk()`，不增加排序，81/81题的融合ID、顺序、分数和名次均与原Python RRF一致。问题在输入名次，不在融合公式；把RRF移回ContextBase也不能自动修复输入顺序。

代码依据：[原图路集合与排序，约262行](../../../hindsight-api-slim/hindsight_api/engine/memories/pg/link_expansion.py)、[旧下推SQL](../../../hindsight-api-slim/hindsight_api/engine/memories/pg/recall_pushdown.sql)。

## 5. 修复方案：保留原始名次，RRF继续留在PG

本次没有改变RRF公式、权重、Top-K、模型输入模板、BGE精度、批量大小或预算。

| 修复位置 | 具体处理 | 为什么需要 |
| --- | --- | --- |
| 向量与全文 | 复用原SQL构造器生成的完整UNION，保留返回行序 | 拆写查询或添加UUID键会改变并列名次 |
| 图扩展 | 复用原图SQL；兼容原集合构造和联合后的顺序 | 只删除UUID排序仍不能复现Python集合顺序 |
| 时间路 | 保留种子、邻居、首次出现与稳定排序规则；保持浮点乘法顺序 | 两道时间题也必须符合原算法 |
| 融合与裁剪 | 原始单路名次送入已有C RRF/Top-K | 已直接验证融合计算与Python相同 |
| 后处理 | 一次带回候选正文、附件空标识及关联原文，释放连接后调用共享处理 | 模型、评分、预算不复制实现，也不补查 |
| 未支持请求 | 查询前退出接管，原始store处理 | 不继承历史Canonical对照的排序规则 |

实验入口为：

```sql
SELECT recall_equiv.candidates($1::jsonb, $2::name) AS bundle;
```

扩展选择器为`hindsight_api.engine.memories.pg.recall_pushdown:EquivalentPostgresRecallMemories`，仅服务端启用指定Bank，不新增客户端`full_recall`参数。SQL模板仅由认证后的服务端既有构造器产生，不接收HTTP任意SQL。

**兼容机制有明确范围：** 新增C辅助函数模拟CPython 3.11、64位SipHash13、哈希种子0下UUID字符串的集合构造/联合顺序；PG不加载Python运行时。已对真实CPython内置集合执行600组构造、600组联合随机差分，全部通过。它是临时旧行为适配，不是新的通用相关性策略；当前不能宣称任意解释器、随机种子、执行计划或数据规模下均已等价。

未知解释器/哈希配置查库前退出接管。生产8892未改，不能把固定种子实验通过说成已验证该生产进程。后续若正式制定稳定并列规则，应单独做排序与LoCoMo质量实验，不混入本次等价修复。

## 7. 收益、边界与交付位置

本轮首先证明可行性及行为兼容。冻结查询向量不包含在线embedding耗时，顺序单轮运行不能证明完整Recall平均/P50/P95提升。

| 顺序正确性运行的HTTP观测值 | 原始版 | 修复下推版 |
| --- | ---: | ---: |
| RRF平均 / P50 / P95，ms | 22.01 / 19.70 / 40.44 | 17.07 / 15.69 / 23.11 |
| BGE平均 / P50 / P95，s | 7.276 / 7.085 / 8.901 | 6.913 / 6.622 / 8.740 |
| BGE非模型部分平均，ms | 28.99 | 35.80 |

这些不是交错、重复的性能A/B，BGE差额主要伴随模型运行时波动；非模型部分本轮反而增加，因此不能把完整耗时下降归因于PG下推。大Bank、并发与交错A/B仍需后续验证。

等价上下文没有节省Token，本轮也没有新的答题准确率成绩。不调整排序质量的等价下推，不能单凭架构推导准确率上升。
