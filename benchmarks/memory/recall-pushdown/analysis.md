# Recall 下推到 PG：对 LoCoMo 准确率、P95 与 Token 的影响

> **维护说明（2026-11-19）：** 本报告记录旧 conv-30 Bank 的 81 题下推研究及早期原型，后续全量 1,540 题和 V1 优化以[打榜主入口](../README.md)为准。当前设计见[design.md](design.md)，进展见[progress.md](progress.md)，下一阶段一晚实施计划见[plan.md](plan.md)。该阶段仍未启动。原研究目录保留历史快照；今后本报告正文只在这里维护。

分析日期：2026-11-19。参考文档：《Hindsight 记忆检索执行分析与 PostgreSQL 增强方案》（[原文件位置与哈希](evidence/source-contract-audit.json)）。源码基线：`memory-benchmark` 分支、`e7a0b54828b9605e18e19848e56d56f078dbafed`。

本报告已补充夜间原型与实际验证：只读导出打榜使用的 LoCoMo Bank，在独立 PG 18.4 实例运行 SQL/C 融合原型；保留现有服务、Bank 和打榜结果。另为 81 个查询准备并冻结向量，没有新增 reader、judge 或 BGE 调用。第 7 章说明落地方案及研发边界，第 8 章报告原型实测与限制。

## 1. 结论：下推先争取同准更快，再验证更准或更省

**源码确实提供了完整 Recall 的存储侧接管接口，PG 可以沿这个接口建设融合执行。最直接的收益目标是降低 Recall 的执行开销与 P95；准确率和模型 Token 不会仅因执行位置改变而自动改善。**

| 指标 | 仅做等价执行下推：数据、算法、模型与返回内容保持一致 | 下推之后再优化检索或证据选择 | 当前判断 |
| --- | --- | --- | --- |
| **Recall P95** | 可以争取减少 SQL 往返、候选搬运与串行等待；仍需负载对照验证 | 可进一步优化访问路径、并发和模型批次，也可能因增加检索或重排而变慢 | **最直接的性能目标** |
| **LoCoMo 准确率 / 答案 F1** | 送入 reader 的内容不变时，应保持质量，不应预期仅靠下推提分 | 在相同时间或 Token 预算下，提高关键证据覆盖与排名，才有提分路径 | **需要独立的质量策略和实验** |
| **模型 Token** | 相同模型输入不变；少传数据库候选不是少用模型 Token | 减少冗余证据、改进预算分配，并确认关键依据没有丢失，才可能下降 | **应验证同等质量下能否减少实际模型输入** |

建议把收益目标表述为三种可检验结果：**同等质量下更快；相同时延下证据更充分；同等质量下输入更精简。** 它们可以分别成立，不应先承诺三项同时改善。

**本轮验证后的判断：可以实现下推，但当前 109 条事实的 Bank 不足以证明“大幅降低端到端 P95”或“下推提升准确率”。** C 融合函数已通过全部 81 题的原始候选排名回放。79 题受控下推分支减少约 57% 候选正文搬运，但适配层 P95 的改善只有零点几毫秒；普通 SQL 融合还略慢。已有 BGE 实测支持“排序改变可能提分”，同时也显示其 CPU 推理会明显增加时延。两类证据不能混为一谈。

## 2. 源码确认：预留了什么，当前 PG 做到哪一步

### 2.1 两个接口的职责不同

| 接口 | 返回什么 | 后续还由谁处理 |
| --- | --- | --- |
| `recall_unified(...)` | 四路候选：向量、全文、图、时间 | Python 引擎继续融合、裁剪、重排、预算筛选和补全 |
| `full_recall(FullRecallRequest)` | 排好顺序并完成所承接阶段的 `RecallResult` | 引擎接到非空结果后直接返回这条存储侧结果 |

`FullRecallRequest` 已包含查询文本与向量、事实类型、标签/时间条件、检索预算、重排模式与候选上限、时间及策略权重、最低分、事实与原文预算、tokenizer，以及来源事实等开关。接口默认返回 `None`，表示不接管；不支持的请求形状应便宜地回退，不能近似执行后冒充等价结果。

当前 `PostgresMemories` 实现了 `recall_unified`，没有覆盖 `full_recall`。因此，**“已有接入契约”已经确认，“PG 已经完成融合下推”尚未实现。** 源码与哈希记录见[接口核验](evidence/source-contract-audit.json)。

这里指产品实现。本轮另有隔离的 `PGRecallPrototype.full_recall` 实验适配器，尚不能作为产品后端直接替换；其候选 DAG、原型范围与兼容性差距见第 8 章。

接口注释中的“四次 store 交互”是候选、补读、原文、实体等阶段调用，不是旧现场的 19 次 PG 业务 SQL。规划可以将核心检索合成一次请求，但认证、配置和统计等仍可能执行其他 SQL，必须分层计数。

源码位置：[base.py](../../../hindsight-api-slim/hindsight_api/engine/memories/base.py) 第 804、1759、1799 行；[postgres.py](../../../hindsight-api-slim/hindsight_api/engine/memories/postgres.py) 第 124 行；[memory_engine.py](../../../hindsight-api-slim/hindsight_api/engine/memory_engine.py) 第 9428 行。

### 2.2 完整接管仍有明确边界

```text
应用/API：认证、Bank 配置、请求解析
                  |
                  v
应用生成 query embedding                 <-- 当前接口之前，仍在应用侧
                  |
                  v
full_recall(request)
  检索与关系扩展 -> 融合与裁剪 -> 重排与加权
      -> 事实预算筛选、原文/实体/来源等返回处理
                  |
                  v
RecallResult
                  |
                  v
评测或应用打包最终上下文 -> reader 生成答案 <-- 仍在外部
```

`FullRecallRequest` 传入的是重排模式等策略，不包含完整的模型端点、权重版本与运行环境。PG 实现还需要配置或接入模型执行器；接上方法并不等于模型推理也自然完成。

Memlake 官方架构也说明：Hindsight 随请求传入融合、重排、权重和预算策略，存储侧就近执行并返回入选记忆。这为执行下推提供产品参照；其存储架构、硬件和测试条件与 PG 不同，不能照搬提速数字。[Memlake 架构](https://docs.hindsight.vectorize.io/enterprise/memlake/architecture/)、[基准限制](https://docs.hindsight.vectorize.io/enterprise/memlake/performance/)

### 3.2 已有错题说明：查出来，不等于 reader 看到了

### 3.3 打榜会话已完成 BGE 复测：质量提高，时延也明显增加

`ContextBase benchmark 打榜` 会话于 2026-11-19 完成 `locomobge_20261119_005630`：复用同一 Bank、同一批 81 题，保持 reader/judge 模型、AMB prompt 和 8K 预算。它改变的是排序策略与模型执行，不是 PG 下推。

| 指标 | 原 RRF | 本地 BGE | 能说明什么 |
| --- | ---: | ---: | --- |
| 正确题数 / 准确率 | 70/81，86.42% | 76/81，93.83% | 观察到净增加 6 题、7.41 个百分点 |
| 答案 F1 | 21.98% | 26.64% | 同一评分代码下提高 4.66 个百分点 |
| Recall HTTP P95 | 537.96 ms | 6,849.86 ms | 增加 CPU 模型计算后显著变慢，不能称为同时提分提速 |

这两轮包含不同并发与恢复过程，模型生成也有波动；一个 Bank 的 81 题属于开发证据，不能作为全量成绩或严格因果估计。两个完整摘要、原文件哈希及边界见 [BGE 对照证据](evidence/locomo-rerank-comparison.json)。

## 4. P95：最直接的目标，但要分开数据库与模型耗时

### 4.1 按参考文档，优先做三类执行优化

| 机制 | 当前证据与源码位置 | 预期改善 | 需要实测的边界 |
| --- | --- | --- | --- |
| **融合与延迟物化** | PG 候选 SQL 仍读取 `text`、`context` 等字段；通用引擎已有 `hydrate_results` 钩子，PG 默认已返回完整正文 | 融合/裁剪前尽量只传 ID、分数和必要属性，减少网络、解码和内存压力 | 不能把候选字节减少比例直接当作 P95 或模型 Token 降幅 |
| **依赖感知并行与批量关系访问** | 当前 PG 仍先组合语义/全文，再同连接做时序，之后图任务按类型并行 | 独立分支尽早执行，减少不必要的串行等待；图仍须等待种子 | 更多并发可能加重 PG、连接池与 CPU 竞争，P95 也可能恶化 |
| **适用的 Top-K 剪枝** | 参考文档建议可靠上界下少评分；既有两种保守 RRF 回放没有提前终止 | 在能证明上界的子算子中减少无竞争力计算 | 普通距离/全文上界不等于任意 RRF、时间权重与神经重排的上界 |

源码：[PG 候选读取](../../../hindsight-api-slim/hindsight_api/engine/memories/pg/recall.py) 第 115 行；[补读钩子](../../../hindsight-api-slim/hindsight_api/engine/memories/base.py) 第 1543 行。这里既有可复用钩子，也有 PG 尚可研究的具体实现空间。

### 4.2 旧实测只能用于敏感性分析，不能预测新 P95

2026-11-12 文档中的两条单次请求提供如下算术示例。假设检索阶段缩短一半，其他阶段保持不变且按串行关键路径计算：

| 旧单次请求 | 原接口时间 | 原检索阶段 | 假设检索减半后的接口时间 | 说明 |
| --- | ---: | ---: | ---: | --- |
| RRF recall | 1.585 s | 0.923 s | 约 1.124 s | 约减少 29.1%；没有昂贵重排阶段时，检索优化更容易体现 |
| MaaS recall | 10.294 s | 0.493 s | 约 10.047 s | 约减少 2.4%；7.782 s 的重排阶段保持不变 |

这是**假设计算，不是实测、目标承诺或 P95 估计**，也不能与本节 538 ms 的另一数据集基线拼接。[计算依据](evidence/latency-sensitivity.json)

三题、109 候选的独立 CPU BGE 微测平均约 4.04 秒/题；随后真实 81 题 BGE Recall HTTP P95 为 6.85 秒。两者计时范围不同，不能相减推算其余阶段。它们共同说明模型计算在当前场景中非常重要：把同一模型移到 PG 附近、仍使用相同 CPU 和相同输入，不会自动消除这些计算。

### 4.3 P95 应怎样测

分别报告存储侧执行、Recall HTTP，以及 RAG 问答端到端三类 P95；问答计时不包含离线裁判。存储侧可使用已有 `store_stages` 与 `full_recall` 阶段埋点，不要在下推后失去阶段可见性。[埋点实现](../../../hindsight-api-slim/hindsight_api/engine/memory_engine.py) 第 9496 行

固定数据、模型、资源与请求到达率，对单请求、小并发和接近饱和的负载分别测量；区分热缓存、冷打开、超时和重试。小 Bank 与大 Bank、多 Bank 分开。阶段 P95 不能相加得到请求 P95；19 条 SQL 时间求和也不能替代关键路径。

## 5. 准确率与 Token：需要优化证据选择，而非只移动执行位置

### 5.1 两条有依据的收益路径

**路径一：相同时延预算，找到更多有效证据。** 等价下推节省的时间可以用于更充分的 ANN 搜索、有界图/时间扩展或更合适的候选重排。它可能改善多跳、时间推理题的证据覆盖，但已经改变了检索策略；更多候选也可能增加噪声。必须与同算法的应用侧实现比较，才能区分策略收益和下推收益。

**路径二：相同 Token 预算，让关键证据进入最终输入。** q029 已说明预算前的候选存在，问题出在排名和配额。可以比较重排、事实/原文配额、来源覆盖与冗余处理；q073 则要求保留原文细节，不能以相似为由删掉独有证据。

当前代码已有 `prefer_observations` 来源去重和事实预算选择；评测客户端也已按完整条目打包、避免硬切 JSON。这些是基线，不能重新包装为下推的新能力。[事实选择](../../../hindsight-api-slim/hindsight_api/engine/fact_budget.py)、[客户端打包](../support.py) 第 504 行

### 5.2 目前还有两次预算，完整下推不自动覆盖最终打包

```text
PG/存储侧 full_recall
    facts 的 max_tokens + chunks 的 max_chunk_tokens 等预算
                         |
                         v
当前评测 support.pack_context                 <-- 仍由评测侧执行
    最终 8,192 总预算，事实 4,000 + 原文 4,000 + 包装
                         |
                         v
实际 reader prompt
```

当前已完成运行的 recall 事实、原文各设 8,192，而 reader 之前还会做总计 8K 的打包。**`FullRecallRequest.max_tokens` 不是“最终 reader 上下文的全量上限”。** 仅实现接口，不能解决 q029 这种下游再次筛掉证据的问题。

要协调最终选择，应用适配层需明确传递最终预算、事实/原文规则、tokenizer 及序列化口径，或者让客户端继续按相同策略校验。现有接口尚未表达当前 `pack_context` 的全部规则。内核可以提供通用预算选择机制，不必固化某个 LoCoMo JSON 或业务类型。

Token 在序列化边界不一定可简单相加；缓存单条长度不能替代最终文本校验。数据挪到数据库后，若正文、原文、日期和包装全部相同，实际上下文 Token 也应相同。

### 5.3 Token 必须分四个口径

| 口径 | 下推的直接影响 | 本次应怎样记录 |
| --- | --- | --- |
| PG 到应用的候选字节 | 可通过就地融合、裁剪、延迟取列减少 | 字节、行数、协议与解码耗时；不用“省 Token”替代 |
| Reranker 输入 | 同一批 query/text 不会因执行位置改变而缩短 | 候选数、实际模型分词长度、批次、截断与重试 |
| Reader 实际输入 | 仅当最终证据或包装改变时，才有下降的机制依据 | 分开统计记忆上下文与完整 prompt；保持同一 tokenizer |
| 模型实际用量与费用 | 还受输出、缓存、限流和重试影响 | reader、judge、embedding、rerank 分项；未知用量不记为 0 |

本机协议以 `o200k_base` 记忆上下文为主口径，同时保留 AMB 的 `cl100k_base` 统计。不能将 7,765.44 的上下文数当成全部调用 Token，也不能把 1,915→300 的候选裁剪比例当成 reader 的 Token 降幅。

本方案在冻结记忆上比较 Recall，写入期 retain 的 Token 不属于执行下推的直接节省；若同时改变写入策略，需要另建实验。

## 6. 验证方案：先分离“下推”和“策略”两个变量

| 组别 | 改什么 | 保持什么 | 用于回答的问题 |
| --- | --- | --- | --- |
| **A：当前 PG 基线** | 无 | 冻结记忆与向量/关系、评测协议、reader/judge、预算、运行资源 | 当前结果与时延是多少？ |
| **B：等价 full_recall** | 存储接管执行，优化搬运和调度 | 与 A 相同候选与评分规则、模型、最终结果及 reader 输入 | 仅改变执行位置，能否同准更快？ |
| **C：策略对照** | 排名/覆盖/预算策略，一次只改一个主要因素 | A 或 B 的数据、reader/judge 与预算档位 | 哪些质量或 Token 收益来自策略？同策略在应用侧与存储侧差多少？ |

### 6.1 B 组先做等价性，不急于重新付费答题

冻结 query embedding、`now/question_date`、配置及模型版本；逐题比较候选与最终 ID/顺序、正文、相关分数、来源、原文和最终打包字符串。执行统计允许不同。若最终 reader 输入逐字一致，可以先证明没有引入新的信息差异，再运行有必要的模型评估；相同 prompt 下模型仍可能波动，不能把偶然答案变化当作下推提分。

特别需要覆盖：标签/时间过滤、RRF/interleave/重排模式、模型失败回退、来源预算、`prefer_observations` 和排序并列。当前 chunks 在事实预算筛选前收集；改成只取最终事实的 chunks 会改变结果，不能当作无损优化。当前事实预算对“所有候选均过长”的情况会保留一条完整事实并允许超预算；零预算、空文本与超长事实都要按实际代码做边界差分，不能仅凭文档描述重写。

没有已存在的“强制 Python 路径”请求开关可供假定使用。可用两个测试实例/存储实现对照：默认 PG 的 `full_recall` 返回 `None`，原型实现对已支持形状接管，未支持形状仍返回 `None`。

### 6.2 C 组再画质量、时延与 Token 的权衡曲线

先在固定 8K 协议上验证 q027/q029 这类已知问题，然后使用未参与调参的题目检验总体结果；开发样本不能代替完整成绩。更改预算时另列 4K/8K 等实验档位，并保持事实、原文、包装的统计边界一致。

报告总体准确率与答案 F1，同时按题型和对话分组；补充 gold 证据覆盖和最终上下文中证据覆盖。LoCoMo 的对话证据 ID 与数据库 UUID 不同，需通过入库来源建立映射。不要把已有相关事实未进入最终输入的问题，都归为检索未命中。

性能测试另用重复、固定到达率的请求负载，不将一次 81 题模型作答运行直接当作数据库压测。记录成功、超时和失败；质量分母保留全部应测题，另列成功请求上的质量，避免仅由少超时造成的表观提分混入检索质量结论。

两端复用同一冻结 Bank/事实/向量/关系快照，避免重新抽取或后台整合改变语料。服务端下推版本与当前部署版本、当前工作区版本分别归档。正式运行继续使用本项目固定 AMB，不切到网上最新 main。LoCoMo 数据与原始评分来源见[官方仓库](https://github.com/snap-research/locomo)。

## 7. 具体下推方案：一个接管入口，分阶段交付执行能力

### 7.1 入口与流程：接管 Recall，不把业务类型固化进内核

**对 Hindsight 复用 `full_recall(request)`；对 PG 建设融合检索执行与批量模型重排两项能力。** `world`、`observation`、关系类型、权重和预算仍由应用解释并传参。数据库执行通用的过滤、排名、关联、预算与投影，不在内核写死这些业务名。

```text
既有 Recall API / MemoryRecall
             |
             v
  full_recall(request)                     应用适配与能力检查
             |
             v
  1. 生成候选，只携带 ID、排名与必要属性
       向量检索 ----种子----> 有界图扩展
       全文检索 ----------------------┐    独立分支可并行
       时间检索（有时间条件时）-------┤    图扩展等待种子
                                     v
  2. 库内融合 Top-K ----> 补读入选正文 ----> 批量模型重排能力
       去重、RRF、上界剪枝                  按请求的排序模式执行
                                     |
                                     v
  3. 最终评分、预算选择、补全原文/实体 ----> RecallResult
                                     |
                                     v
      既有客户端 pack_context ----> reader 答题
```

这是一个入口的内部执行流程，**不是新增多个对外接口**。其中“可并行”“上界剪枝”属于拟研发目标；本轮 C 函数原型尚未实现它们。

### 7.2 哪些复用，哪些确实需要研发

| 工作 | 可复用的现有能力 | 要新增的实现 | 分类与边界 |
| --- | --- | --- | --- |
| **接管入口与策略传递** | `FullRecallRequest`、`RecallResult`、返回 `None` 回退、`store_stages` | PG 后端适配、支持形状检查、正确传递自然语言时间分析结果、回退及阶段监控 | **应用/存储适配研发**，不需要修改 PG 内核 |
| **候选过滤与关系扩展** | pgvector 距离检索；PG 全文索引；B-tree、LATERAL、连接、聚合；现有图/时间 SQL | 将分散 SQL 组织为依赖明确的计划，先传窄列，裁剪后取正文 | 首版大部分可用 **SQL 重写**，不能将这些已有算子重新列为内核发明 |

| **最终评分与预算** | 现有 Python 评分、BPE、事实预算和客户端完整 JSON 打包；PG SQL 可做评分与过滤 | 保持语义的存储侧实现；缓存 Token 长度时携带正文哈希和 tokenizer 版本；最终序列化校验 | 先复用验证过的规则。**位置改变不自动产生质量收益**，也不自动覆盖最终 reader 预算 |

PG 18 已提供 CustomScan 扩展接入设施，因此应先用扩展验证，不预设必须维护一套 PG core 分叉。需要改 core 的位置，应由原型暴露的接口限制决定。[PG CustomScan](https://www.postgresql.org/docs/18/custom-scan.html)

另有两个不能混淆的事实：pgvector 0.8.7 的 HNSW/IVFFlat handler 中，`amcanparallel=false`，`amcanbuildparallel=true`，前者与查询扫描、后者与建索引有关；`amcanreturn=NULL` 表明它们不直接提供 index-only 返回能力。**窄列候选仍可能访问 heap，不能据此宣称消除了 heap I/O。** 不同检索分支仍可能各用串行索引扫描并在计划级并行，不能反过来说它们完全不能并发。[HNSW 源码](https://raw.githubusercontent.com/pgvector/pgvector/v0.8.7/src/hnsw.c)、[IVFFlat 源码](https://raw.githubusercontent.com/pgvector/pgvector/v0.8.7/src/ivfflat.c)、[PG 并行计划](https://www.postgresql.org/docs/18/parallel-plans.html)

### 7.3 用实际 SQL 说明：到底少做什么

在当前 LoCoMo 快照上，以本次 world-only、高预算 1,000 的请求剖面调用未修改的 PG store，普通题候选阶段采集到 **2 次业务 fetch**：向量＋全文组合 SQL、图扩展 SQL。有时间条件的 q047 为 **5 次**：组合检索、时间候选、两轮时间关系扩展、图扩展。它们尚未计入后续原文补全、鉴权与配置。**11 月 12 日另一 Bank 的 19 次 SQL，不应套用到当前每道题。** 完整 SQL 与采集范围见[当前 SQL 计数](evidence/current-sql-counts.json)、[普通题实际组合 SQL](evidence/current-sql/q000-01.sql)。

现有组合查询会在候选阶段读取如下字段（实际 SQL 节选）：

```sql
SELECT id, text, context, event_date, occurred_start, occurred_end,
       mentioned_at, fact_type, document_id, chunk_id, tags, metadata,
       proof_count,
       1 - (embedding <=> $1::vector) AS similarity,
       NULL::float AS bm25_score, 'semantic' AS source
FROM ctxdb_ws_locomo_conv30_20261118_200523.memory_units
WHERE bank_id = $2 AND fact_type = 'world'
  AND embedding IS NOT NULL
  AND (1 - (embedding <=> $1::vector)) >= 0.3
ORDER BY embedding <=> $1::vector
LIMIT 1000;
```

同一记忆可能同时命中向量、全文和图；应用接收了多份正文后再去重。原型将候选阶段改成 `id/arm/rank/score`，在 PG 中融合后再关联正文。下面是原型中的实际函数调用，输入数组来自同一条 SQL 的候选 CTE，不需要先把候选发给应用再传回来：

```sql
SELECT f.*
FROM packed
CROSS JOIN LATERAL recall_probe.rrf_topk(
    packed.ids, packed.ranks, $5, 60::float8
) f;
```

`$5` 为候选上限。该函数按 UUID 合并并累加 RRF，按分数与首次出现顺序保留 Top-K；随后对入选 ID 补读 `memory_units`。普通 SQL 对照采用有序 `SUM(1.0/(60+rank))` 和 `LIMIT`，同样能表达这件事。完整的[应用融合对照 SQL](evidence/prototype/baseline-candidate.sql)与[库内融合 SQL](evidence/prototype/pushed-candidate.sql)均保留。

**当前收益主要是减少重复正文的传输和对象构造。** 当前只有 109 个唯一事实，低于 Top-300，几乎不存在“把大批唯一候选裁掉”的空间。不能将其描述为从 300 条减少到 35 条，也不能把传输节省等同于索引扫描工作量下降。

### 7.4 真正值得继续研发的部分：让候选生成与融合共同停止

本轮 C 函数先接收完整候选数组，再完成累分和 Top-K。它没有控制子计划，因此仍会把候选全部生成出来。**下一步重点应是候选流与融合执行器协同，而不是继续包装函数接口。**

拟采用 CustomScan/自定义路径承接候选 DAG：向量和全文等子计划输出窄 tuple slot；种子满足条件后启动有界关系扩展；融合状态按 ID 保存累计分与来源状态。执行器既要决定下一个读取哪一路，也要在可以证明的情况下停止继续拉取。

RRF 可利用各路已读取的排名前沿推算剩余贡献上界。例如某候选尚未在某路出现，而该路已读到排名 r，则它在这一路的潜在贡献不超过 `1/(60+r+1)`。前提是每路 ID 唯一、排名流满足约定，且上界覆盖尚未完成的图/时间分支。将已知分数、各未完成来源的上界及当前第 K 名一起比较，才有机会证明无需继续读取。证明须包括未见候选与并列规则；前提不成立或上界过松时仍必须读完，不能强行宣布剪枝成功。

这里保证的是**给定候选臂语义下的 RRF Top-K**，不能据此把近似 ANN 变成精确全库检索；也不能拿 RRF 上界去保证神经模型的最终分数。模型重排前的候选裁剪属于另一层质量/成本选择。

验收要看“实际少访问多少索引候选、少读多少 heap/TOAST、少生成多少中间行、并行后关键路径缩短多少”，同时检查 P95、CPU 和总工作量。若只是把应用 CPU 转移到 PG CPU，而查询总工作没有减少，就不算该项研发目标达成。

### 7.5 模型能力如何落地，避免把推理成本藏进数据库

首先复用已经验证的 BGE 批量接口：PG 先提供入选 ID 与模型所需文本，由近库执行器评分，再以 ID＋分数回送后续评分/预算阶段。模型权重版本、输入模板、截断长度、精度和回退策略必须与基线一致。**同样的 109 对输入仍需完成同样的模型计算；近库不等于少算。**

第一版允许 `full_recall` 适配层内部有“候选 SQL → 模型执行 → 结果处理/补读”的阶段往返；`full_recall` 是一次存储接管，不等于全流程只能是一条 SQL。不能为了宣传“一条 SQL”让普通 backend 无控制地等待长时间模型调用。若后续研发可挂起/恢复的模型子计划，还需单独解决资源占用、取消、快照寿命和故障恢复。

对于当前 Bank，BGE 的 6 秒级完整 Recall 与毫秒级候选处理形成明显量级差异。要降低 BGE 路径时延，应独立验证推理实现、硬件和安全的模型输入减少机制；缩小候选集合会改变算法，必须重新评估质量，不能计作等价下推收益。当前已存在候选上限参数，不将调参重新列为内核研发。

## 8. 夜间原型：已经做了什么，证据支持到哪里

### 8.1 使用真实打榜 Bank 的只读快照，未改动打榜环境

从打榜使用的 `locomo_conv30_20261118_200523` 专用 schema 只读导出，在独立 Unix socket、独立数据目录的 PG 18.4 实例恢复，使用已安装的 pgvector 0.8.6。数据包含 **109 条事实、2,212 条关系、373 条事实—实体关联、115 个实体、19 份文档、36 个原文块**。试验结束核对源库与快照逐表行数及内容摘要一致。[数据与环境核验](evidence/prototype-data-audit.json)

用户指定的 PG 源码为 18.4、提交 `f5cc81719e6da4cbdb1f797c48b693e91018153a`。在独立 worktree 实现 C 函数并用 PGXS 编译，没有改动原 PG 工作区的已有修改，也未替换运行中的 PG 二进制。

实现包括：

- 通用 `rrf_topk(uuid[], ranks[], K, rrf_constant)`：哈希合并、有界堆、稳定并列顺序；不认识任何 Agent Memory 业务类型。
- 通用 `budget_select(...)`：使用调用方提供的准确 Token 成本做预算选择；已做差分测试，**未接入本次完整路径计时**。
- `PGRecallPrototype.full_recall`：候选检索/融合在 PG，评分、BPE 与原文处理仍复用应用代码；不支持的请求返回 `None`。
- 同一候选 DAG 的 Python 融合、普通 SQL 融合和 C 函数融合三条对照路径。

这是 **C 函数与存储适配原型，不是已经完成的 CustomScan 执行器**。原型接收预先分析好的请求、冻结查询向量，并仅覆盖本数据集的 world-only 形状；自然语言时间解析在计时前准备。两道有时间条件的题回退到未修改的 store 路径，其余 79 题执行候选下推。默认多事实类型、标签/来源、模型模式及完整扩展加载生命周期尚未覆盖；**不能配置到 8892 作为产品后端直接替换。**

### 8.2 正确性验证：融合函数等价，不等于整条新 SQL 已等价替换线上

| 验证 | 实际结果 | 结论 |
| --- | --- | --- |
| 对未修改 Hindsight 的原始候选排名做 C 融合回放，包含两道时间题 | **81/81 的 ID、顺序、RRF 分数精确一致** | 融合函数保留了现有 RRF 的计算语义 |
| 随机、重复 ID、并列、空集、Top-K、预算与异常输入 | 8 项 PG 实例测试通过，其中包含 400 轮 RRF＋400 轮预算差分 | 覆盖函数边界；不是完整产品契约测试 |
| 三条受控路径：统一并列规则，79 题下推＋2 题相同回退 | 81 题响应一致；每条路径 10 轮、共 2,430 次计时调用均核对冻结响应 | 可以比较这三条路径的执行成本及 Token 等价性 |

| 对比旧 81 题的最终打包字符串 | 没有逐题完全相同的上下文 | **不能直接继承旧 70/81 成绩，更不能宣称原型提高了准确率** |

已核验当前 store 的并列顺序差异：将未修改 store 的各臂统一为“分数降序、UUID 升序”后，79/79 题的 RRF ID、顺序、分数及来源排名与受控 DAG 一致。现有图融合使用 Python 集合迭代，受控 SQL 显式打破并列；排序位置会影响 RRF 与预算。正式接入前须明确并列规则，在两侧同时实现并作为独立变更验收，不能把它藏在性能优化中。[并列规则核验](evidence/candidate-order-audit.json)

历史 8892 部署与当前源码分支还存在版本差异。因此，即使解释了当前 store 的并列差异，也不能直接继承旧运行的答卷分数。

证据：[原始四路融合回放](evidence/source-fusion-equivalence.json)、[完整结果摘要](evidence/prototype-results.json)。

### 8.3 时延和搬运实测：有小幅改善，尚未证明端到端显著收益

最终实验使用同一 PG 实例、相同候选 SQL 和评分/预算代码；单并发、热缓存、固定种子随机交错三条路径，每条 81 题×10 轮。每路检索预算 1,000、融合候选上限 300，与现有 high 预算设置对齐；本 Bank 总共只有 109 条事实。**计时从调用实验适配层到得到 RecallResult，不含 embedding、时间分析、HTTP、reader 或 judge。** 它不是 8892 API P95。

路径一也使用改写后的候选 DAG；这组实验隔离的是“融合放在哪一侧、正文在融合前还是融合后传出”的差异，不是直接拿 8892 原实现与完整新内核比较。

| 指标 | 路径一：Python 融合 | 路径二：普通 SQL 融合 | 路径三：C 函数融合 |
| --- | ---: | ---: | ---: |
| 适配层平均耗时 | 6.778 ms | 7.063 ms | 6.579 ms |
| 适配层 P95 | **7.124 ms** | **7.386 ms** | **6.884 ms** |
| 候选处理 P95 | 2.491 ms | 2.655 ms | 2.267 ms |
| SQL 返回候选行数均值，仅 79 题下推分支 | 249.27 | 107.72 | 107.72 |
| SQL 返回的 text＋context UTF-8 字节均值，仅 79 题 | 80,253.80 | 34,728.92 | 34,728.92 |

路径三相对路径一的适配层 P95 点估计减少 **0.241 ms，约 3.4%**。搬运统计仅对 79 题直接下推分支计算实际查询回包的 `text＋context`，减少 **56.7%**；两道回退题不混入这项物理回包统计。字节不包含 PG 协议、其他列，不代表 heap I/O 或模型 Token。

按题目成组重采样，P95 节省量的探索性 95% 区间为 **−0.195—0.351 ms，跨过 0**。此前开发轮次的点估计也只有零点几毫秒，参数与实现修正均保留。单 Bank、宿主机干扰和微小差异限制了解释力，**不能据此承诺产品 API P95 有稳定、显著的下降**。普通 SQL 路径在本规模下更慢，也说明“下推”本身不是性能保证。[全部计时](evidence/prototype-timings.json)、[保留的全部实验轮次与修正说明](evidence/prototype-trials.json)

查询计划没有 `Gather`/`Parallel Append`；本轮没有证明查询内并行。C 路径仍需完整生成候选并构造数组，**没有实现或证明动态提前剪枝**。当前小 Bank 的唯一事实少于 Top-300，更不适合据此估计海量数据的剪枝效果。[去除查询向量等字面量的计划摘要](evidence/prototype-explain-summary.json)

### 8.4 准确率与 Token 的结论

**准确率：本轮没有新的下推准确率。** 原始排名回放证明的是融合等价性；受控路径证明的是同输入条件下执行成本的差异。新 DAG 改了并列顺序，且没有新增 reader/judge，因此不提供虚构的“下推后 76/81”或“提升 7.41 个百分点”。76/81 属于另一会话已完成的 BGE 排序实验。

**Token：受控三条路径的最终打包内容相同，Token 节省为 0。** 最终实验的 81 份上下文合计均为 631,045 个 `o200k_base` Token；这也不是旧 RRF 运行的 629,001，因为它们的上下文并不相同。候选正文传输减少与模型 Token 不变可以同时成立。

**P95：目前只测得受控适配层的微小改善，没有测得完整 HTTP 下推对照。** 不将 7 ms 与原服务 538 ms 或 BGE 6.85 s 直接相减，更不将几个阶段的 P95 相加。当前证据支持继续验证大 Bank 的执行效率，不支持将本次微测当成端到端加速承诺。

## 9. 公平使用现有 81 题：下一次正式 A/B 的验收条件

### 9.1 先做到真正的等价接入

冻结原 Bank 快照、查询向量、时间锚点、并列规则、模型版本/输入模板、来源关系、min_scores、预算和最终 packer。先完成时间分支、当前实际请求的事实类型、标签/来源和失败回退；逐题核对完整响应、最终 reader prompt，而不只比 ID 集合。

自然语言时间条件尤其要明确：当前 hook 之前传入的 `temporal_window` 主要来自显式参数，传统路径还会解析查询文本。实现应把这次解析正确前移并传入 store，或在 store 内保持等价行为，避免没有显式窗口时误删时间检索。本原型的两道时间题采用既有解析器预先准备并回退，尚未解决完整产品接入。

**未达到逐题等价，就不能用这版原型宣称“仅移动执行位置”的准确率或时延收益。** 若为消除不确定性统一并列规则，应先形成新基线，再比较它的应用侧和库内实现。

### 9.2 性能 A/B 与质量 A/B 分开运行

| 对照 | 固定条件 | 测量目标 |
| --- | --- | --- |
| RRF：应用执行 vs PG 接管 | 同候选、同排名/评分、同最终输入，不调用 BGE | 测执行位置对存储阶段和 Recall HTTP P95 的影响 |
| BGE：应用执行 vs PG 接管 | 同一模型、同一 109 对输入或同样的候选上限、同硬件、同批次/精度/输入模板 | 测近库执行本身的收益，不能夹带模型或输入减少 |
| 证据策略：新旧排序/原文选择/预算 | 每次只改变一项主要策略，reader/judge 与数据固定 | 重新答题、判题，观察准确率/F1、实际 Token 与时延的净变化 |

性能实验复用全部 81 个真实查询、多轮随机交错，分别测试并发 1 与固定的小并发，记录吞吐、成功/超时/失败、P50/P95，以及索引访问、heap/TOAST、行数/字节、模型排队/推理等。查询结果缓存关闭；冷热缓存分开；全部尾延迟与失败保留。两个实现先在同一冻结库比较，再验证完整 HTTP；不能将保存的响应回放时延冒充实时数据库时延。

相同最终 prompt 的等价实验无需为了制造两个分数重复付费生成答案；它提供的是输入等价证据。任何修改最终输入的方案都要使用既有 `benchmarks/memory/runner.py`、固定 AMB reader/judge 做新的完整 81 题运行，并保留所有对错判定及未知用量。不能只重答 q029 等已知错题，再拼入旧答卷组成新成绩。

质量报告同时给出总体准确率、答案 F1、由错变对/由对变错的题目，以及关键证据在“数据库候选 → Recall 返回 → reader 最终输入”三个位置的覆盖。先把 q037/q044 的下游打包丢失与 q073 的上游原文未返回分开定位；不能把 reader 已见依据却答错的问题归为数据库漏召回。

### 9.3 对研发决策的建议

**同意继续做融合执行原型，但不以当前 81 题承诺大幅提速或提分。** 这批题用于正确性与小范围质量检查；内核性能立项还需要更大、更多 Bank 和有代表性的过滤/关系扇出负载。不能复制事实扩容后仍把测试称为真实 LoCoMo 准确率实验。

第一阶段先完成 PG `full_recall` 兼容适配、普通 SQL 基线和实际端到端剖析。只有确认候选生成、搬运或串行调度构成显著成本，再推进候选流融合、依赖感知并行与安全上界剪枝；使用与普通 SQL、应用执行相同的结果质量作为验收条件。

对当前 BGE 路径，模型计算与证据保留是更直接的问题。PG 可以提供更好的执行组织和近库模型能力，但**优化位置、减少模型计算量、提高证据质量是三件需要分别举证的事**。
