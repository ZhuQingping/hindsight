# BEAM 1M：Recall 下推等价性与性能验证报告

2026-11-20 · 独立环境 · 基于第一版 `05d2894c5` 继续优化


版本说明：下列性能与 120 次真实 BGE 数据来自夜间测量版本。随后代码已 rebase 到远程 `18be05bde`；新增默认路径开/关 40 次 HTTP 核对、模型输入哈希和单元测试通过，未重新测量完整 BGE 性能。详见 [整合与验证记录](rebase-validation.md)。

## 1. 本轮结论

**功能可行：完整导入一个 BEAM 1M 会话后，PG 一次候选调用完成检索、RRF 和候选补全。真实本地 BGE 仍在 ContextBase，之后不再补查 PG。在固定相同检索输入的条件下，20 题、3 轮、120 次测量的 Recall 响应全部一致。**

**尚未证明 PG 下推能稳定降低完整 Recall 的平均时延和 P50。** 排除模型的数据库路径诊断中，平均约 52 ms，开启前后基本持平，P50 略有上升；P95 从 124.71 ms 降为 65.11 ms，但补充探针发现长尾与 Python 垃圾回收停顿相关，不能写成 PG 检索算子加速。真实 BGE 的完整 Recall 约 56 秒，其中 CPU 模型重排占 97.1%。本轮不能把完整耗时的小幅波动归因于 PG。

本轮完成了兼容适配、PG 中间结果组织优化、逐题等价验证和性能实验。没有切换 BM25，没有改变候选数、模型、评分或 Token 预算；LoCoMo 原实例和服务未重启或修改。第一版基线保持干净，本轮设计、实现和证据现已 rebase 后纳入独立分支提交，尚未推送。

## 2. 数据是否足够真实，比较是否公平

| 项目 | 本轮实际情况 |
| --- | --- |
| 数据来源 | 固定版本 BEAM 1M split 的首个会话，选择发生在评估结果之前 |
| 完整输入 | 50 文档，985,337 个 `cl100k_base` Token；20 道官方问题 |
| 抽取结果 | 2,524 条事实：world 1,513；experience 1,011 |
| 检索数据 | 1,509 原文块、1,263 实体、9,716 实体关联、62,031 条关系 |
| Retain | GLM 5.3；51 个操作完成，抽取错误 0；50 份原文逐一一致 |
| Recall 请求 | `budget=high`；事实预算 12,288 Token，原文预算 8,192 Token；同一参考时间，默认事实类型 |
| Embedding / rerank | 原有火山 1,024 维 embedding；本地 BGE v2-m3，CPU FP32、batch 8、OMP 4 |
| 数据库 / 主机 | PG 18.4、pgvector 0.8.6、原生全文；Apple M5、24 GiB 内存 |
| 隔离 | 新 PG 55440；关闭/开启服务 8898/8899；同一冻结 Bank |
| 冻结 | 完整 dump；测试后七张记忆表行数与哈希全部不变 |

**BEAM 1M 指会话约 100 万 Token，不是 100 万条事实。** 本数据比原 109 条事实更接近长会话，但仍不能证明百万向量或高并发场景的性能。

Retain 全程使用 GLM 5.3。早期部分操作使用默认推理 effort，后续在同一导入任务中使用网关支持的 low effort；没有为不同对照组重新抽取数据。该调整不影响冻结后 A/B 的数据一致性，但本轮不评价抽取质量。

对照包含原始源码 `0951c3664b`、修改后关闭、最小兼容下推、优化下推。原始源码只用于核对行为；性能表中的关闭组运行同一修改版本的原有路径。没有给原始结果补加同分排序。

**发现并控制了一个外部变量：火山 embedding 对同一请求存在数值波动。** 六次相同输入得到两种不同 FP32 向量，初始实时对照因此出现候选差异，该轮失败记录已保留。正式验证固定两边用于检索的真实查询向量，并固定参考时间；每次仍实际调用火山，计入其网络等待，BGE 输入和输出不作替换。因此下文完整时延属于“受控端到端”，不是任意时刻独立请求都能逐字相等的承诺。

依据：[数据与冻结](evidence/dataset-and-freeze.json)、[逐题等价证据](evidence/equivalence.json)、[模型调用与时延明细](evidence/controlled-http-timings.json)。

## 3. 实际改了什么

### 3.1 先补齐第一版不支持的真实路径

第一版直接用于本数据时，14 题会被“查询词超过原生全文阈值”检查拒绝；余下 6 题仍会被实际存在的 experience 数据拒绝。它不能直接作为本轮完整对照。

本轮增加独立兼容版本，复用原始 SQL 模板，在 PG 内执行原有选词逻辑，按原规则处理 world/experience 的检索预算、合并顺序和时间扩展。此项属于范围补齐，不计算为性能优化。observation 实际数据和附件等仍不在本轮支持范围。

### 3.2 保留查询语义，减少 PG 内部复制与逐条处理

最小兼容版用不断增长的 JSONB 数组和分数字典组织候选，包装下推自身产生了明显开销。选定的优化版 P3 改为类型化候选数组，批量合并图分数，再复用第一版 C RRF。

```text
原 Recall 接口
    |
ContextBase：查询向量、请求参数、时间窗口
    |
一次参数化 PG 候选调用
    ├─ 原生向量 + 全文检索
    ├─ 依赖向量种子的关系扩展 + 条件触发的时间检索
    ├─ 类型化候选数组 → 批量图分数合并 → C RRF / 前 300
    └─ 补齐事实与可能需要的原文块，一次返回
    |
ContextBase：真实 BGE → 原有评分 → 原有事实/原文预算
    |
完整 Recall 响应；模型后不再补查 PG
```

```sql
SELECT recall_beam_arrays.candidates($1::jsonb, $2::name) AS bundle;
```

两个参数分别是服务端生成的候选请求与认证解析出的 schema。JSON 内的原始查询模板由服务端生成。入口不是面向客户端的任意 SQL 执行接口。

图分数仍严格按原 `(entity + semantic) + causal` 顺序相加；保留原集合枚举、同分顺序和浮点行为。没有把 SQL 改成按 UUID 排序来“制造等价”。连接在 BGE 执行前归还。此次每题四路原始候选合计为 967～4,024 条，仍统一保留 300 对输入给 BGE，最终返回 182～241 条事实；下推没有减少模型工作量。

**这是 SQL/PL/pgSQL 实现优化，复用现有 C RRF；本轮没有修改 PG 主干 C 代码，也没有新增 C 算子。** 入口内部仍有多条 SQL，尚未成为统一物理执行计划；本轮选定实现没有跨检索路的查询内并行，也没有新增分数上界剪枝。**原流程通过 `asyncio.gather` 按事实类型并发执行图检索；本版 PG `FOREACH/EXECUTE` 按类型串行，封装为一次调用并没有保留这部分并发。** 这是后续要解决的执行结构问题，不能把“库内连续处理”写成已经并行。

### 3.3 调用次数减少，但不等于全部工作减少

正确性抓取中，原路径通常有 5～6 次候选与补全业务 SQL，触发时间路径的请求为 7 次；驱动首次类型发现、Bank 配置及 native 服务鉴权另计。优化下推的候选业务入口为 1 次；真实服务预热已由 PG 日志核对，正式 61 次开启请求均命中下推，没有静默回退。

为保证模型之后不补查，PG 会提前返回前 300 候选可能使用的原文；其中一部分最终不会装入预算。因此调用更少，并不必然意味着读取字节更少或总时延更短。详见 [实际 SQL、作用与逐题次数](SQL交互证据.md)。

## 4. 性能结果：三种口径分开看

P95 使用样本排序后的最近秩方法；不混用三组样本，也不把预热加入统计。

### 4.1 PG 入口：优化了下推实现本身

同一冻结参数；每版本 300 次，排除两轮预热，题目和版本顺序随机交错。包含参数传输、PG 执行、JSON 编码与结果传输，不包含模型及 Python 最终处理。

| PG 候选入口 | 平均 ms | P50 ms | P95 ms |
| --- | ---: | ---: | ---: |
| 最小兼容下推 B0 | 248.09 | 227.54 | 388.64 |
| P2：仅向量/全文使用数组 | 149.78 | 151.93 | 193.46 |
| P3：增加图候选数组与批量合并 | 36.88 | 38.17 | 48.71 |

P3 消除了最小兼容下推版的大量中间态开销。**248.09 → 36.88 ms 是两个下推实现之间的收益，不能说成超过原始 ContextBase 的收益。** 每次返回的完整候选包均做了等价核对。

依据：[PG 入口 1,200 个测量样本](evidence/pg-entry-timings.json)。

### 4.2 数据库路径：P95 改善，平均和 P50 未改善

冻结向量，以透传 RRF 分数替代真实 BGE；其余检索、评分、预算和 HTTP 返回流程照常执行。采用 ABCCBA 交错块，各块排除一整轮预热；每路径 200 次，关闭重型观察器。

| 路径 | 平均 ms | P50 ms | P95 ms |
| --- | ---: | ---: | ---: |
| 关闭下推，原有查询流程 | 52.29 | 48.19 | 124.71 |
| 开启 P3 | 51.94 | 51.64 | 65.11 |

平均仅相差约 0.35 ms；P50 增加约 3.45 ms；P95 减少约 59.60 ms（47.8%）。这是数据库交互及其余 Python 处理的诊断结果，不能直接替代真实模型参与的完整 Recall P95。补充 GC 探针中，原路径全部 6 次超过 100 ms 的请求都伴随 Python 二代垃圾回收，P3 为 1 次。仅在独立诊断进程暂时关闭 GC 后，原路径 P95 为 61.00 ms，P3 为 63.44 ms，原有大部分长尾消失；平均分别为 46.02 / 50.14 ms。**因此本轮 P95 改善与 Python GC 停顿减少一致，没有证据说明向量或图 SQL 本身变快。** 这组验证的客户端与 API 同进程，不能直接外推为独立部署服务的生产 P95；关闭 GC 只是归因实验，没有改动产品配置。

依据：[数据库路径明细](evidence/database-path-timings.json)、[GC 归因对照](evidence/gc-diagnostic.json)。

### 4.3 真实 BGE：完整 Recall 的主要耗时仍在模型

20 题 × 3 轮，每组 60 次；单请求运行，逐题交错开/关顺序，另有每组一次预热。使用真实火山请求和真实本地 BGE；检索向量固定，比较的是同一候选工作量。

| 完整 Recall，单位秒 | 平均 | P50 | P95 |
| --- | ---: | ---: | ---: |
| 关闭下推 | 56.450 | 55.664 | 62.586 |
| 开启 P3 | 56.186 | 55.394 | 62.220 |

开启组平均少约 0.264 秒（0.47%），其中 BGE 本身平均少约 0.252 秒，embedding 少约 0.011 秒。**逐请求扣除实际 BGE 与 embedding 时间后，其余 PG/Python/HTTP 平均仅从 100.54 ms 变为 98.68 ms。完整耗时的差值主要来自模型执行波动，不能据此宣称 PG 贡献了 0.264 秒收益。**

| 关闭组平均耗时构成 | 耗时 | 占完整 Recall |
| --- | ---: | ---: |
| 实际本地 BGE | 54.830 秒 | 97.13% |
| 实际 embedding 请求 | 1.520 秒 | 2.69% |
| PG、Python 及 HTTP 其余处理 | 100.54 ms | 0.18% |

即使把当前其余处理全部消除，完整平均时延的理论上限收益也只有约 0.18%。这说明**在本机 CPU BGE 配置下，仅继续压缩几十毫秒 PG 时间，难以显著改善完整平均 Recall**。该判断只适用于本数据、主机和模型配置；更快模型、远程数据库、大量事实或并发负载需要重新测量。

依据：[120 次受控端到端与模型分解](evidence/controlled-http-timings.json)。

## 5. 索引、计划和并行尝试的实际结论

| 尝试 | 实测证据 | 本轮处理 |
| --- | --- | --- |
| 图覆盖索引 | 在物理克隆上建立 `(from_unit_id, link_type, weight DESC) INCLUDE (to_unit_id, bank_id, entity_id)`；代表题实际使用新索引，候选等价；平均 35.13 → 35.40 ms，P95 46.58 → 48.43 ms | 无收益，不改主实验实例索引 |
| custom/generic 计划 | 克隆上对原路径分别强制计划类型，三种模式各 200 样本且响应一致；平均约 50.74～52.68 ms，没有明显改善 | 属于已有 PG 参数诊断，不计为内核成果；尾延迟原因未闭环 |
| 原文标量结果集 P4 | 模型输入和响应等价；数据库路径平均 51.31 ms，P50 50.15 ms，P95 63.85 ms，相对 P3 改善很小 | 不增加推荐实现的传输协议复杂度 |
| 原有图任务并发 | 源码 `asyncio.gather`；补充观测中 world/experience 两个 SQL 客户端执行区间重叠；P3 使用串行循环 | 后续应保留该并发，再评估净收益；不能只统计调用次数 |
| 图任务函数 UNION P5 | 实际嵌套计划未出现 Gather/Parallel Append 或并行 worker，并且更慢 | 不采用，不宣称已并行 |

没有把失败或无收益实验删掉。覆盖索引和计划实验均在独立物理克隆上运行，结束后克隆已关闭。不能从一次覆盖索引无收益推出“图索引不值得做”，也不能从本次 UNION 未并行推出“PG 不支持并行”。依据：[实验汇总](evidence/experiments.json)。

## 6. 等价性、准确率和 Token 边界

| 验证项 | 结果 |
| --- | --- |
| 原始 / 修改后关闭 / 兼容下推 / P3 | 20/20 四路 ID、顺序、分数和 RRF 结果一致 |
| 原始源码准备的模型输入与 P3 | 20/20 一致，每题 300 对 query/text |
| 实际 BGE 对照 | 120/120 响应一致；BGE 输入与原始源码一致，模型分数哈希一致 |
| 额外时间窗口请求 | 2/2 一致，覆盖 world/experience，排除在正式 20 题性能样本之外 |
| 全文选词 | 500 个组合与原函数一致，包括停用词、重复词和错误回退 |
| 历史 109 事实 / 81 题 | 在新 PG 的独立恢复库中逐题候选包一致；没有访问活动 LoCoMo 库 |
| 数据与基线 | 七张记忆表哈希不变；第一版工作区干净 |

本轮没有运行 reader/judge，也没有生成新的 LoCoMo 或 BEAM 准确率。相同输入、评分与返回正文支持“下推没有改变这批请求的证据”，不支持“准确率提高”。同理，模型输入与最终响应一致，**本轮没有 Token 节省**；减少数据库调用不等于减少模型 Token。

等价范围限定为冻结 Bank、已验证请求、相同向量/参考时间、CPython 3.11 的受控同分顺序配置。observation 实际数据、标签过滤、附件、实体补全等其余形状不能据此宣称已覆盖；不支持的请求保留原路径，执行后发生错误会直接暴露，不静默重跑查询。

## 7. 后续如何判断还值不值得继续做 PG 性能

**本版保留为等价、可测的下推原型；不以完整平均时延提升作为当前交付收益。** 补充实验已发现两个关键事实：当前诊断 P95 的主要长尾与 Python GC 同步；PG 过程又把原有按类型图任务并发改成了串行。因此不应从“SQL 调用少了”直接跳到“大规模内核研发值得做”。

1. **先保住已有并发，再考虑新增并发。** 原始 `PostgresMemories.recall_unified` 使用 `asyncio.gather`；world/experience 图 SQL 的客户端执行区间确有重叠，P3 的 `FOREACH/EXECUTE` 则串行。单次 PG 调用若继续推进，应以能实际调度独立任务的执行结构为目标，保留原游标顺序、类型预算与 RRF；验收要看到 worker 和重叠执行。它是 P50 退步的待验证解释，当前尚未证明净收益。
2. **用 PG 实际执行时间决定优化对象。** 下一轮把独立服务里的 SQL 时间、Python 分配/GC、序列化分别计量；已有覆盖索引和计划模式没有给出明显收益，不继续盲目加索引。当前 GC 归因发生在同进程诊断，不能替代独立服务的数据库测量。
3. **规模证据不足时，不预先承诺大内核收益。** 先扩大完整会话及真实事实规模，再复测关键路径与资源消耗。单会话 2,524 事实不足以支撑专用 ANN 或图存储内核投入；也没有理由因本轮结果否定更大规模场景。

依据：[图任务调度观测](evidence/graph-scheduling.json)。

如目标优先级仍是当前机器上的完整平均 Recall，模型执行应另设公平对照。它与数据库优化分开立项和计量，不能通过减少候选或更换模型配置来包装本次 PG 收益。
