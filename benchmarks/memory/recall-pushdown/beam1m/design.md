# BEAM 1M：Recall 下推等价适配与性能优化设计


本轮已完成，实际结论见 [性能验证报告](BEAM1M-Recall下推性能验证报告.md)：结果等价，但未证明完整平均/P50收益；诊断 P95 长尾与 Python GC 相关，原有按类型图任务并发尚未保留。

## 1. 目标与边界

在同一冻结数据、同一查询向量、同一时间和模型配置下，减少 Recall 的数据库处理开销；保留候选、RRF 名次、模型输入和最终响应。第一版 `05d2894c5` 已单独保护；LoCoMo 环境不参与本次导入和性能实验。

对外仍使用原 Recall HTTP 接口。客户端不传 `full_recall` 开关。服务端通过 Memories 扩展选择普通 Postgres 路径或实验下推路径。PG 只处理候选阶段，BGE、最终评分和 Token 预算继续使用 ContextBase 原流程。

## 2. 数据与原始支持范围

固定版本 BEAM 1M 的首个完整会话：50 文档、20 问题，约 98.5 万输入 Token。实际抽取 2,524 条事实（world 1,513；experience 1,011）、1,509 个原文块和 62,031 条关系。BEAM 1M 指会话长度，不是 100 万条向量。

第一版在该数据上不能直接作为完整基线：14 题因查询词数超过原生全文阈值被 Python guard 拒绝；其余 6 题仍会因实际存在 experience 事实被 PG 拒绝。不能删除 experience 或改变请求来绕过这个问题。

因此先增加独立的兼容基线 `recall_beam_compatible.candidates`：保持原始 native UNION、按类型的检索预算、合并顺序和同分规则，支持 world/experience；将原有全文选词逻辑放进本次 PG 调用。observation 实际数据、附件及其余不支持的请求形状仍有明确边界。兼容适配不计为性能收益。

## 3. 选定实现：类型化候选与批量图分数合并

选定类：`ArrayPostgresRecallMemories`；PG 入口：`recall_beam_arrays.candidates`。

```text
原 Recall HTTP 请求
  -> ContextBase 生成查询向量、解析参数和时间范围
  -> 一次参数化 PG 候选调用
       原生向量/全文查询
       + 按事实类型进行图扩展、时间扩展
       -> 类型化候选数组、批量图分数合并
       -> 第一版 C RRF、前 300 条
       -> 补齐事实与所需原文块，一次返回
  -> ContextBase 实际调用本地 BGE
  -> 原有评分与 Token 预算处理
  -> 原 Recall 响应，无候选补查
```

原生查询模板和游标返回顺序保留。向量、全文及图候选的中间态采用 UUID/float8 数组，避免不断复制增长的 JSONB 数组、分数字典。图分数用批量 SQL 合并，严格保留 `(entity + semantic) + causal` 的浮点运算顺序及原始集合枚举顺序。最终仍调用第一版 C RRF；不添加 UUID 同分排序，不减少候选，不修改模型、评分或预算。

连接在模型执行前归还连接池。单次候选业务调用不等于整个 HTTP 请求只产生一条数据库语句；原有鉴权、Bank 配置和连接设置另有固定交互。必须分别统计。

## 4. 实验演进与未选中的独立版本

- P1：按需计算补全距离，单独收益很小；这一改动已并入 P3，不单独采用 P1 入口。
- P2：只把向量/全文候选改为数组，仍有图分数 JSONB 复制；P3 继承并继续优化，不单独采用 P2。
- P4：用一个标量行结果集传输原文，20 题结果和模型输入等价，但平均时延改善很小，暂不增加推荐实现的协议复杂度。
- 图覆盖索引：在物理克隆上新增相同键序的覆盖索引，结果等价，但未获得收益，未修改冻结主实例索引。
- P5：将独立图任务写成函数 UNION；代表题实际计划未出现 Gather/Parallel Append，不能称为已实现库内并行，不采用。

本轮推荐实现没有实现跨检索路的查询内并行。图扩展依赖向量种子，也不能把四路简单描述为完全独立。PG 现有并行能力不代表包装成 PL/pgSQL 后就会自动并行。

## 5. 公平比较

原始代码 `0951c3664b`、修改后关闭、兼容下推、优化下推：固定同一数据和向量，逐题比较四路 ID/顺序/分数、RRF、模型输入和响应。没有给原始版额外排序。另加两个显式时间窗口请求验证混合事实类型的时间路径；它们不混入正式 20 题样本。

PG 入口：每版本 300 次测量，排除两轮预热，题目和版本顺序用固定种子打乱。

数据库路径诊断：冻结查询向量，以 RRF passthrough 代替真实模型，关闭重型观察器；采用 ABCCBA 交错块，排除各块一整轮预热。此指标不能当作完整生产 Recall 时延。

实际服务：两套独立 native ContextBase 使用同一冻结 PG；模型配置相同，真实 BGE，每题交错开/关顺序，共 3 轮。发现火山 embedding 对相同请求返回数值波动后，明确固定检索输入向量；仍实际调用火山并计入网络等待。两边 BGE 输入与输出只记录哈希，原始失败样本单独保留，不进入性能统计。

## 6. 验收与交付

最终报告分别列出 PG 入口、排除模型的诊断和包含真实 BGE 的受控端到端指标。不能把消除实验下推版额外开销的收益，直接说成超过原始 ContextBase 的收益。若平均或 P50 没有改善，报告必须明确写出。

不运行新的 reader/judge，不声称准确率提高；相同响应和模型输入意味着相同打包规则下的证据与 Token 不变。首版基线、失败探索和原始证据均保留；夜间阶段原先不自动提交。用户随后明确授权 rebase 与提交：现已整合远程 `18be05bde`，在独立实验分支提交本轮设计、实现及证据，未推送；并行研发仍暂停。

## 7. Rebase 后的集成边界

远程整合基线为 `18be05bde`，包含 opt-in Recall Profile。默认 Profile 的开关下推核对通过；本轮没有扩大公开 API。

`recall_profile=locomo` 的文档日期补读是另一项功能，可能在召回后产生额外元数据 SQL，不属于本轮默认请求“一次候选调用、模型后无候选补查”的已验证范围。不能因合并了相关代码，就宣称该 Profile 也只有一次数据库交互。

历史性能仍绑定夜间测量版本；本次只新增兼容与等价核对，不把历史测量写成 rebase 后的新性能结果。并行与动态剪枝仍未实现，后续研发暂停。详见 [整合记录](rebase-validation.md)。
