# 下一步计划：一晚补齐现有 81 题 Recall 下推

更新日期：2026-11-19。**状态：暂不启动。** 用户已要求先收敛范围并给出安排；本文件是后续执行依据，不是启动授权、正在运行的任务或已完成承诺。

## 1. 交付目标

在固定旧 Bank 和同一批 81 题上，通过 `full_recall` 补齐 PG 时间检索、最终评分、预算选择和本地 BGE 批量桥接，形成可验证的实验版本。既有客户端最终 8K 打包、reader/judge 和固定 AMB 保持同一协议。

详细形状及执行边界以[当前设计](design.md)为准。不扩展到全量 1540 题、V1 窗口算法、其他模型、通用标签/observation/source 或生产级模型平台。

## 2. 6–8 小时安排

| 阶段 | 时间 | 工作 | 检查点 |
| --- | --- | --- | --- |
| 固定共同基线 | 0–1 小时 | 核对实际请求、Bank 快照、high=1000/融合上限300、模型输入模板和资源；选择同一支持 full_recall 的源码版本 | A/B 数据、算法与资源一致；不能一侧使用旧 8892 部署、另一侧使用新源码 |
| 时间与评分 | 1–3 小时 | 补齐两道时间题的候选/有界扩展，迁移最终评分规则 | 时间范围、候选来源、权重和并列规则逐项差分 |
| 预算与 BGE | 3–6 小时 | 准备按内容哈希校验的 Token 成本/截断信息；接入 PG 预算及本地批量重排桥接 | 模型输入一致；评分/预算在 PG 执行，不用题号缓存结果 |
| 集成验收 | 6–8 小时 | 检查全部81题实际接管、完整响应及 reader 输入；做固定负载 HTTP 对照，整理结果 | 两道时间题不回退；保留所有失败、差异和尾延迟，输出实际完成清单 |

6–8 小时是最小实验范围的估算。主要不确定性为浮点/并列排序、Token 截断、模型桥接和失败语义；发现差异先处理正确性，不通过降低验收标准赶时间。

## 3. 执行边界

- 使用独立工作区、PG 克隆和测试入口，保持源 Bank 只读，不重新 retain，不覆盖旧成绩，不重启现有 8892，也不修改正在运行的冻结脚本。
- 启动时记录实际 Git、PG/插件、模型权重、输入模板、预算及资源配置。当前同事维护与运行状态以[主入口](../README.md)为准；本计划不允许同时抢占其 CPU 重排负载后再声称资源相同。
- 复用既有评分、分词、模型及错误处理规则；不在本轮另造质量策略或弱化模型输入。
- 对本次81题之外的未支持请求返回 None；本次81题必须全部走实现路径，不能靠回退、静态候选或旧答案回放通过。
- 准确率评测继续走既有 `runner.py`；旧研究目录的 Python 实验脚本只作历史方法参考，不发展第二套维护入口。

## 4. 验收与归因

**正确性先于计时。** 对全部81题比较候选、来源排名、模型输入/分数、最终评分、事实/原文选择、截断和最终 reader prompt。若统一并列规则，需要两侧同时生效并形成新共同基线。

**性能分层。** 分开报告 PG 执行、模型排队/推理、完整 HTTP Recall 的 P50/P95；固定硬件、批次、并发及请求负载，随机交错、多轮测量。不把原型7ms与历史API538ms或BGE6.85s相减，不把历史缓存时延当新请求时延。

**质量和 Token 分开。** 最终 prompt 相同时，先报告输入等价与执行效率；不为了制造两个分数重复生成答案。若 prompt 变化，使用同一固定协议重新完成81题答题/判题，保留每道原始对错和未知用量，不能拼入旧答卷组成新成绩。上下文字节、reader输入Token和完整模型用量分别统计。

完整答题/判题若受模型网络重试拖延，单独记录进度，不能用历史76/81补齐。未完成的HTTP测试、质量测试必须明确标为未运行或未完成。
