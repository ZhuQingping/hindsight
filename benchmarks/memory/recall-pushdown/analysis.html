1. 结论：下推先争取同准更快，再验证更准或更省

源码确实提供了完整 Recall 的存储侧接管接口，PG 可以沿这个接口建设融合执行。最直接的收益目标是降低 Recall 的执行开销与 P95；准确率和模型 Token 不会仅因执行位置改变而自动改善。

指标 仅做等价执行下推：数据、算法、模型与返回内容保持一致 下推之后再优化检索或证据选择 当前判断
Recall P95 可以争取减少 SQL 往返、候选搬运与串行等待；仍需负载对照验证 可进一步优化访问路径、并发和模型批次，也可能因增加检索或重排而变慢 最直接的性能目标
LoCoMo 准确率 / 答案 F1 送入 reader 的内容不变时，应保持质量，不应预期仅靠下推提分 在相同时间或 Token 预算下，提高关键证据覆盖与排名，才有提分路径 需要独立的质量策略和实验
模型 Token 相同模型输入不变；少传数据库候选不是少用模型 Token 减少冗余证据、改进预算分配，并确认关键依据没有丢失，才可能下降 应验证同等质量下能否减少实际模型输入

建议把收益目标表述为三种可检验结果：同等质量下更快；相同时延下证据更充分；同等质量下输入更精简。 它们可以分别成立，不应先承诺三项同时改善。

本轮验证后的判断：可以实现下推，但当前 109 条事实的 Bank 不足以证明“大幅降低端到端 P95”或“下推提升准确率”。 C 融合函数已通过全部 81 题的原始候选排名回放。79 题受控下推分支减少约 57% 候选正文搬运，但适配层 P95 的改善只有零点几毫秒；普通 SQL 融合还略慢。已有 BGE 实测支持“排序改变可能提分”，同时也显示其 CPU 推理会明显增加时延。两类证据不能混为一谈。

2. 源码确认：预留了什么，当前 PG 做到哪一步

2.1 两个接口的职责不同

接口 返回什么 后续还由谁处理
recall_unified(...) 四路候选：向量、全文、图、时间 Python 引擎继续融合、裁剪、重排、预算筛选和补全
full_recall(FullRecallRequest) 排好顺序并完成所承接阶段的 RecallResult 引擎接到非空结果后直接返回这条存储侧结果

FullRecallRequest 已包含查询文本与向量、事实类型、标签/时间条件、检索预算、重排模式与候选上限、时间及策略权重、最低分、事实与原文预算、tokenizer，以及来源事实等开关。接口默认返回 None，表示不接管；不支持的请求形状应便宜地回退，不能近似执行后冒充等价结果。

默认 PostgresMemories 仍实现 recall_unified、full_recall 默认返回 None。本轮新增的实验子类已实现一次候选下推与共用后处理，见实现报告；不把默认后端与已选择实验扩展混为一谈。历史接口核验记录保持不变。 源码与哈希记录见接口核验。

这里指产品实现。本轮另有隔离的 PGRecallPrototype.full_recall 实验适配器，尚不能作为产品后端直接替换；其候选 DAG、原型范围与兼容性差距见第 8 章。

接口注释中的“四次 store 交互”是候选、补读、原文、实体等阶段调用，不是旧现场的 19 次 PG 业务 SQL。规划可以将核心检索合成一次请求，但认证、配置和统计等仍可能执行其他 SQL，必须分层计数。

4.3 P95 应怎样测

分别报告存储侧执行、Recall HTTP，以及 RAG 问答端到端三类 P95；问答计时不包含离线裁判。存储侧可使用已有 store_stages 与 full_recall 阶段埋点，不要在下推后失去阶段可见性。埋点实现 第 9496 行

固定数据、模型、资源与请求到达率，对单请求、小并发和接近饱和的负载分别测量；区分热缓存、冷打开、超时和重试。小 Bank 与大 Bank、多 Bank 分开。阶段 P95 不能相加得到请求 P95；19 条 SQL 时间求和也不能替代关键路径。

4.4 最新决策：先验证完整 Recall 平均与 P50 的改善上限

当前目标以完整 HTTP Recall 的平均耗时/P50 为准。旧 BGE 81 题平均为 6397.09ms、P50 为 6341.65ms；原型适配层平均 6.778→6.579ms、P50 6.597→6.363ms，两组计时范围不同，不能相减或外推。旧 81 份 BGE 回包的 trace 均为 None，尚不能还原正式服务的 SQL、排队和模型推理占比。

收益预审原建议先用 8 题×3 轮真实 Recall 分段诊断，逐请求计算“拟优化的 PG 关键路径全部消除”的乐观边界，再判断完整平均/P50 是否有业务价值。若上限也不足，不继续为一次调用投入；具体记录项、门槛和后续 A/B 见最小收益验证。该分段诊断未独立执行；用户后续已授权先实现可行性首版，当前进展见实现报告。

5. 准确率与 Token：需要优化证据选择，而非只移动执行位置

5.1 两条有依据的收益路径

路径一：相同时延预算，找到更多有效证据。 等价下推节省的时间可以用于更充分的 ANN 搜索、有界图/时间扩展或更合适的候选重排。它可能改善多跳、时间推理题的证据覆盖，但已经改变了检索策略；更多候选也可能增加噪声。必须与同算法的应用侧实现比较，才能区分策略收益和下推收益。

路径二：相同 Token 预算，让关键证据进入最终输入。 q029 已说明预算前的候选存在，问题出在排名和配额。可以比较重排、事实/原文配额、来源覆盖与冗余处理；q073 则要求保留原文细节，不能以相似为由删掉独有证据。

当前代码已有 prefer_observations 来源去重和事实预算选择；评测客户端也已按完整条目打包、避免硬切 JSON。这些是基线，不能重新包装为下推的新能力。事实选择、客户端打包 第 504 行

5.3 Token 必须分四个口径

口径 下推的直接影响 本次应怎样记录
PG 到应用的候选字节 可通过就地融合、裁剪、延迟取列减少 字节、行数、协议与解码耗时；不用“省 Token”替代
Reranker 输入 同一批 query/text 不会因执行位置改变而缩短 候选数、实际模型分词长度、批次、截断与重试
Reader 实际输入 仅当最终证据或包装改变时，才有下降的机制依据 分开统计记忆上下文与完整 prompt；保持同一 tokenizer
模型实际用量与费用 还受输出、缓存、限流和重试影响 reader、judge、embedding、rerank 分项；未知用量不记为 0

本机协议以 o200k_base 记忆上下文为主口径，同时保留 AMB 的 cl100k_base 统计。不能将 7,765.44 的上下文数当成全部调用 Token，也不能把 1,915→300 的候选裁剪比例当成 reader 的 Token 降幅。

本方案在冻结记忆上比较 Recall，写入期 retain 的 Token 不属于执行下推的直接节省；若同时改变写入策略，需要另建实验。

6. 验证方案：先分离“下推”和“策略”两个变量

组别 改什么 保持什么 用于回答的问题

6.1 B 组先做等价性，不急于重新付费答题

冻结 query embedding、now/question_date、配置及模型版本；逐题比较候选与最终 ID/顺序、正文、相关分数、来源、原文和最终打包字符串。执行统计允许不同。若最终 reader 输入逐字一致，可以先证明没有引入新的信息差异，再运行有必要的模型评估；相同 prompt 下模型仍可能波动，不能把偶然答案变化当作下推提分。

特别需要覆盖：标签/时间过滤、RRF/interleave/重排模式、模型失败回退、来源预算、prefer_observations 和排序并列。当前 chunks 在事实预算筛选前收集；改成只取最终事实的 chunks 会改变结果，不能当作无损优化。当前事实预算对“所有候选均过长”的情况会保留一条完整事实并允许超预算；零预算、空文本与超长事实都要按实际代码做边界差分，不能仅凭文档描述重写。

没有已存在的“强制 Python 路径”请求开关可供假定使用。可用两个测试实例/存储实现对照：默认 PG 的 full_recall 返回 None，原型实现对已支持形状接管，未支持形状仍返回 None。

6.2 C 组再画质量、时延与 Token 的权衡曲线

报告总体准确率与答案 F1，同时按题型和对话分组；补充 gold 证据覆盖和最终上下文中证据覆盖。LoCoMo 的对话证据 ID 与数据库 UUID 不同，需通过入库来源建立映射。不要把已有相关事实未进入最终输入的问题，都归为检索未命中。

性能测试另用重复、固定到达率的请求负载，不将一次 81 题模型作答运行直接当作数据库压测。记录成功、超时和失败；质量分母保留全部应测题，另列成功请求上的质量，避免仅由少超时造成的表观提分混入检索质量结论。

7.3 用实际 SQL 说明：到底少做什么

在当前 LoCoMo 快照上，以本次 world-only、高预算 1,000 的请求剖面调用未修改的 PG store，普通题候选阶段采集到 2 次业务 fetch：向量＋全文组合 SQL、图扩展 SQL。有时间条件的 q047 为 5 次：组合检索、时间候选、两轮时间关系扩展、图扩展。它们尚未计入后续原文补全、鉴权与配置。11 月 12 日另一 Bank 的 19 次 SQL，不应套用到当前每道题。 完整 SQL 与采集范围见当前 SQL 计数、普通题实际组合 SQL。

现有组合查询会在候选阶段读取如下字段（实际 SQL 节选）：

SELECT id, text, context, event_date, occurred_start, occurred_end,
       mentioned_at, fact_type, document_id, chunk_id, tags, metadata,
       proof_count,
       1 - (embedding <=> $1::vector) AS similarity,
       NULL::float AS bm25_score, 'semantic' AS source
FROM ctxdb_ws_locomo_conv30_20261118_200523.memory_units
WHERE bank_id = $2 AND fact_type = 'world'
  AND embedding IS NOT NULL
  AND (1 - (embedding <=> $1::vector)) >= 0.3
ORDER BY embedding <=> $1::vector
LIMIT 1000;

同一记忆可能同时命中向量、全文和图；应用接收了多份正文后再去重。原型将候选阶段改成 id/arm/rank/score，在 PG 中融合后再关联正文。下面是原型中的实际函数调用，输入数组来自同一条 SQL 的候选 CTE，不需要先把候选发给应用再传回来：

SELECT f.*
FROM packed
CROSS JOIN LATERAL recall_probe.rrf_topk(
    packed.ids, packed.ranks, $5, 60::float8
) f;

$5 为候选上限。该函数按 UUID 合并并累加 RRF，按分数与首次出现顺序保留 Top-K；随后对入选 ID 补读 memory_units。普通 SQL 对照采用有序 SUM(1.0/(60+rank)) 和 LIMIT，同样能表达这件事。完整的应用融合对照 SQL与库内融合 SQL均保留。

当前收益主要是减少重复正文的传输和对象构造。 当前只有 109 个唯一事实，低于 Top-300，几乎不存在“把大批唯一候选裁掉”的空间。不能将其描述为从 300 条减少到 35 条，也不能把传输节省等同于索引扫描工作量下降。

7.4 真正值得继续研发的部分：让候选生成与融合共同停止

本轮 C 函数先接收完整候选数组，再完成累分和 Top-K。它没有控制子计划，因此仍会把候选全部生成出来。下一步重点应是候选流与融合执行器协同，而不是继续包装函数接口。

拟采用 CustomScan/自定义路径承接候选 DAG：向量和全文等子计划输出窄 tuple slot；种子满足条件后启动有界关系扩展；融合状态按 ID 保存累计分与来源状态。执行器既要决定下一个读取哪一路，也要在可以证明的情况下停止继续拉取。

RRF 可利用各路已读取的排名前沿推算剩余贡献上界。例如某候选尚未在某路出现，而该路已读到排名 r，则它在这一路的潜在贡献不超过 1/(60+r+1)。前提是每路 ID 唯一、排名流满足约定，且上界覆盖尚未完成的图/时间分支。将已知分数、各未完成来源的上界及当前第 K 名一起比较，才有机会证明无需继续读取。证明须包括未见候选与并列规则；前提不成立或上界过松时仍必须读完，不能强行宣布剪枝成功。

这里保证的是给定候选臂语义下的 RRF Top-K，不能据此把近似 ANN 变成精确全库检索；也不能拿 RRF 上界去保证神经模型的最终分数。模型重排前的候选裁剪属于另一层质量/成本选择。

验收要看“实际少访问多少索引候选、少读多少 heap/TOAST、少生成多少中间行、并行后关键路径缩短多少”，同时检查 P95、CPU 和总工作量。若只是把应用 CPU 转移到 PG CPU，而查询总工作没有减少，就不算该项研发目标达成。

7.5 简化实现：模型与预算保留在 ContextBase

PG 只完成四路候选、RRF/裁剪及补全，一次返回候选正文、各路信号和关联原文并集。ContextBase 复用现有 BGE 输入模板、归一化、最终评分及预算规则；后处理后才返回 RecallResult，不需要 PG 模型桥接。两边具体文件和职责见当前设计。

PG 不知道模型最终选中哪些候选，因此要提前返回其可能用到的原文，不能按最终事实/原文预算提前排除。ContextBase 在内存中按模型排序去重、计数及截断，保持先处理原文、再筛事实预算的原顺序。缺字段暴露为错误，不再补查，也不能伪造空值。这会增加部分原文提前读取和传输，必须测完整包大小，不能继承早期仅候选正文的 56.7% 降幅。

一次参数化 PG 调用结束后释放查询连接，再执行模型；模型等待不再延长该查询快照。响应层也不补查附件或原文。API 外层鉴权/配置与 PG 内部语句单列，不能宣称整个 HTTP 只访问一次 PG。

先前实施估算为6–9小时；本轮已经完成实现与所测81题验收，详见首版报告。本轮首版已实现并通过RRF/BGE各81题验收；完整Recall收益仍未确认，见实现报告。

当前 BGE 的完整 Recall 为秒级，候选处理为毫秒级；相同模型输入仍需同样推理工作。本版不预先承诺显著 P95 改善、提分或省 Token；后续若缩减模型输入，属于改变策略，应另行验证质量。

查询计划没有 Gather/Parallel Append；本轮没有证明查询内并行。C 路径仍需完整生成候选并构造数组，没有实现或证明动态提前剪枝。当前小 Bank 的唯一事实少于 Top-300，更不适合据此估计海量数据的剪枝效果。去除查询向量等字面量的计划摘要

8.4 准确率与 Token 的结论

准确率：本轮没有新的下推准确率。 原始排名回放证明的是融合等价性；受控路径证明的是同输入条件下执行成本的差异。新 DAG 改了并列顺序，且没有新增 reader/judge，因此不提供虚构的“下推后 76/81”或“提升 7.41 个百分点”。76/81 属于另一会话已完成的 BGE 排序实验。

Token：受控三条路径的最终打包内容相同，Token 节省为 0。 最终实验的 81 份上下文合计均为 631,045 个 o200k_base Token；这也不是旧 RRF 运行的 629,001，因为它们的上下文并不相同。候选正文传输减少与模型 Token 不变可以同时成立。

P95：目前只测得受控适配层的微小改善，没有测得完整 HTTP 下推对照。 不将 7 ms 与原服务 538 ms 或 BGE 6.85 s 直接相减，更不将几个阶段的 P95 相加。当前证据支持继续验证大 Bank 的执行效率，不支持将本次微测当成端到端加速承诺。

9. 公平使用现有 81 题：下一次正式 A/B 的验收条件

9.1 先做到真正的等价接入

冻结原 Bank 快照、查询向量、时间锚点、并列规则、模型版本/输入模板、来源关系、min_scores、预算和最终 packer。先完成时间分支、当前实际请求的事实类型、标签/来源和失败回退；逐题核对完整响应、最终 reader prompt，而不只比 ID 集合。

自然语言时间条件尤其要明确：当前 hook 之前传入的 temporal_window 主要来自显式参数，传统路径还会解析查询文本。实现应把这次解析正确前移并传入 store，或在 store 内保持等价行为，避免没有显式窗口时误删时间检索。本原型的两道时间题采用既有解析器预先准备并回退，尚未解决完整产品接入。

未达到逐题等价，就不能用这版原型宣称“仅移动执行位置”的准确率或时延收益。 若为消除不确定性统一并列规则，应先形成新基线，再比较它的应用侧和库内实现。

9.2 性能 A/B 与质量 A/B 分开运行

对照 固定条件 测量目标
RRF：应用执行 vs PG 接管 同候选、同排名/评分、同最终输入，不调用 BGE 测执行位置对存储阶段和 Recall HTTP P95 的影响
BGE：原候选路径 vs PG 候选路径 模型均在 ContextBase；同一模型、同一候选输入、硬件、批次/精度和模板 测候选下推对完整 Recall 的净收益，不混入模型执行位置或输入量变化
证据策略：新旧排序/原文选择/预算 每次只改变一项主要策略，reader/judge 与数据固定 重新答题、判题，观察准确率/F1、实际 Token 与时延的净变化

性能实验复用全部 81 个真实查询、多轮随机交错，分别测试并发 1 与固定的小并发，记录吞吐、成功/超时/失败、P50/P95，以及索引访问、heap/TOAST、行数/字节、模型排队/推理等。查询结果缓存关闭；冷热缓存分开；全部尾延迟与失败保留。两个实现先在同一冻结库比较，再验证完整 HTTP；不能将保存的响应回放时延冒充实时数据库时延。

相同最终 prompt 的等价实验无需为了制造两个分数重复付费生成答案；它提供的是输入等价证据。任何修改最终输入的方案都要使用既有 benchmarks/memory/runner.py、固定 AMB reader/judge 做新的完整 81 题运行，并保留所有对错判定及未知用量。不能只重答 q029 等已知错题，再拼入旧答卷组成新成绩。

质量报告同时给出总体准确率、答案 F1、由错变对/由对变错的题目，以及关键证据在“数据库候选 → Recall 返回 → reader 最终输入”三个位置的覆盖。先把 q037/q044 的下游打包丢失与 q073 的上游原文未返回分开定位；不能把 reader 已见依据却答错的问题归为数据库漏召回。

9.3 对研发决策的建议

同意继续做融合执行原型，但不以当前 81 题承诺大幅提速或提分。 这批题用于正确性与小范围质量检查；内核性能立项还需要更大、更多 Bank 和有代表性的过滤/关系扇出负载。不能复制事实扩容后仍把测试称为真实 LoCoMo 准确率实验。

第一阶段交付“PG 一次取完整候选、ContextBase 后处理、无补查且结果等价”的 81 题版本，不把现有多次查库简单藏进 Python 包装；同结果、一次调用和无补查同时通过后，再分析净收益。只有确认候选生成、搬运或串行调度成本显著，再推进候选流融合、依赖感知并行与安全上界剪枝；仍需保持相同质量。

当前 BGE 路径的模型计算仍占重要部分。本版先验证候选执行与往返收益，模型及证据选择规则不变；改变执行位置、减少模型计算、提高证据质量必须分别举证。
