# 复用本机 PG 与 LoCoMo 数据的下推验证

> 历史验证记录：本文数字来自共同规范化对照，并非未修改原始版。旧下推曾因同分顺序变更而不等价；最新修复与真实原版对照统一见[三组对照与修复验证](three-way-original-compatibility.md)。

更新日期：2026-11-19。状态：RRF与真实本地BGE各81题规范化A/B全部通过；原Bank哈希及PG启动时间未变。本文记录后续原库验证，与先前隔离快照验收分别统计。

**验收结论：下推版与同源码的规范化对照在81题上等价；本文未验证与未修改原始版的兼容性，不能据此宣称原Recall行为完全未变。** 关闭/开启下推分别运行81题，不启用模型与真实BGE两组共324次HTTP请求。两组响应和reader正文均81/81一致，BGE组模型输入81/81一致；下推侧每题一次候选SQL、零后续补查。详细结果见第3节，通用生产请求不在此次验收范围。

本次下推对象是 **ContextBase服务端Recall四路检索之后的RRF融合与候选Top-K**。LoCoMo Python客户端的合并或上下文打包不在下推范围；本次未修改`benchmarks/memory/runner.py`或`support.py`。这里的Top-K是模型前的候选数量上限，不是客户端的Token预算裁剪。

**三组原版对照已有新结论：RRF下推版与未修改原始版81题响应及reader正文均不完全一致，根因为同分UUID排序改变RRF名次；原始版与修改后默认store则81题一致。稳定排序属于策略变更，不能据此宣称无损下推。** 最新进展见[三组原版兼容性验证](three-way-original-compatibility.md)。

## 1. 本次如何接入

直接使用本机已有 PostgreSQL 18.4、端口5432、数据库 `contextbase_gpt61_20261107`，以及原有 Bank `locomo_conv30_20261118_200523`。Bank包含109条world事实；没有执行initdb、Alembic迁移、重新retain或数据导入，没有重启PG或原8892/8891服务。

本版没有修改PG core，也不需要替换postgres二进制。新增内容是独立schema中的下推函数和动态加载的C RRF函数；原有表、索引和Bank配置不修改。

```text
A：127.0.0.1:8895  检索SQL＋服务端 Python RRF ─┐
                                     ├─ 同一台现有PG、同一份LoCoMo Bank
B：127.0.0.1:8896  一次PG候选下推 ────┘
                       |
          两侧使用相同的ContextBase BGE、评分与预算
```

两个测试接口使用相同Recall路由、相同源码和请求。它们是独立的临时验证进程，不是替换现有管理UI、鉴权网关或内置Worker。测试账号只授予目标schema及必要配置的读取权限，默认只读事务，不能写入记忆数据；辅助进程不重复运行原服务的后台维护任务。

## 2. 接口与请求

| 对照 | 地址 |
| --- | --- |
| A，关闭候选下推 | `POST http://127.0.0.1:8895/v1/default/banks/locomo_conv30_20261118_200523/memories/recall` |
| B，启用候选下推 | `POST http://127.0.0.1:8896/v1/default/banks/locomo_conv30_20261118_200523/memories/recall` |

两侧都要求独立测试Bearer Key，绑定loopback，只开放指定Bank的Recall请求。Key与数据库URL仅存放在本机忽略目录，不写入本文或Git。

请求包含同一问题、`budget=high`、事实预算8192、原文预算8192、相同提问时间锚点；实体补全关闭。原81题的真实查询向量固定复用，以隔离embedding波动；BGE仍实际执行。因此本轮HTTP耗时**不包含实时embedding服务时间**。

### 开关下推，与开关模型，分别比较

这里的“原有检索SQL”指PG执行向量、全文、图、时间检索，返回各路候选；不代表整次Recall。原SQL本身不做RRF、不调用BGE。原Recall在SQL返回后，由[服务端 Python RRF函数](../../../hindsight-api-slim/hindsight_api/engine/search/fusion.py)按各路名次合并相同ID、生成融合顺序，再裁剪模型候选。RRF用于融合不同分数尺度的检索结果；Python只是原软件选择的执行位置，本版将这部分计算移入PG。

| 验证组 | A：关闭候选下推 | B：开启候选下推 |
| --- | --- | --- |
| RRF组 | 原有检索SQL → 服务端 Python RRF → 原评分与预算 | PG四路检索＋RRF＋候选补全 → 原评分与预算 |
| BGE组 | 原有检索SQL → 服务端 Python RRF → 真实BGE → 原评分与预算 | PG四路检索＋RRF＋候选补全 → 真实BGE → 原评分与预算 |

**BGE组两侧都实际执行模型。** 下推适配层取回候选并释放PG连接后，调用 `request.runtime.finalize(...)`；共用后处理继续执行原 `reranker_instance.rerank(...)`、评分、预算，再返回完整RecallResult。模型没有下推到PG，执行模型的步骤没有省略。

A加载同源码的原查询对照store，其full_recall返回None；B加载新下推store。没有直接拿旧8892部署和新源码比较。两侧统一UUID并列规则后，逐题检查BGE有序输入哈希、最终HTTP响应和原pack_context的reader正文，同时核对B侧一次候选SQL、无后续补查。RRF组双方都不调用模型，只验证该模式下的等价性。

### 基线定义与兼容性缺口

本轮A不是未修改的原始ContextBase。A/B共用修改后的引擎；A另外加载 `CanonicalPostgresMemories`，将各路结果按分数、UUID排序，并将隐式时间解析前移。B加载PG下推实现。两侧使用同一模型、请求、数据和预算，有助于检验PG实现与共同规则的一致性，但不能排除共用重构带来的同一处错误。

候选顺序可能影响RRF分数、Top-K与最终上下文。统一UUID顺序属于需要验证的行为变化，不能当作JSON字段顺序差异忽略。现有81/81一致的准确表述是“规范化A与B一致”，不是“未修改原始版与B一致”。

原始行为保持需要补做以下三组，不复用规范化A冒充原始基线：

| 组别 | 源码与后端 | 验证目的 |
| --- | --- | --- |
| O | 修改前源码＋原Postgres store | 独立的原始Recall参照 |
| U | 修改后源码＋原Postgres store，不加候选规范化和提前时间解析 | O/U逐题差分，检查共用后处理提取是否改变原行为 |
| B | 修改后源码＋PG下推store | U/B逐题差分，检查真正下推差异 |

先证明O/U一致，再检查U/B。固定数据、查询向量、提问时间、模型与运行配置，逐步比较各路候选、融合排名、模型输入、最终响应及reader正文；所有并列差异保留，不能在比对输出时重新排序以掩盖变化。上述原版兼容性桥接尚未运行，现有定向回归和同源码A/B不能代替它。

### SQL调用与耗时分别怎么看

RRF单轮81题，A侧驱动记录共349次请求内SQL调用，B侧共83次。其中两侧各有2次API外层配置查询；B侧Recall候选阶段固定81次、后续零补查。统计不包含连接预热，PG函数内部仍执行多条SQL，不能称为只有一次底层扫描。

| HTTP指标，毫秒 | 规范化对照A | 候选下推B |
| --- | ---: | ---: |
| RRF 平均 | 18.91 | 13.98 |
| RRF P50 | 17.47 | 12.75 |
| RRF P95 | 27.75 | 19.74 |
| BGE 平均 | 6545.61 | 8078.85 |
| BGE P50 | 6545.90 | 8156.36 |
| BGE P95 | 7813.01 | 8935.43 |

BGE调用跨度平均：A 6521.74ms，B 8052.81ms；逐题HTTP减去该题BGE跨度后的平均：A 23.87ms，B 26.03ms。BGE跨度包含排队/推理/调度，不是纯模型计算时间。

**本轮BGE完整HTTP耗时没有改善：平均6.55→8.08秒；非模型部分23.87→26.03毫秒也未下降。** 时间差主要出现在BGE调用跨度，不能将其全部归因于PG。

**这些是顺序单轮、固定查询向量的观测值，不是随机交错性能试验。** 缓存、模型CPU执行及其他本机负载都会影响差额，不能把完整HTTP差额全部归因于PG；本轮没有建立稳定的端到端提速结论。

## 4. 复用旧库时补齐的启动行为

原引擎读取持久配置前总会执行 `CREATE SCHEMA/TABLE IF NOT EXISTS`。即使表已存在，这类DDL也被只读事务禁止。本轮改为先检查 `to_regclass('ctxdb_meta.system_config')`；已存在时直接读取，仅缺失时保留原首次建表逻辑。

该变化只影响新测试进程的启动，不改写原服务的部署源码。首次失败轮次保留，后续从新冻结版本重新完整验证，没有拼接成功结果。
