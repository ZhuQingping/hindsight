# 更多应用场景

以下场景说明如何把记忆能力放入业务流程。Bank、来源组织和调用时机都由应用决定，不能只靠更换提示词完成接入。

## 对话助手：延续已确认的偏好和背景

### 场景

用户在不同时间表达了写作偏好、当前项目背景和已经完成的事项。下次会话中，助手需要接着工作，减少重复询问。

### 组织来源

| 内容 | 来源组织建议 | 维护方式 |
| --- | --- | --- |
| 一段完整会话 | 使用稳定的会话文档 ID | 应用保存完整快照时用替换；提交新增片段时明确使用追加 |
| 当前偏好 | 单独保存一份偏好文档 | 用户确认改变后替换完整内容 |
| 已完成事项 | 按任务或事件分别保存 | 保留日期、对象和结果 |

如果不同用户需要独立的访问权限，可为各自内容使用不同 Bank，并由应用服务端选择被授权的目标。仅在元数据里记录 `user_id` 或 `session_id`，不会自动建立访问隔离。

### 调用顺序

1. 收到用户问题，保留本轮必要的近期上下文。
2. 用问题和相关背景调用 Recall，补充长期信息。
3. 将命中记忆连同来源交给应用模型，或使用 Reflect 生成回答。
4. 本轮结束后，将需要长期保留的内容写入对应来源。

不需要把每条临时推测、问候或重复工具输出都当作长期背景。应用可以明确区分用户已确认的信息、助手建议以及执行结果，在内容里保留这种区别。

### 偏好变化怎样处理

用户从“希望详细解释”改为“以后优先给简短结论”时，可以替换专门维护的偏好文档。历史会话仍可能包含原来的表述，因此应用还需要决定这些历史内容是否参与当前偏好检索。

例如，为现行偏好文档使用专门标签，并在相关查询中严格筛选；历史会话保留用于事件追溯。不能仅靠不断追加互相矛盾的内容，假定服务总会替应用决定哪一条仍然有效。

### 验证方式

在新会话中提出确实需要该背景的问题，检查返回来源是否属于目标用户和当前偏好文档。验证内容更新时，同时核对原文、召回结果与回答依据，不以模型一句“我记住了”作为写入成功凭证。

## 运维助手：复用已经验证的处理经验

### 场景

同类告警反复出现，排障经验分散在工单、复盘和聊天记录中。助手需要快速找到相似现象、历史原因和已执行的处理办法。

### 每份记录写清什么

一份故障记录至少应让读者理解：

| 信息 | 示例 |
| --- | --- |
| 对象与时间 | 哪个服务、环境、版本，在何时出现问题 |
| 现象 | 告警、错误、用户影响或指标变化 |
| 原因与证据 | 已确认的原因，如何定位 |
| 处理 | 实际执行的动作及前提 |
| 验证 | 怎样确认恢复，是否仍有遗留问题 |

将“怀疑原因”与“已确认原因”分开表述。故障处理结束后再补齐记录；需要修改结论时，更新原来源或清楚记录纠正关系。

### 查询与使用

例如：“支付服务出现连接占用升高，历史上有哪些相似情况，应先核对什么？”

应用可以先召回同一服务或组件范围内的记录，再把历史线索与本次监控、日志和实例状态一起交给 Agent。历史经验提供排查依据，当前状态仍需从业务系统、监控和日志取得。

事件时间有助于理解当时的背景。Recall 的时间窗口可以影响排序，但不是严格的时间过滤条件；需要精确统计某个期间的全部故障时，应结合业务记录查询。

### 整理为知识页

当同类记录积累后，可以围绕稳定问题建立知识页，例如“连接占用升高的常见原因、排查顺序和适用前提”。

知识页用于形成便于阅读的主题材料，原始故障记录仍是依据。新增案例后，应确认页面已经完成相应刷新，不能仅看到页面存在就认定它包含最新故障。

## 从试用转为日常使用

无论哪种场景，都应先用一组有明确来源的小规模资料跑通流程，再检查实际问题的检索与回答效果。

建议关注：

- 是否命中了正确来源，而非只看回答是否通顺。
- 来源过期或出错时，是否有明确的更新与纠正方式。
- 调用方是否选择了正确的 Bank 和内容范围。
- 原文和派生知识的完成状态是否符合使用要求。

操作步骤见[控制台使用](console.md)，调用示例见[项目助手完整案例](project-assistant.md)。
