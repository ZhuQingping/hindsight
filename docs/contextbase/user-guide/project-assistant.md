# 完整案例：让项目助手持续使用团队经验

本例以一个虚构的 Alpha 项目为背景：团队希望新的会话和不同的助手，都能查到现行规范、重要决策及已经解决的问题。项目约定发生变化后，也要能明确更新，而不是依靠不断追加的对话“猜出最新版本”。

## 案例目标

完成后，你可以：

- 将规范、决策和故障记录作为不同来源保存。
- 在新会话中查询项目背景，并回到命中的来源。
- 选择把记忆交给应用自己的模型，或直接调用 Reflect。
- 更新现行规范，核对来源内容，并按需删除演示资料。
- 在控制台查看同一批文档、记忆和任务。

准备一个专用测试 Bank 和具有读写权限的业务 Key。示例使用以 `contextbase_demo_alpha_` 开头的文档 ID；请将这些 ID 留给演示使用。

## 第一步：把资料按来源组织

把三类内容分别提交，后续才能独立更新和清理：

| 来源 | 文档 ID | 保存内容 |
| --- | --- | --- |
| 现行规范 | `contextbase_demo_alpha_rules` | 数据库版本、结构变更与发布要求 |
| 技术决策 | `contextbase_demo_alpha_decision_001` | 连接池上限、作出决定的背景和理由 |
| 故障记录 | `contextbase_demo_alpha_incident_001` | 现象、原因、处理办法和验证结果 |

每份资料都使用 `project:alpha` 和 `guide:project-assistant` 标签。前者表示项目，后者区分这批演示资料；检索时要求同时匹配。

文档 ID 用于管理来源，标签用于筛选，元数据可以记录类别等来源属性。不要用每次调用的新 UUID 代替一份现行规范的稳定文档 ID，否则后续替换时难以定位原文。

对于历史事件，例如每次故障或独立决策，分别分配文档 ID。对于“当前规范”这种需要维护现行版本的内容，沿用同一个 ID。

## 第二步：在形成明确结果后写入

规范可以在发布时写入，决策可以在评审完成后写入，故障记录可以在处理与验证结束后写入。写入内容应能脱离原会话被理解。

例如，与“这个办法有效”相比，下面的记录更有用：

> Alpha 项目出现连接占用升高。排查发现部分异常路径未释放连接；修复后检查活跃连接与未结束事务，确认占用恢复。再次出现类似现象时，先检查连接释放和事务状态，再决定是否调整连接池。

这段内容说明了对象、现象、原因、动作和结果。它是一条演示记录，不代表对任何实际实例的诊断。

本例使用同步处理完成的写入，便于紧接着验证 Recall。Python 的异步 I/O 方法仍然可以等待服务端完成主要处理，详见[异步任务](api/operations.md#sdk-中的两个异步)。

## 第三步：在新任务开始前检索

新的会话需要“修改数据库结构并评估连接问题”时，应用先根据当前问题调用 Recall，而不是把三份资料全文都放进提示词。

本例同时指定两个标签，并使用 `all_strict`，仅检索演示资料。为便于首次验证，示例先检索 `world` 和 `experience`；持续使用时，也可以召回后续整理的 `observation`。

结果应检查三个方面：

| 检查项 | 目的 |
| --- | --- |
| `text` 是否与问题相关 | 判断是否取得有用背景 |
| `document_id` 是否属于预期来源 | 核对资料归属 |
| `chunk_id` 对应的 `chunks` 是否可用 | 需要时读取原始上下文 |

提取的条目数和文字不固定，不应以“必须返回三条”作为成功条件。标签、原文保存配置及来源内容都会影响实际返回结果。

## 第四步：把记忆用于回答

应用有两条路径：

**使用自己的模型或 Agent 流程。** 将命中记忆组织为带来源编号的上下文，与当前问题一起交给应用模型。保留“编号 → 记忆 ID / 文档 ID”的映射，展示回答时才能回到实际来源。

**直接使用 Reflect。** 将问题和相同的标签范围交给 ContextBase，开启回答依据返回。应用展示 `text`，并使用 `based_on` 中实际返回的内容说明依据。

SDK 示例同时演示上下文组织和 Reflect，但不会替应用调用另一个模型服务。组装好的上下文可以接入你已有的模型调用流程。

如果没有命中相关记忆，先检查范围和来源，不要将空结果包装成“已经查证”的结论。

## 第五步：更新现行规范

假设 Alpha 项目决定将示例规范里的数据库版本从 PostgreSQL 16 改为 17，其他发布要求保持不变。继续使用 `contextbase_demo_alpha_rules`，以 `replace` 提交完整的新正文。

这是更新记忆来源，不会操作或升级实际数据库。

随后读取文档详情，确认原文已更新，再执行相关查询。需要区分：

- **现行规范更新**：替换同一份来源。
- **新增历史决策**：新建独立文档，保留发生日期与适用范围。
- **提取结果不准确**：通过控制台纠正相应事实；如果原文也错误，应先修正来源。

一次来源替换不代表所有观察和知识页都已刷新。应用依赖主题页面时，还应检查页面的刷新状态。

## 第六步：查看结果与清理

在控制台选择同一个 Bank，打开文档列表，按 `contextbase_demo_alpha_` 筛选。可以查看三份来源、原始分块和派生记忆，也可以围绕这些资料创建知识页。

两套完整示例默认保留文档，便于查看。附加 `--cleanup` 再运行时，会在流程末尾删除这三份演示来源。删除来源不可撤销，运行前确认 Bank 与示例 ID 未被其他业务复用。

如果另行创建了知识页，也应检查并刷新或清理相应页面。删除来源文档不等于删除已经保存的知识页正文。

## 接入自己的项目时怎样调整

先替换内容来源和写入时机，再决定 Bank、文档 ID 和标签的组织方式。不要直接把演示中的三个固定 ID 用于所有项目。

| 业务情况 | 建议组织方式 |
| --- | --- |
| 一个团队共享项目记忆 | 使用项目 Bank，为客户端分别签发有归属的 Key |
| 同一项目内区分主题 | 在同一 Bank 内用稳定标签筛选 |
| 不同客户需要独立访问权限 | 使用不同 Bank 并分别授权，不只依赖标签 |
| 多个 Agent 共享 | 连接同一服务和 Bank，分别配置有效凭据 |
| 需要追踪会话来源 | 使用应用会话 ID 设计文档 ID 或元数据，明确更新策略 |

客户端会话结束后，只有实际提交到服务并处理完成的内容能够被后续请求使用。共享 Bank 不会让另一个 Agent 直接读取尚未保存的本地上下文。
