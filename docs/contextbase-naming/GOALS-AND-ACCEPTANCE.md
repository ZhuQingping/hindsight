# ContextBase 命名解耦与改名目标、验收合同

状态：`TASK_DEFINED / IMPLEMENTATION_NOT_STARTED / CONTEXTBASE_VALIDATION_NOT_RUN`。2026-10-19。本文件定义新session的任务目标，不声称改名或解耦已经完成。

## 目标及决策来源

用户提出“名词改成ContextBase”，随后质疑“如果还有很多工作量要做，那说明我们之前没做好啊”，最终要求“把我们的目标和验收目标持久化……在新session做个任务”。目标是复用已整合的产品能力，补齐命名解耦，使产品改名成为有边界、可重复、可验证的操作；不能以大批人工字符串替换掩盖设计缺口。

| 项目 | 当前权威及边界 |
| --- | --- |
| 正式产品展示名 | 用户指定`ContextBase`，保留大小写；不能用展示名充当所有机器标识。 |
| 修改量判断 | 先盘点真实需要手改的源入口、生成物、测试输入、兼容/历史引用；分别报告初次解耦改动、日后改名步骤、构建/验收耗时。此前“半天/1–2个人日”估计已撤回，不作为承诺或验收依据。 |
| 命名分层 | 延续既有原则：部署展示与固定发行/协议身份分离。此前“固定agentstratum”是旧整合候选合同，不自动证明新产品名仍须用旧发行名，也不自动授权删除旧标识。 |

新session不必再次询问是否启动任务。先完成盘点与可审查的命名映射，继续独立可推进的工作；确有超出既有授权的外部不兼容变更，再围绕具体差异和影响澄清，不提出笼统的重启确认。

## 产品与工程目标

1. 人看到的产品名统一为`ContextBase`；显示名、技术slug、固定发行身份、协议身份、客户数据分别有明确职责和来源。
2. 品牌默认值、发行元数据和兼容映射有一份逻辑权威定义。Python、TypeScript、Rust、shell/manifest通过薄适配或可重复生成消费它；不要求为此搭建通用多品牌框架。
3. 首次补齐解耦可以修改命名适配层、配置解析、生成/打包入口与有意义的测试。完成后，再改一个品牌应只改明确的品牌输入并运行既定流程，不逐页、逐插件、逐脚本改业务源码。
4. 保留上一轮有效成果：UI布局和原生功能、动态品牌重启/旧页签防护、会话撤销、Origin/Host校验、特殊bank ID、有界搜索分页、原生API/SDK/MCP、客户端远程连接、MCP ownership保护、错误和日志边界、Rust依赖及nullable PATCH修复。
5. 默认复用现有数据与配置，通过显式兼容策略维持旧连接/凭证。展示名变化不应隐式创建新Workspace、重命名bank或切换endpoint。
6. 当前任务不包含多用户、多API Key管理、Workspace schema隔离、数据库重构、业务功能重写、公共云发布、仓库/域名迁移或主干合并。

## 保留旧名称的规则

不要求仓库全文搜索旧词为零。版权/许可证、历史记录、兼容键和别名、原生SDK技术名、客户内容与ID允许保留，并说明原因。面向新客户的当前显示或发行信息若仍保留旧名，必须在映射中解释；不能以“历史”掩盖未改完。也不能将旧词过滤应用到客户数据或错误标识上。

## 完成判定

只有目标范围已明确、N01–N12均有对应结果且阻断问题关闭，才可以标完整交付。范围未定、只改页面、只搜索替换、只写设计、只生成客户端或只跑unit，都不能叫完整完成。真实宿主、真实模型质量、其他平台和云发布若不在本轮执行范围，应分别列NOT_RUN，不作为已通过的本地证明。
