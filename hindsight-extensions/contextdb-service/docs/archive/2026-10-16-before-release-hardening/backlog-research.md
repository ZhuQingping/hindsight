### 1.1 整体走读：统一约定与冲突处理（2026-10-16，待实施）

**后续范围澄清：本次最新确认的是 WS-04——仅将 GET 工作空间详情改为按唯一 workspace_name 查询。它取代本节及 WS-02 中该 GET 按 bank_id 寻址的建议，不据此决定 DELETE、业务 Bank ID、schema 或授权输入的取值。WS-02 的整体可读标识方案保留为候选，不能与本项混成一次已确认改造。**

**结论：优化方向整体合理，但不能把各条建议分别实施后直接拼接。** 本轮以原生 Hindsight 和首发产品需求重新走读；已写代码仅用于识别影响范围，不作为保留某个设计的理由。以下为当时整理的整体方案，工作空间寻址范围按最新 WS-04 澄清；第 2、4、6、8 节中标记已实施的合同仍是运行基线，不能当作目标方案已经上线。

原生 Hindsight 允许调用方指定可读 bank_id，创建、删除和业务接口都使用该标识，另有独立的 name 展示字段。原生删除 Bank 清理该 Bank 的内容，不删除整套共享 schema；我们采用每工作空间一个 schema，因此还需要外围生命周期管理。依据为[原生接口](https://github.com/vectorize-io/hindsight/blob/a77c1f3412a7b82f36588dffce1a8d7480e99cc7/hindsight-api-slim/hindsight_api/api/http.py#L8554)及同提交 memory_engine.py::delete_bank。复用原生 Bank ID 和引擎能力，不照搬其共享 schema 的删除假设。

#### 发现的冲突及统一处理

| 级别 | 涉及条目 | 冲突或遗漏 | 统一处理 |
| --- | --- | --- | --- |
| P1 | WS-02、API-02/05 | 业务用 jiamu，管理和授权仍要求客户填写 UUID | 管理路径、业务调用及授权输入统一使用 bank_id；内部 workspace_id 只承担不可复用的身份与关联 |
| P1 | WS-02/03、API-06 | 等旧 schema 删除完成即可同名重建，不能阻止迟到的旧 DELETE 指向新空间 | 删除携带绑定空间身份和版本的 If-Match；先查幂等历史，再解析当前地址。具体合同见 WS-02 |
| P1 | WS-03、API-02、DB-02 | 删除授权后 selected 至少一项的约束会阻止清理；按可读地址回填还可能继承旧授权 | 内部允许清理后的空 selected，访问全部拒绝；清理授权同步增加 Key 版本，旧编辑提交返回412，不自动绑定同名新空间 |
| P1 | WS-03、API-04/06、DB-06 | 删除空间行会破坏操作外键、结果查询和浏览器恢复；当前删除代码先找空间，历史命中顺序也不符 | 终态操作独立保存原对象快照；空间已删除仍可查原结果。统一服务端与 UI 的重试/查询期限，过期意图不重放 |
| P1 | AUTH-01、UM-09、DB-01/03 | “不增加角色”与统一认证需要 admin/member 不一致；原表注释只描述业务 Key | 普通成员仍无角色选择；后台只增加唯一受保护管理员。表、注释、启动校验和列表排除规则一起调整 |
| P1 | UM-10、AUTH-01、DB-02/04 | 成员名称当前可重复；隐藏管理员加入同一用户表后还可能出现同名歧义 | 实例内 active/disabled 用户名称规范化后唯一，包含内置管理员；软删除后可复用名称，新 ID 不继承旧 Key，存量冲突先处理再迁移 |
| P1 | AUTH-01、DEP-03/05/06 | 认证改为 PG 后，初始化、凭据持久化与 UI 启动仍可能使用旧配置摘要流程 | 先持久保存秘密，再离线建库和写管理员摘要，API 就绪后启动 UI；统一认证后移除运行时 ADMIN_KEY_SHA256，不保留回退 |
| P1 | WS-02/03、DEP-01 | 可读 schema 能复用，而旧初始化/清理执行者可能还在运行 | 清理完成前继续占用名称；执行权必须覆盖实际 DDL 及清理过程，未知执行者阻止复用，不能只比较一次 UUID 或等租约过期 |
| P2 | API-08/09、DEP-05 | 身份接口改名、启动重试和减少重复认证可能相互覆盖 | 统一一个服务端身份检查函数；只对启动依赖故障有限重试，不缓存跨请求授权；改名不新增检查次数 |

#### 下一轮统一模型

| 对外/内部概念 | 约定 |
| --- | --- |
| 对外稳定标识 | 当时整体候选为可读 bank_id；最新 GET 详情单独按 WS-04 使用 workspace_name，其他寻址调整不因本项自动成立 |
| 展示名称 | name，例如“嘉木知识库”；WS-04 用于精确查询时须正确编码，与原生 bank_id 不要求相等。本轮不新增改名接口 |
| 内部身份 | workspace_id，随机32位 ID；用于外键、权限实际绑定、准入和任务代际。保留只读返回供 UI 关联或排查，但不要求客户把它作为工作空间寻址或授权输入 |
| 物理 schema | 新建为 ctxdb_ws_jiamu；从注册映射获取，不从未经验证的 URL 直接拼 SQL。旧空间保持原 schema |
| 指定空间授权 | API 接收 bank_id，受理时解析当前 active 空间并绑定内部 workspace_id；同名重建不继承 |
| 全部空间授权 | 按明确的统一权限覆盖未来空间，也覆盖同名重建的新空间；仍没有管理权限 |
| 管理身份 | 所有 Key 统一从 PG 认证，后台唯一 admin；UI 密码与服务端 Admin Key 继续分开 |
| 空间生命周期 | 保留异步受理与查询；先排空并清理，再释放地址。不是因为现有代码已异步，而是独立 schema 初始化与在线删除存在多步骤和恢复需求 |

不增加 slug、别名服务、第二套管理 MCP、在线实例注册、成员角色选择、独立认证服务或通用任务平台。保留14个管理操作，只调整必要路径参数、字段和删除条件。原生记忆算法、业务请求路径与返回协议保持；新增空间使用原生可读 Bank ID。是否需要原生小范围 hook，以实际安全边界为准，不预先承诺零侵入。

#### 实施依赖与验收门槛

1. **先统一合同**：固定 bank_id 输入/输出、空间 ETag、幂等查找顺序和保留期限，再同步模型、OpenAPI、UI 代理与文档。尚未发布，不默认保留两套可写合同或 ID/名称猜测回退。
2. **认证与部署一起交付**：AUTH-01、UM-10、API-09、DEP-01/03/05/06 协调；成员重名先预检，内置管理员名称规则与唯一索引一致。DEP-02/04 可先独立处理。全新部署直接使用目标结构；保留本地体验数据时提供明确离线迁移，不为实验版本建立永久兼容层。
3. **工作空间整体交付**：WS-02/03 连同授权输入、Key 版本、空 selected、操作历史外键及执行者保护一批验证。完整删除和同名复用未通过前，不开放可复用的可读地址。
4. **UI 收敛**：WS-01 与新合同同步；使用 bank_id 调用、内部 ID 区分同名对象，保存删除 ETag 和操作意图，不自动重提过期写入。
5. **最后验证交付和生产边界**：干净部署、原生 REST/MCP、真实模型基本功能与权限隔离分别验证；HA、容量及 PG/PGroonga 恢复单独验收。API-08/DB-05 性能候选不与结构调整捆绑实施。

实施前必须写明终态操作的重试/查询保留时长、清理触发方式与 UI 意图期限；这是 WS-03 的交付条件，尚未选定具体天数。审核结论为 **ACCEPT WITH RISKS（接受统一方向，实施前补齐保留合同与验证证据）**，不代表当前代码达到商用标准。

本轮验证：**RUN** 通读本清单与当前设计，只读核对原生基线及优化工作树的路由、授权、幂等查找和表约束；**NOT RUN** 代码测试、迁移、部署与故障试验。本轮代码修改权限未授予，仅更新待优化文档；没有新增独立专家评审，历史专家结论不覆盖上述新合同。

## 2. 用户管理

### 2.1 本轮建议

保持一个实例管理员、成员归属与 Key 授权的现有模型，主要优化页面关系和操作反馈：

- 新建成员只填写名称，不增加管理员角色选项。
- 成员行展开后直接显示自己的 Key，明确成员与凭据的归属。
- 新建 Key 配置名称、工作空间范围、只读或读写；默认读写，完整明文只在签发成功时显示一次。
- 指定空间支持逐空间权限，例如 MySQL 只读、PG 读写；全部空间仍使用统一权限。优化版已实施。
- Key 列表显示脱敏标识，便于核对应用配置中的 Key。
- 统一使用“吊销 API Key”；成功后从正常列表移除，不显示已吊销历史行。
- 删除成员后从列表移除，明确其全部 Key 失效、空间数据保留。
- 成员、Key 的后台历史和审计继续保留，不为本轮 UI 简化改成物理删除；工作空间清理另按 WS-03，不把本句扩大为永久保留全部对象。

这轮建议借鉴阿里 ContextDB 的成员行展开、Key 表格和吊销反馈，保留我们跨工作空间授权的产品模型。不引入其云账号绑定、Owner、用户组等完整权限体系。

- 创建由用户提交，助手没有直接观察创建成功时的完整 Key 弹窗；不能把“明文仅展示一次”写成本次 UI 已实测结论。

- 未查看阿里服务端数据库或实现，不能从 UI 行消失判断物理删除或历史保留方式。

### 2.4 角色与授权边界

本节记录已实施版本的边界。后续按第 3.1 节在后台增加 admin/member 角色用于统一认证；普通成员 UI/API 仍不提供角色选择，不开放多个管理员。

**首版不增加成员角色选择。** 当前只有一个实例管理员，通过 UI 密码登录；UI 后台使用运维 Admin Key。成员用于记录业务 Key 归属及统一启停，没有独立的 UI 登录身份。

如果现在增加“管理员”，还需要定义管理范围、能否登录 UI、能否创建其他管理员以及与部署 Admin Key 的关系。没有明确场景时，不先加入这些分支。

| 关系 | 阿里本次页面及公开资料 | 我们的首版建议 |
| --- | --- | --- |
| 成员归属 | 在工作空间下管理成员 | 在实例下管理成员 |
| 角色 | 页面创建时可选管理员/成员，列表还存在 Owner | 普通成员目录不提供角色选择；实例管理员为部署身份 |
| 业务授权 | 还有角色、用户组和资源授权机制 | 在 Key 上配置全部/指定空间及只读/读写 |
| 多空间 | 本次未验证跨空间凭据能力 | 一把 Key 可访问一个、多个或全部空间 |
| 云账号关联 | 页面有阿里云 UID 绑定 | 首版不增加云账号绑定 |

不能把我们的模型描述为“完全等同于阿里，只多一个多空间字段”。可以借鉴交互方式，但成员归属和授权来源不同。

授权规则继续保持：

1. 成员本身不再配置一套空间权限，避免与 Key 权限重复。
2. Key 的工作空间范围为“全部”或“指定一个/多个”；全部范围包含未来创建的空间。
3. 优化前一把 Key 统一权限；优化版指定空间逐项选择只读/读写，全部空间使用统一权限。不增加“全部空间默认权限＋个别空间例外”规则。
4. 只读可以 Recall/Reflect；读写增加 Retain 和已允许的内容操作。二者都不能管理工作空间、成员或其他 Key。
5. 全空间业务 Key 仍是业务凭据，不能变成运维 Admin Key，也不能用来登录 UI。
6. 用户管理页的全部成员和 Key 仍是实例范围，不随当前内容页选中的空间改变。页内注明“管理当前实例的成员与 API Key”，避免误认为仅管理当前空间。

### 2.5 优化项明细

#### UM-01 成员入口、名称与列表（P1，已实施）

**问题：** 成员操作与 Key 区域分离，归属不够直观；“撤销/吊销”用词不一致。

**目标：** 页面名称保留“用户管理”，页内统一使用“成员”和“API Key”。成员表展示名称、状态、创建时间。成员 ID 可在详情或复制入口查看，不占用主要阅读空间；显示名称不能代替内部 ID。

每个成员行提供展开箭头和“管理 API Key”入口，两者控制同一块展开区域。编辑名称、停用/启用、删除等次要操作收进“更多”菜单，避免一行堆放多个按钮。停用成员保留在列表并标注状态，已删除成员不显示。

#### UM-02 创建成员流程（P1，已实施）

首版只填写名称，提交成功后定位并展开该成员的 Key 区域，提供“新增 API Key”按钮。创建成员不会隐式授予空间权限，也不自动生成一把全空间 Key。

阿里的“同时生成初始 Key”有使用价值，但我们还需要选择空间与读写权限。首版先复用独立的创建成员、创建 Key 流程，避免把授权字段和两个资源的失败处理挤进一个表单。后续若发现额外一步明显影响使用，再评估合并引导，不新增重复接口。

#### UM-03 成员下的 Key 表格（P1，已实施）

建议列：名称、脱敏 Key、工作空间范围、权限、创建时间、最近使用时间、操作。时间缺失显示“—”，不把“尚未记录”解释成“绝对从未使用”。空间较多时展示摘要，展开或悬浮可看完整范围；显示空间名称，同时保留 ID 映射。

正常 Key 表格无需单独列“可用/已吊销”：已吊销记录不进入该列表。所属成员停用时，在区域顶部说明“成员已停用，其全部 API Key 暂不可用”，不要把这些 Key 误标为已吊销。

加载中显示加载提示；只有请求成功且结果为空时才显示“暂无 API Key”。本次阿里页面在刚展开的瞬间曾短暂显示空列表，后续加载出数据；我们的页面应避免这种闪烁误导。

#### UM-04 Key 脱敏与明文展示（P1，已实施）

阿里示例为 `ctxdb-***5f82bf`；我们的凭据沿用当前格式，显示示例为 `ctx_live_***5f82bf`，不为了 UI 展示修改实际 Key 格式。

- 脱敏标识由固定类型前缀和实际凭据末尾 6 个字符组成，便于与应用配置核对；随机尾缀可能包含大小写字母、数字、`-` 或 `_`，不要限定为十六进制。
- 完整明文只在签发成功时展示一次，明确提示及时保存，并提供复制按钮。关闭后不能从详情、编辑或普通列表恢复。
- 列表不提供“复制完整 Key”；可以复制脱敏标识或 Key ID，但按钮文案必须说明复制的内容。
- 不把完整明文放入日志、URL、浏览器持久存储或审计记录。
- 尾缀仅用于识别，不能参与权限判断；尾缀相同不能证明是同一把 Key，操作始终按 Key ID 定位。

优化前仅有 HMAC 摘要，不能还原尾缀。优化版签发时在服务端固定校验的 `metadata.display_suffix` 保存真实末6字符，通过 `display_key` 返回掩码，不保存明文、不开放任意 metadata 写入。

既有 Key 无法补回真实尾缀时，显示“历史 Key（ID …）”或仅显示掩码，不编造尾缀，也不要求用户重新提交明文。不能仅在当前浏览器内截取明文实现，必须保证刷新和服务重启后仍能展示。

#### UM-05 Key 创建、编辑和授权（P1，已实施）

创建表单分为名称、工作空间范围、权限三组。2026-10-16 用户明确要求：**权限默认读写，避免首次使用时因未主动配置而无法写入。** 这项决定取代前面讨论中“默认只读”的建议。

优化版 UI 与创建 API 保留默认 `read_write`，逐空间新增行也默认读写。默认权限不等于默认授予全部空间：空间范围仍默认“指定”，必须选择至少一个空间。

| 字段 | 交互要求 |
| --- | --- |
| 名称 | 必填，便于区分应用或用途；例如“订单服务”“演示只读” |
| 工作空间 | 选“指定工作空间”或“全部工作空间（包含未来新创建工作空间）”；指定时必须至少选择一个可用空间 |
| 权限 | 新建默认读写，允许主动选择只读；只读可查询及 Recall/Reflect，读写可写入和修改内容，不因此获得管理权限 |

两种范围的建议交互：

| 授权方式 | 权限配置 | 未来新建空间 |
| --- | --- | --- |
| 指定工作空间 | 每行一个空间及只读/读写选项；新勾选空间默认读写，可逐行改只读 | 不自动授权 |
| 全部工作空间（包含未来新创建工作空间） | 一组统一的只读/读写选项，默认读写 | 沿用该 Key 保存的统一权限；如果主动选了只读，未来空间也只读 |

指定空间可提供“全选当前工作空间”及批量设置权限，减少重复操作。全选当前空间仍保存为指定授权，不包含未来空间。选择全部空间后隐藏逐空间编辑区，明确统一权限会作用于未来空间；需要差异化权限时切换到指定空间。

不要求用户逐项确认“读写”，但保留清晰可见的权限选择，不能把创建默认值写成无条件强制读写。切换范围不静默抹去用户已经选择的只读；如必须重置授权，应在提交前明确展示最终范围与权限。

编辑时回填已有权限，不把已有只读 Key 改成默认读写；只修改名称不能改变授权。后续若在编辑中新增一个空间，新增行默认读写，原有行保留其权限。

编辑在现有入口支持名称、空间范围、权限；修改不重新生成 Key，不要求业务更换凭据。优化前 `ApiKeyPatch` 只能完整替换授权；优化版合同见 4.3：名称独立编辑，`authorization` 一旦提交即完整替换，PATCH 不应用创建时的默认读写。逐空间方案会涉及 API 字段、PG 授权存储、REST/MCP 鉴权和现有记录处理，不是仅增加一个 UI 下拉框；实施时仍需落实迁移与存量处理。

继续复用现有版本并发校验。保存冲突时提示刷新后重试，不覆盖其他管理员刚保存的授权。弹窗需显示所属成员和脱敏 Key，以免编辑错对象。

#### UM-06 吊销 Key 后移除列表（P1，已实施）

统一文案为“吊销 API Key”。确认框显示成员、Key 名称和脱敏标识，提示：

> 吊销后，这把 API Key 将永久失效，无法恢复。使用它的应用将无法继续发起请求。

服务端成功后移除该行并更新数量；失败保留原行并显示错误。超时结果不确定时，先刷新确认，不能擅自显示成功。保留现有幂等吊销行为。

查询条件及 `total` 统计都排除 `revoked_at IS NOT NULL`，再做分页；不能只在前端过滤当前页，否则页数、总数和空页会不一致。首版不增加“已吊销”列表、恢复按钮或单 Key 暂停功能。

吊销阻断后续 REST 请求/MCP 工具调用，不承诺取消已经接受的后台任务。确认文案和手册应避免把“失效”说成强制终止全部在途任务。

#### UM-07 成员停用与删除（P1，已实施）

| 操作 | 建议语义 | 前台结果 |
| --- | --- | --- |
| 停用 | 该成员所有 Key 的新访问被拒绝，可以恢复 | 成员保留并显示“已停用” |
| 启用 | 未吊销 Key 恢复受其原授权约束的访问 | 成员恢复可用，已吊销 Key 不复活 |
| 删除 | 该成员的全部 Key 不再能访问；不提供用户恢复入口 | 成员及展开区域从正常列表移除 |

删除确认显示成员名称，可同时展示 Key 数量；提示“删除后该成员全部 API Key 将失效，无法恢复。工作空间和记忆数据保留”。若展示数量，应明确只是提示，最终删除不能只影响打开弹窗时看到的那几把 Key。

成功后更新列表、总数、展开状态；删除某页最后一项时回到有效页。失败保留原成员。成员 ID 永不复用；重新创建同名成员不能继承旧 Key。

#### UM-08 后台历史与审计（P1，保持现有原则）

| 对象 | 当前保存方式 | 本轮建议 |
| --- | --- | --- |
| 成员 | `ctxdb_meta.users.status='deleted'` | 保留，正常列表排除 |
| API Key | `ctxdb_meta.api_keys.revoked_at` 记录吊销时间 | 保留，正常列表排除 |
| 管理事件 | `ctxdb_meta.audit_events` 记录创建、变更、吊销和删除 | 保留，不记录明文 |

保留记录有助于追溯归属、时间及重复操作，不是让 Key 失效的必要条件。物理删除配合充分审计也可以实现，但本轮改成物理删除没有明显的用户收益，且无需为列表展示增加存储改动。

删除成员时，现有鉴权通过成员状态统一拒绝其 Key，不要求逐条更新每个 Key 的 `revoked_at`。排查时必须同时看成员状态和 Key 吊销状态，不能只凭 `revoked_at IS NULL` 判断凭据仍有效。历史保留与后续清理策略另行评估，本轮不承诺永久保留或新增清理任务。

#### UM-09 可用性补充（P2，待评估）

- 根据实际成员量评估名称搜索，不额外增加当前无需求的复杂筛选。
- 复制成功、保存成功、吊销失败等反馈使用一致中文。
- 展开多个成员时保持归属清晰；不同时混入不同成员的请求结果。
- 普通成员不增加角色选择或个人 UI 登录；AUTH-01 会在后台为唯一系统管理员增加受约束的 admin/member 角色。以后多人独立管理另行设计，不能把本项解释为禁止统一认证所需的后台角色。

#### UM-10 成员名称在实例内唯一（P1，待实施）

2026-10-16，用户体验发现可创建同名 User。只读核对当前 users 表及创建模型：名称有长度/非空校验，但没有名称唯一约束。虽然认证按 user_id 关联，不会仅因同名就自动串权限，但成员选择、Key 归属、停用/删除确认容易产生歧义，应在首发修正。

**目标规则：**

- 实例内 active 与 disabled 成员的名称共同保持唯一；停用不释放名称，避免两个同名对象并存后难以区分。
- 名称先 NFKC、去首尾空白并检查规范化后1～64字符，再 casefold 得到内部 name_key；大小写及全角/半角等规范化等价名称不能重复。name_key 可保留 text，不机械限制为64字符，不额外折叠内部空格或做模糊匹配。
- 新建与改名执行同一规则。PG 使用 `UNIQUE (name_key) WHERE status<>'deleted'` 类型的唯一部分索引兜底；并发请求也只能成功一个，冲突统一返回409及安全的名称提示。UI 及时提示并保留输入，不能只依赖前端先查再插。
- 删除成员后允许复用名称，但新成员使用新的 user_id，旧成员及其 Key 的失效状态不变；没有恢复旧成员的入口。成员 ID 不复用，名称不作为认证或 Key 归属依据。
- AUTH-01 的隐藏内置管理员同样参与非删除名称唯一性；其规范化名称作为系统保留名，普通 CRUD 不能占用、改写或操作系统管理员。普通成员仍无角色选择，不新增管理员管理接口。
- 保留体验数据时，迁移先报告规范化重名组，包括停用成员及内置管理员名称冲突。存在冲突则拒绝迁移，待管理员明确改名后再运行；不自动合并用户、改名、删除或移动 Key。新建表与升级路径均安装 name_key、唯一索引及 COMMENT。

**范围：** 复用 POST /users、PATCH /users/{user_id}、既有列表与删除，不增加查询或去重接口。更新模型、Repository 的规范化和冲突映射、PG 结构/迁移、UI 错误提示及 OpenAPI 说明；不要把成员唯一性机械套到所有 Key 名称。

**验收：** 同名、大小写等价、全角等价、首尾空白、并发创建/改名均按规则处理；停用后不能同名创建；删除后同名新成员不继承旧 Key；迁移冲突拒绝且原数据不变；隐藏管理员保留名不能被普通成员占用。此项尚未实施或测试。

### 3.1 AUTH-01：管理员与业务 Key 统一认证（P1，待实施）

2026-10-16，根据本轮讨论确认优化方向。**本节是待实施方案；当前代码和运行服务仍使用“配置摘要验证 Admin、PG 摘要验证业务 Key”的方式。** 本次只记录，不修改代码、配置、数据库或服务。

#### 问题与目标

当前调用方式相同，服务端却有两条认证路径：Admin Key 与 CONTEXTDB_ADMIN_KEY_SHA256 比对，业务 Key 查询 PG、使用 pepper 校验 HMAC 摘要。这简化了唯一运维身份的部署管理，但增加认证分支、配置同步和理解成本。

拆分不是因为管理员 Key 只能在启动前生成。随机凭据可在任何时候离线生成；是否生效取决于服务接受的认证记录。初始化命令可以在服务启动前直接将管理员摘要写入 PG，不依赖在线 HTTP 接口。

目标是：**所有 API Key 共用 PG 记录和摘要校验，验证有效身份后再按用户角色授权。** 保持一个实例管理员、普通用户多 Key、逐空间业务权限，以及现有 REST/MCP 调用方式。

#### 用户角色与管理边界

在 ctxdb_meta.users 增加受约束的 role，取值 admin/member，普通用户默认 member。不新增角色表或 IAM 服务，也不在 Key 上重复增加一份管理员角色。

| 对象 | 目标行为 |
| --- | --- |
| 内置系统管理员 | 初始化时离线创建唯一 admin 用户及一把管理员 Key；可管理全部空间、用户、Key，并访问全部 active 空间的数据 |
| 普通用户 | 创建 API 和 UI 只接收名称，服务端固定 role=member；不能提交 role 或自行升级权限 |
| 普通用户的 Key | 沿用 all/selected 和 read/read_write；全空间业务 Key 仍不具有管理权限 |
| 管理员展示 | 内置管理员及其 Key 不进入普通成员列表、选择器或普通 Key 管理入口；列表 total 和分页同步排除 |
| 管理员保护 | 普通用户/Key CRUD 接口即使用 Admin Key 调用，也不能编辑、停用、删除系统管理员，或创建、修改、吊销其管理员 Key；本期仍由受控离线运维处理 |

角色属于用户，因此该用户名下所有 Key 都继承相同身份。管理员名下本期只保留一把运维 Key，不签发所谓“受限管理员业务 Key”；业务应用必须使用普通用户的 Key。管理员仍受空间状态、schema 映射、准入与排空检查，不能绕过原生 Bank 生命周期限制。

#### 统一认证与接口授权

```text
Authorization: Bearer <完整 API Key>
  → 解析 Key ID
  → 查询 api_keys 及所属 users
  → 使用同一个 pepper，校验完整 Key 的 HMAC-SHA256 摘要
  → 检查 Key 未吊销、用户为 active
  → 管理接口：要求 users.role=admin
  → 业务 REST/MCP：admin 访问全部 active 空间；member 检查 Key 的逐空间权限
```

ctx_admin_ / ctx_live_ 可以保留，便于识别凭据用途和兼容已有格式；前缀不能决定管理员身份，更改前缀不能提权。认证依据为完整凭据摘要及 PG 用户角色。

管理员和业务 Key 均不在 PG 保存明文。沿用 api_keys 的归属、摘要、吊销和版本字段；管理员记录可复用 all + read_write，不另建管理员 Key 表或公开授权格式。新建 Key 明文仍只返回一次；查询、日志、审计和错误响应不得暴露明文、摘要或 pepper。

管理 API 仍为14个操作，不新增 HTTP 实例注册、角色修改、管理员创建或管理员恢复接口。管理员身份检查保持现有返回结构和 instance-admin 身份标识；真实管理员用户 ID 用于内部关联，不能因换存储而悄然改变客户端合同。当前路径 GET /admin/session 的命名拟按 API-09 调整为 GET /admin/identity；该改名与统一认证可一并实施，但不改变返回字段和授权要求。

#### 初始化与配置收敛

1. 准备专用 PG、扩展及部署配置，离线生成管理员凭据、UI 密码和 pepper。
2. 按 DEP-06 先确认凭据已安全持久保存，再由离线初始化命令在同一事务绑定部署信息、创建唯一系统管理员，并写入管理员 Key 的 HMAC 摘要；无需先启动 Hindsight。文件和 PG 不是一个事务，文件已保存而 PG 初始化失败时允许用原凭据重试，不能重新生成后覆盖。
3. 重复初始化校验已有绑定并保持凭据不变，不重建管理员、不重新生成 pepper、不复活已吊销凭据；不把初始化入口当成未认证在线恢复接口。
4. 启动 API/Worker，API 就绪后启动 UI。UI 使用既有服务端管理员 Key 调管理和数据接口。

| 配置/文件 | 目标取舍 |
| --- | --- |
| HINDSIGHT_CP_DATAPLANE_API_KEY | 保留，UI 服务端持有管理员明文；统一存储摘要不能替代请求所需的完整凭据 |
| HINDSIGHT_CP_ACCESS_KEY | 保留独立 UI 密码；普通业务 Key 仍不能登录 UI |
| CONTEXTDB_KEY_PEPPER | 保留，统一校验所有 Key；必须随受保护的部署配置备份，不存 PG |
| CONTEXTDB_ADMIN_KEY_SHA256 | 统一认证完成后移出运行时配置；只允许旧版迁移时作为旧凭据校验依据，不保留双认证回退 |
| 管理员凭据文件 | 受保护文件保管完整 secret 和 key_id；key_id 可从 secret 解析，无需另设环境变量 |
| generate-admin-key 输出 | 原 sha256 是完整 Key 的普通 SHA-256，不能当作新方案的 HMAC 摘要使用；是否保留为离线交接校验值在命令文档中明确，不再让运行时依赖它 |

API 从 PG 验证身份，UI 不增加 PG 连接，不获取 pepper 或模型密钥。数据库不可用时认证失败关闭，不用旧环境变量绕过 PG。离线运维入口需要数据库权限和受保护凭据，不能变成“任意人重置管理员”。

#### 迁移与改动范围

先停止目标 API/Worker、备份数据库和私有配置，再通过有序元数据迁移实施，不手工改版本号，也不改原生 Hindsight 业务表。本次不预先指定新的结构版本数字，由实际迁移确定。

- 现有业务用户补 role=member，保留 ID、Key 明文格式、HMAC 摘要、授权、吊销状态和审计。

#### DEP-01：交付版本与实际导入来源一致（P1）

**问题与依据：** 日志中的镜像 API 包缺少扩展依赖的 `BankListScope`，混用挂载扩展与旧 API 后导入失败。当前源码已定义该符号；`docker/standalone/Dockerfile` 也已有源码复制和安装流程，不能据此断言当前 Dockerfile 必然产生旧包。实际使用的 `hindsight-mt` 镜像构建来源尚未核实。

**目标与范围：** 补齐可追溯的 ContextDB 交付入口，API、扩展、UI 从同一交付基线构建；记录提交、是否包含未提交改动、锁文件版本、镜像 digest、Python/Node 版本。现有工作树有未提交实现，不能仅用 HEAD 判断运行代码。启动前通过目标 Python 输出实际模块路径、版本和必要扩展接口的导入结果；不混用镜像旧包与另一份源码，不在服务启动时临时安装依赖。现有 Dockerfile 可复用，优先修交付流程与检查，而非另造运行时。

**验收：** 同一产物可直接运行离线初始化及 API/UI；故意混入旧 API 时，在启动服务前明确报告导入来源和缺失接口，脚本非零退出，而不是进入难以定位的重启循环。文档注明源码模式和镜像模式各自的解释器、扩展安装/加载方式。

#### DEP-02：纠正 pg0 包名与可选依赖安装（P1）

**问题与依据：** 日志将“`import pg0` 失败”和“安装 `pg0` 失败”解释为私有包缺失，这不符合当前仓库。`hindsight-api-slim/pyproject.toml` 已声明 `embedded-db = ["pg0-embedded>=0.15.2"]`；`uv.lock` 有对应 PyPI 产物，发行包名是 `pg0-embedded`，导入名才是 `pg0`。无需再新增同名强制依赖。

**目标与范围：** 在部署文档明确两条路径：外部 PG 不要求安装 pg0；选择内嵌 PG 时，对目标 API 环境执行带 `--extra embedded-db` 的锁定同步，并检查 `import pg0`。例如仓库已有 `uv sync --frozen --extra embedded-db` 用法，具体环境路径随部署模板固定。镜像已有安装 embedded-db 的步骤，应校验交付结果；不复制其他 venv 的 site-packages，不把“双 venv 分工”变成标准方案。

**验收：** 干净环境按所选路径一次准备完成；内嵌模式同一 Python 可导入 pg0、API 和扩展，外部 PG 模式不被 pg0 检查阻塞。缺依赖时错误提示正确的 extra/发行包名。

#### DEP-03：部署配置优先级明确且可诊断（P1）

**问题与依据：** 当前 `hindsight_api/config.py::load_dotenv_for_entrypoint()` 使用 `find_dotenv(usecwd=True)` 和 `override=True`，API、Worker、原生 admin 入口会加载；库导入则不加载。该优先级有现成测试明确保护，是原生约定，不能直接改成“已设置 DB URL 就全部跳过”。ContextDB 的离线 migrate 直接读环境变量，因此还存在“初始化读部署配置，API 后读到父目录 `.env`”的错库风险。

**目标与范围：** 优先为受管部署提供显式禁用 `.env` 搜索或显式指定配置文件的入口，统一 API/Worker/相关 CLI 的行为；保留原生开发模式既有约定。若尚未增加代码开关，启动模板固定工作目录并检查该目录及祖先的实际 `.env` 搜索结果，发现未经指定的文件时拒绝继续，而不是仅假定部署目录没有 `.env` 就安全。输出加载的配置文件路径和脱敏后的数据库目标、模型/后端摘要，禁止打印 Key、pepper 或带密码的 DSN。

配置同时收敛：普通独享部署以 HINDSIGHT_API_DATABASE_URL 为唯一必填数据库地址，离线初始化默认复用；确需独立 DDL 账号时才显式设置可选 CONTEXTDB_BOOTSTRAP_DATABASE_URL，并核对是同一逻辑目标库，不能强制普通部署重复配置。AUTH-01 完成后移除运行时 CONTEXTDB_ADMIN_KEY_SHA256；pepper 与 UI 服务端管理员明文仍需独立持久保存。此处是目标配置，当前 migrate 仍要求 BOOTSTRAP_DATABASE_URL，不能直接套用尚未实现的省略规则。

**修正日志建议：** 在调用 `main()` 前再次 export 同样会被后续 `override=True` 覆盖，不是有效解决办法；`unset` 更不能防止文件重新赋值。仓库 `.gitignore` 已包含 `.env`，忽略跟踪不等于阻止运行时读取，也不应自动删除客户文件。

**验收：** 在 cwd、父目录、仓库根分别放置冲突 `.env`，实际启动 API/Worker 而非只导入配置模块，确认受管模式始终使用指定配置或明确拒绝；migrate 与 API 指向同一目标库，日志能定位配置来源且无凭据泄露。原生默认模式及库导入无副作用的回归保持。

#### DEP-04：稳定 UI 构建入口与模块格式（P1，修复方案待复现后确定）

**问题与依据：** 日志报告 Node 24 下加载 `next.config.compiled.js` 时出现 `exports is not defined`，转写 `.mjs` 后成功。当前仍使用 `next.config.ts`，锁文件中的 Next 为16.3.7；但没有原容器的最小复现，不能将“package.json 缺 type=module”或“Next/Turbopack 缺陷”直接认定为根因。

**目标与范围：** 以锁文件、明确的 Node/npm/Next 版本及干净安装复现，排查配置编译方式、缓存和包作用域。若需要改为 `next.config.mjs`，提交维护一份正式配置并正确处理 `__dirname` 等 ESM 差异；保留 next-intl、basePath、上传限制、distDir、standalone 等既有行为。不要在部署时用简单去类型脚本生成另一份配置，也不直接给全包增加 type=module 而忽略其余脚本。

**验收：** 在文档支持的 Node 22.12+ 和24环境中，使用锁定依赖完成 SDK/UI 构建及 standalone 登录/静态资源验证，无需临时修改源码。未复现时先交付准确环境矩阵和复现脚本，不宣称构建缺陷已修复。

#### DEP-05：API 就绪顺序和 UI 启动错误分类（P1）

**问题与依据：** 当前 UI `src/instrumentation.ts::register()` 启动时仅校验一次后台 Admin；失败统一抛出“UI password and an active admin/all server key”错误。`verifyContextDBAdmin()` 对部分上游故障也返回类似 Key 错误，难以区分未就绪与凭据无效。日志中的先后启动竞态符合这条路径，但未在当前环境重现。原生 `docker/standalone/start-all.sh` 已有等待 API 健康的逻辑，应复用并核对 ContextDB 自定义启动路径是否绕开了它。

**目标与范围：** 固化“离线 migrate → API/Worker → `/health/ready` 成功 → UI”的模板。等待有总超时，超时非零退出并指向对应阶段日志；不能等待耗尽后仍启动 UI。UI 先做本地配置检查，再对超时、连接失败、上游503等暂时不可用错误做有限重试；缺配置、401/403或身份响应不符立即明确失败。启动重试不改变正常请求中每次校验 Admin 的规则，不缓存授权，也不在依赖失败时放行。

**验收：** API 延迟启动后 UI 可在期限内正常就绪；API 永不就绪则明确失败；错误 Admin Key 不被当成“还在启动”反复等待；API 启动失败、UI 失败各自可从日志定位。同步修正文案中的 admin/all，避免暗示全空间业务 Key 可以管理 UI。

#### DEP-06：凭据首次保存、持久化与重复部署（P1）

**问题与依据：** 日志 P8/P9 使用旧实验版 POST /instances、恢复 Admin Key 和 CK；当前没有这些入口或 CK。可复用的实际问题是：一次性 secret 输出前未确认目录可写，以及配置写入容器可写层导致重建丢失。当前 `generate-admin-key` 只向标准输出打印凭据，原部署手册已有 noclobber 保存和私密目录要求，需把这些要求落实为可靠的部署步骤。

**目标与范围：** 首次生成前，以实际运行 UID/GID 检查持久目录可写；使用受保护临时文件、完整 JSON 校验及原子且不覆盖已有文件的保存方式，确认落盘成功后再生成关联配置或初始化数据库。统一持久保存 Admin secret、UI 密码、pepper、API/UI 配置；内嵌 PG 的数据目录也挂载持久卷。目录建议0700、秘密文件0600，正确处理属主，不使用 chmod 777。区分首次部署与启动已有部署：后者缺少既有秘密时拒绝启动，不能静默生成新值；识别实际受支持的秘密来源，不强制一定存在 pepper.txt。

**验收：** 目录不可写、文件已存在、磁盘写失败时不覆盖旧凭据、不继续启动，也不把 secret 打到普通日志；正常重启和重建容器后原业务 Key、UI 配置及数据保持。缺 pepper 时失败关闭；Admin secret 丢失按当前版本的受控离线轮换流程处理，不指向旧 HTTP 恢复接口。本项可独立实施，未来 AUTH-01 改变摘要存储时同步调整配置生成逻辑。

#### DEP-07：UI 字体随交付产物提供（P2）

**问题与依据：** `src/app/[locale]/layout.tsx` 当前通过 `next/font/google` 使用 Inter、JetBrains Mono，构建依赖外部字体抓取。日志中的代理故障不在本轮处理范围，但这个额外构建依赖可直接从产品交付中消除。

**目标与范围：** 使用许可允许再分发的本地字体资源和 `next/font/local`，或者明确采用系统字体；字体文件、许可证、字重、CSS 变量及 fallback 一起维护。构建直接使用固定资源，不临时下载，也不靠修改源码为空字体对象或依赖偶然缓存。

**验收：** npm 依赖和其他构建依赖预先准备完成后，禁止访问 Google Fonts 仍可完成 UI 构建；登录页、导航、代码字体及所需语言 fallback 正常。该项不承诺整个依赖安装过程无需网络。

#### DEP-08：部署预检与验收能力分层（P2）

**问题与依据：** 日志还暴露了平台二进制缺失、工具链准备不全，以及 native 后端暂代中文全文验收的问题。P6 的安装失败由网络引起，本节不认定 npm/锁文件有缺陷；P10 的 apt 不可达不纳入修复。原部署手册已列出工具版本和英文/中文后端区别，应补充可执行检查与结果记录，而不是重复罗列安装建议。

**目标与范围：** 部署前检查选定安装模式需要的 Python/Node/npm/uv、操作系统/架构、SDK 构建所需 esbuild 可执行文件，以及目标 PG 版本、UTF8、可用/已启用扩展。按目标平台完成 optional dependencies 安装，不给所有平台硬加 `@esbuild/linux-x64`。明确外部 PG/pg0 的边界，编译依赖仅在选择源码编译插件时要求，不把 cargo 等一律视为运行前提。

**验收：** 缺失项在初始化前一次列出且不泄露凭据；选择 native 可完成英文基本功能验证，但报告明确“中文分词/全文能力未验收”。选择 PGroonga 或 jieba 方案时，缺对应扩展/分词能力应阻止该目标的验收，不静默改成 native 后仍宣称中文检索完整通过。预检成功与真实 MaaS Retain/Recall/Reflect 成功分开记录。

## 4. API 设计

### 4.1 结论与范围

2026-10-16，REST/Web、UI、Agent 三位专家对当前实现和本清单第 2、6 节分别检视，主控复核后收敛为以下建议。**以下目标已在独立优化工作树实施；新版 curl/OpenAPI 已同步，旧体验服务和原手册仍保留原合同。**

保留现有 14 个管理操作，不再合并资源或增加实例注册、管理 MCP、可配置角色体系。AUTH-01 所需后台 admin/member 不属于新增角色管理产品。首期主要改四件事：Key 授权只保留一个来源；编辑和列表符合用户管理体验；工作空间失败可见、刷新可恢复；普通业务读取不能带出运维凭据。

其中 **API-01 是本次已修复的首发安全风险**：新增合成原生任务的 SDK/MCP 集成回归，验证业务查询不暴露载荷、回显及错误中的凭据，管理员诊断保留；没有使用真实凭据或外部 Webhook 投递。第 4 节保留问题分析与验收要求，最终执行状态见第 8 节。

优化前代码基线为 `contextdb/service-management-v2-simple-20261016`，HEAD `d5e851b60315b79696e995874e7edc1e9a7bae23` **加已有未提交实现**，不能只用提交号复现。详见 [审查记录与基线](evidence/api-design-review-2026-10-16/review-summary.md)。

### 4.2 每个管理接口是否需要

统一前缀 `/ext/contextdb/v1`，全部只接受运维 Admin Key。**本表记录上一轮已实施合同；工作空间下一轮按 WS-02 改用 bank_id，成员、Key、操作仍用服务端 ID。** 请求不传实例 ID、云租户 ID、schema、操作者或元数据版本。AUTH-01 改认证来源，不改变这些权限边界。

| # | 方法与路径 | 首期用途与取舍 |
| --- | --- | --- |
| 1 | GET `/admin/session` | 保留身份检查能力；当前路径拟按 API-09 改为 `/admin/identity`；不扩为会话管理或实例管理 API |
| 2 | POST `/workspaces` | 保留；下一轮按 WS-02 增加 bank_id；保留幂等 Header、202 和操作 ID |

| 6 | GET `/operations/{id}` | 保留，查询空间创建/删除进度；不与原生业务异步任务混为一个接口 |

### 4.3 API-02：一个明确的授权对象（P1，工作量较大）

**优化前问题：** `access_mode + workspace_ids + permission` 只能表示统一权限。直接再加逐空间字段会形成多份授权来源；旧 PATCH 还不能只改 Key 名称。

**建议合同：** 用 `authorization` 替换现有三个公开授权字段，内部存储按第 6 节保持受约束的字段/关系，不把权限变成任意 JSONB。保留原 URL 和 HTTP 方法，不新增授权接口。

**版本说明：本节 JSON 与32位 workspace_id 规则是已实施基线。下一轮统一以 WS-02 的 bank_id 输入为准，PG 仍绑定内部 workspace_id；不要同时实现两份公开授权输入。** 默认值、完整替换、逐空间权限保持。清理后的空 selected、Key 版本联动及读取模型例外也统一按 WS-02/03 处理。

创建指定空间 Key：

```json
{
  "name": "订单应用",
  "authorization": {
    "mode": "selected",
    "workspaces": [
      {"workspace_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa", "permission": "read"},
      {"workspace_id": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb", "permission": "read_write"}
    ]
  }
}
```

全部空间 Key：

```json
{
  "name": "实例应用",
  "authorization": {"mode": "all", "permission": "read_write"}
}
```

仅修改名称，原授权和 Key 明文均不改变：

```json
{"name": "订单应用生产环境"}
```

修改授权时，提交完整目标对象，未列出的旧空间授权被移除：

```json
{
  "authorization": {
    "mode": "selected",
    "workspaces": [
      {"workspace_id": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb", "permission": "read"}
    ]
  }
}
```

合同规则：

- POST 必须有 authorization 和明确 mode。新建权限省略时默认 `read_write`；UI 默认选择“指定”，至少选择一个空间，不隐式授权全部空间。
- PATCH 至少有 name 或 authorization；省略授权表示不修改。提供 authorization 时完整替换，每项 permission 必须明确，**不能套用 POST 默认值补读写**。拒绝空对象、null、未知字段及新旧授权字段混传。
- selected 至少 1 个、最多 1000 个空间，不重复，ID 为 32 位小写十六进制；不接受同级统一 permission。all 只保存统一 permission，不接受 workspaces 或个别空间例外。
- 只改名称不执行授权替换，也不因旧授权空间已删除而失败。编辑授权时明确展示失效项，允许用户移除；新增授权只接受 active 空间。
- 创建默认读写，编辑回填原值；新增空间行默认读写，原有只读行保持。all 包含未来空间；selected 的“全选当前空间”不包含未来空间。
- name 与授权修改在同一事务检查版本、写入并审计。保留 If-Match；412 后刷新并重新确认，不能自动换新版本覆盖。

该 PATCH 使用明确的 `application/json` 应用合同，不宣称实现通用 JSON Merge Patch，也不引入逐项 JSON Patch 指令。原子修改和条件更新符合 [RFC 5789 §2](https://www.rfc-editor.org/rfc/rfc5789.html#section-2) 的方向；完整授权替换是本方案自己的简化规则。

**影响：** 模型、PG 授权存储及迁移、UI 类型/白名单、REST/MCP 实际鉴权一起调整，是本轮最大改动。必须按实际目标空间生成有效权限；不能把某空间读写提升成整把 Key 读写。多空间 MCP 工具列表可展示能力并集，但每次调用仍按目标空间授权，单空间 MCP 按该空间过滤。已接受的 Worker 任务继续按既有内部执行上下文工作，不重新拿已吊销 Key 登录。

**验收：** 同一 Key 对 A Recall/Reflect 成功、Retain 拒绝，对 B Retain 成功；REST/MCP 一致；只改名不增权；PATCH 缺权限拒绝；并发旧版本拒绝；selected 旧空间删除后，同名新空间获得新 ID，不继承旧授权。

### 4.4 API-03：Key 元数据、正常列表与选择器（P1，工作量中）

**问题：** 列表缺少脱敏标识，仍含已吊销 Key；`status=active` 容易被当成鉴权结果；空间分页没加载完时也可能被误认为授权失效。

**建议：**

- 签发时保存实际末尾 6 字符，列表返回 `display_key`，例如 `ctx_live_***5f82bf`。旧记录无尾缀时明确显示“历史 Key”，不能从摘要伪造或恢复明文。
- Key 正常读对象收敛为 `key_id、user_id、name、display_key、authorization、version、created_at、last_used_at`；创建响应额外有 secret。正常列表先 SQL 过滤吊销记录，再 count 和分页，可去掉恒定的 active/null 状态字段；内部 revoked_at 和审计保留。
- 成员停用在所属区域提示，未吊销 Key 仍可管理；不再增加 effective_status、吊销历史列表或明文查询接口。
- 列表继续 q/limit/offset；空间选择只允许 active。后页未加载不等于空间已删除，不能静默丢授权；复用单空间 GET 解析已选但未加载的对象，并限制并发。按 WS-02 切换 bank_id 后仍核对只读内部身份，不把同名新空间视为原授权；失效项显示不可用，不自动选中替代对象。
- 吊销、删除最后一项后修正当前页与 total；只刷新变更成员的 Key 区域，不遍历加载全体成员的全部 Key。

**验收：** 明文只在签发响应出现；重启后脱敏标识稳定；吊销过滤与分页一致；停用不等于吊销；超过 50 个空间时编辑不会丢失后页授权。复用 UM-03～UM-07、DB-04，不新增重复接口。

### 4.5 API-04：空间操作失败可见、刷新可恢复（P1，工作量中）

**优化前事实：** UI 主空间列表调用原生 Bank 列表，只显示 active 空间；管理 GET /workspaces 能显示中间/失败状态，但未作为该目录来源。UI 在函数内部每秒查操作，120 秒后抛错，刷新会丢失进度和请求意图。

**建议：** 管理目录使用现有 GET /workspaces；内容页切换仍限 active。工作空间读响应增加一个只读 `latest_operation_id`（没有时为 null），从已有任务记录关联取得，不要求复制成第二份任务状态或新加数据库列。刷新后用已有 GET /operations/{id} 恢复查询。

后续 UI 简化按 WS-01 处理：保留上述查询与恢复能力，不要求在每个空间上常驻“查询进度”按钮。

提交前保存本次非敏感操作意图：幂等 Key、原始请求体、原 bank_id、内部身份/operation_id、删除原 ETag 及意图时间，可放当前页 sessionStorage。**不保存 Admin Key、业务 Key 明文或密码。** 新增内容按 WS-02/03 实施；不能在同名重建后用新 ETag 替换旧删除意图。

- 创建/删除 202 仍为受理，未完成不能显示成功或用于新增授权；建议附相对 Location 指向操作查询，UI 代理转发经校验的路径。
- 轮询按 1、2、4 秒退避，最多 5 秒；页面关闭停止本地轮询，超时不取消服务端任务。202 与状态监视的依据见 [RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)；Location 是本方案建议，并非该规范强制所有 202 提供。
- 刷新页面只恢复 GET 查询。初始响应丢失、尚无 operation_id 时显示“结果未知”；只有管理员明确点击“继续确认/重试”后，才按原幂等 Key 和相同原始请求重放 POST/DELETE，并提示这可能重新执行已 failed 的操作。取得 operation_id 后继续 GET，不自动重放写请求。
- latest_operation_id 只能恢复查询，不能重建原始创建请求。当前请求 hash 在名称归一化前计算，不能按响应名称猜测原请求。丢失本地意图时显示服务端失败空间，可删除失败空间后重新创建，不自动按名称重试。
- 不新增操作列表、重试/取消/强制删除接口。排空和未知执行者屏障保留；墓碑、操作外键及历史清理按 WS-03 调整。定义保留窗口前不清理幂等记录；超期恢复意图只核对状态，不重放旧写请求。

**验收：** 首次响应丢失、刷新、服务重启、120 秒等待结束后仍能定位状态，不重复创建；失败创建/删除可见；明确重试仍受原生命周期版本保护，旧操作不能复活已删除空间。

### 4.6 API-05：UI、API、OpenAPI 使用同一输入与错误合同（P1，工作量中）

优化前已核对的差异：API 接受空间 description，UI 代理只放行 name；API 幂等 Header 只校验长度，UI 限 ASCII 字符；API 版本 Header 允许 0/前导零，UI 要求正整数；API 错误是 code/message/request_id，UI 自己产生的错误只有 error 字符串。

收敛规则：

| 项目 | 首期目标 |
| --- | --- |
| 名称 | name 保持 1～64 字符，trim 后非空；空间 NFKC 后再次检查最终长度，name_key 扩长按 DB-02 处理 |
| 空间 description | 保留可选、最长 512；UI 可不提供输入框，但代理不另造不一致合同 |
| 幂等 Header | 两端统一 `[A-Za-z0-9_-]{1,128}`，不接受空白等非预期输入 |
| If-Match | 已实施成员/Key PATCH 为带双引号正整数；WS-02 空间 DELETE 使用包含内部身份的 ETag。按资源声明并同步代理校验，不把数字正则套到全部资源，不使用通配符覆盖 |
| 路径 ID | 成员、Key、操作保留32位小写十六进制；工作空间按 WS-02 用注册 bank_id。新建规则与已有空间读取规则分开，不再泛称全部资源都必须32位 |
| 错误 | 管理 API 与 UI 代理统一最低 code/message/request_id；前端保留 status/code/request_id 并映射中文提示 |
| 参数提示 | 可增加安全的字段位置和原因白名单，不返回原始 Pydantic input、SQL 或完整请求 |
| 响应字段 | 成员去掉 instance_id；部署绑定只在 admin/session；不开放 schema、lease、actor、摘要及任意 metadata 写入 |

保留现有 400/401/403/404/409/412/503。限流或请求体上限由入口执行时使用 429/413，不为格式统一重写原生 REST/MCP 错误协议。新建默认值、编辑必填条件、互斥授权用 OpenAPI 的独立输入模型表达；UI 白名单必须同步。

**验收：** 同一个合法请求经 UI 代理与直连 curl 均可用；空白名称、未知字段、非法 Header 在两端一致拒绝；错误有可追踪 ID且不含凭据；412 不自动覆盖、503 不显示成功。

### 4.7 API-06：重试、并发和吊销边界（P1，工作量小至中）

| 请求 | 首期规则 |
| --- | --- |
| GET 查询 | 可以重试；空间操作轮询采用退避 |
| 工作空间创建/删除 | 同意图用原幂等 Key/请求，删除还保留原 ETag；按 WS-02 先找原历史。failed 明确重试只针对原对象，过期意图按 WS-03 不重放 |
| PATCH 成员/Key | 带 If-Match；响应丢失先刷新对照，412 不换最新版本自动重放旧编辑 |
| 创建成员/Key | 当前无幂等，不自动重试；提交期间禁用双击，超时显示“结果未知” |
| 吊销 Key/删除成员 | 按同一个资源 ID 重试；保留当前重复调用边界，不加确认 Token 或恢复接口 |
| 原生异步 Retain | 复用原生 operation_id 支持，不再封装 ContextDB Retain 接口；属于另一份业务合同 |

Key 创建返回丢失后刷新列表，管理员核对具体对象，再明确吊销不能确认已妥善保存的 Key，必要时重新签发。名称、最近一行和模糊搜索都不是请求唯一标识；有歧义时不自动吊销其他 Key。首期接受手工确认成本，不为透明重放保存密钥明文，不新增一套通用幂等存储平台；后续自动化确有需求再设计请求去重与“明文不可恢复”的结果语义。

吊销仅阻断后续鉴权/授权，不强制取消已受理的 REST、流式调用和队列任务；成员恢复不复活已吊销 Key。Key 的管理 version 不随 last_used_at 每次变化，避免使用中的 Key 无法编辑。

**验收：** 模拟成功提交后断开响应，不自动签第二把 Key；两名编辑者旧版本只允许一方成功；同一 MCP 会话吊销后的下一次工具调用被拒；已受理原生任务按既有语义完成。

### 4.8 API-01：业务诊断读取不能带出运维凭据（P1，已修复）

**修复前调用链（已以合成任务作隔离回归）：** 业务 Key 可请求原生 `GET /v1/default/banks/{bank_id}/operations/{operation_id}?include_payload=true`。空间有 Webhook 投递任务时，原始载荷包含签名 secret 和 http_config（可含 Authorization 等请求头）。旧扩展只把 Webhook 列表/投递列表设为管理员，任务详情仍走普通读权限；任务列表又可发现这些 ID，因而形成敏感载荷读取链。

以下扩展路径位于 `hindsight-extensions/contextdb-service/`，原生路径位于 `hindsight-api-slim/`：

- `hindsight_ext_contextdb/validator.py:151`：额外管理员检查仅覆盖两类 Webhook 列表。
- `hindsight_api/api/http.py:8234`：include_payload 布尔参数传到引擎。
- `hindsight_api/engine/memory_engine.py:21159`：GET_OPERATION_STATUS 读门禁后可选取 task_payload；响应模型及返回对象保留该字段。
- `hindsight_api/webhooks/manager.py:129`、`:211`：两条投递入队路径保存 secret/http_config。任务列表默认不排除此任务类型。

**最小改动：** 优先在扩展的可信传输门禁拒绝业务 Key 请求原始任务载荷，管理员诊断保留；普通任务状态、异步 Retain 查询和原生 URL 不改。业务请求重复 include_payload 参数一律 400；单值按原生布尔规则正常解码和解析，覆盖 true/1/on/yes、大小写和百分号编码，真值 403、合法假值允许普通状态查询、非法值拒绝，不能只匹配字符串 `true`。禁止通过另一入口绕过同一策略。

原生 MCP get_operation 当前不暴露 include_payload，使用默认 false；本次确认的直接风险入口是 REST，不能据此宣称 MCP 已发生同类泄露。

同时核对任务列表/详情的 error、result_metadata，以及 trace/audit/config 等诊断读响应；这些入口目前仅列为检查范围，**未确认都存在凭据泄露**。若外围无法覆盖必要参数语义，再评估最小的原生 hook，不能为少改代码留下授权缺口。

**验收：** 隔离环境使用合成 Webhook 签名密钥和 Authorization 哨兵值；只读、读写 Key 都不能取原始载荷，管理员可诊断；业务响应、错误、日志不出现哨兵值；普通业务任务状态查询继续可用。不得拿真实凭据做探测。

### 4.9 API-07：保留现有安全入口，补齐部署验收（P1）

已具备：UI 密码会话、同源写检查、固定服务端 Admin Key、代理路径/字段白名单，管理 API 先鉴权再校验请求体。不能写成“当前没有 CSRF 防护”或“浏览器持有 Admin Key”。同源检查依据及代理边界可参照 [OWASP CSRF 防护说明](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#verifying-the-origin-with-standard-headers)。

入口负责 HTTPS、超时、请求体上限和登录/管理请求限流；API 负责身份、成员状态、Key 吊销、目标空间权限与 schema 状态；UI 负责会话和同源保护。管理 JSON 可采用独立小上限（例如 256 KiB，须覆盖最大 1000 项授权实测），不把该上限套到原生 Retain 文本。公网路径和直连路径必须明确同等责任，不新增第二套登录/认证平台。

**验收：** 实际跨站 UI 写入拒绝、错误服务端 Key 拒绝、业务 all Key 管理请求拒绝；浏览器不获得 Admin Key；真实网络入口的 HTTPS、超大请求与突发限流有证据。本轮没有完成这些生产环境验证。

### 4.10 API-08：效率与协议细节按证据优化（P2）

- 同一个管理 UI 请求目前可能由 middleware、管理代理分别查 admin/session，真实 API 再鉴权。明确每条入口责任后减少重复远程检查，保留会话、同源校验和上游认证；原生 UI 数据路径不能漏检，不引入跨请求授权缓存。

- last_used_at 条件更新、全局管理锁及索引取舍按 DB-04/05，未经测量不宣称吞吐收益。
- 当前 ETag 取管理 version，但 last_used_at 可独立变化；这与“完整响应的标准强表示校验器”有差别。后续澄清可编辑快照与使用统计的表示边界，不把它表述为已发生编辑丢更新，也不简单改成弱 ETag 后继续用于 If-Match。参考 [RFC 9110 §8.8.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.1)。

### 4.12 API-09：管理员身份检查接口命名与调用说明（P2，待实施）

2026-10-16，根据接口用途及实际调用位置补充。**本次只记录建议，当前代码及运行服务仍使用 GET /ext/contextdb/v1/admin/session。**

**问题：** session 容易被理解为“登录、建立会话、获得后续调用凭据”。当前接口实际只验证请求携带的 Admin Key，并返回管理员身份和部署绑定，不创建会话、不签发 Token，也不是业务调用的前置步骤。

**目标命名：** 保留能力，将路径调整为 `GET /ext/contextdb/v1/admin/identity`。`/ext` 是 Hindsight 原生扩展挂载前缀，`/contextdb` 是扩展命名空间，`/v1` 是公开 API 版本；这些保持不变。本项不调整 workspaces、users、keys、operations；工作空间路径参数与合同由 WS-02 单独统一，管理操作总数仍为14。

| 调用方/时机 | 实际用途与边界 |
| --- | --- |
| UI 服务端启动 | 检查 HINDSIGHT_CP_DATAPLANE_API_KEY 是否为有效管理员凭据，配置错误时不继续正常提供 UI |
| UI 登录处理 | UI 密码校验通过后，检查后台管理员 Key；浏览器不获取该 Key |
| 登录后的 UI 请求 | middleware 及管理代理通过 verifyContextDBAdmin() 检查后台身份；入口责任和重复检查优化沿用 API-08，不因改名新增一次检查 |
| 运维与部署验证 | 可携带 Admin Key 直接调用，确认后台凭据及部署绑定；不限制为只有 UI 能访问 |
| 业务应用/Agent | 不需要调用，直接携带业务 Key 访问原生 REST/MCP；调用身份检查接口应被拒绝 |

UI 自身的登录仍为 `/api/auth/login`，使用 UI 密码创建浏览器会话；后台 `/admin/identity` 验证的是配置中的服务管理员 Key，两者不能在文档中混称“登录接口”。身份检查成功也不能替代每次业务或管理请求的实际授权。

**改动范围：**

- ContextDB HTTP 路由及响应模型命名；保留 user_id、role、instance_id、cloud_tenant_id 返回字段，不增加凭据或内部表字段。
- UI 的 `contextdb.ts` 中唯一远程调用路径；启动钩子、登录处理、中间件、管理代理继续复用 verifyContextDBAdmin()，不各写一套逻辑。
- 路由、鉴权及 UI 单测、REST/MCP 相关集成用例中的路径引用；生成 OpenAPI，并同步设计、部署、curl 文档和运维脚本。
- 首发前可协调 API/UI 一起切换，不默认长期保留两套同义路由；实施前核对实际外部依赖。如已有发布合同或无法同时切换的调用方，需明确过渡方案，不能只改后端导致 UI 启动或登录失败。

**与其他优化的关系：** AUTH-01 决定身份如何从 PG 认证，本项决定接口名称与职责表达；即使认证统一，仍要求管理员身份。无需新增 PG 表、会话表、管理 MCP 或新的登录凭据，不修改 Hindsight 原生业务接口。

**验收：** 新路径有效 Admin Key 返回200且字段不变，缺失/无效 Key 返回401，有效业务 Key（含 all + read_write）返回403；UI 启动、登录、页面与管理代理均可用；服务启动和用户请求不再引用旧路径，历史归档可保留旧名称并注明适用版本；curl 与 OpenAPI 一致。以上尚未执行，不计入第 8 节已有验收结果。

## 5. 工作空间与其他体验

### 5.1 WS-01：移除常驻“查询进度”，自动展示操作状态（P2，待实施）

2026-10-16，来自当前工作空间页面体验。**本项只记录优化，当前 UI 和服务未修改。**

**问题：** 当前只要工作空间带 latest_operation_id，就显示“查询进度”。成功创建的正常空间同样保留操作 ID，因此按钮长期存在，点击通常只是确认已完成；用户需要手动查询，也容易不清楚查询的是哪个操作。

**目标：** 移除工作空间行中常驻的“查询进度”按钮，将处理状态直接展示在列表中；操作进行时由页面自动更新。查询进度的能力继续保留，用户不用把后台任务当成独立资源来管理。

| 场景 | 目标展示与行为 |
| --- | --- |
| 正常 active 空间 | 显示“正常”，保留进入、删除；不显示最近一次已成功操作的查询按钮 |
| 创建中 | 显示“创建中”及行内加载状态，自动查询已有操作；确认成功后更新为正常并允许进入 |
| 删除中及删除准备阶段 | 显示“删除中”，自动查询；成功后从正常目录移除，不因202响应就立即判断清理完成 |
| 明确操作失败 | 显示“创建失败”或“删除失败”和安全的原因；仅提供实际支持的查看原因、删除失败空间或明确重试入口，不暴露原始 SQL/堆栈 |
| 网络异常、等待超时或结果未知 | 说明“暂时无法确认，操作可能仍在进行”，提供“刷新状态”；查询失败不能写成操作失败 |

处理中使用行内状态反馈，避免要求用户反复点击才能知道是否完成，可参考 [Carbon 行内加载反馈](https://www.carbondesignsystem.com/building-blocks/core/components/inline-loading/guidelines)。当前后台只提供操作状态，没有真实完成比例，UI 不显示虚构百分比。

**保留的安全语义：**

- GET /operations/{id}、latest_operation_id、异步管理记录、删除排空与幂等机制保持。202仍只表示受理；隐藏按钮不等于删除后台查询接口或任务记录。
- 页面刷新后，已有操作 ID 只恢复 GET 查询；“刷新状态”也只查询。未确认结果前不自动重发 POST/DELETE，不根据名称猜测原始请求，不换幂等 Key 重复提交。
- 没有操作 ID 的未知结果保留非敏感意图及明确提示；如需重试，由管理员确认后复用原幂等标识和原请求。失败操作也不因页面刷新自动重新执行。
- 已完成操作停止轮询，正常空间不因仍有 latest_operation_id 而持续查询。轮询有间隔和等待上限，页面卸载时结束等待；结束浏览器等待不会取消服务端已受理操作。

**改动范围：** 主要调整 ContextDBWorkspacesView 和现有状态恢复、轮询逻辑及文案，复用已有管理 API。默认界面围绕空间名称、状态和失败原因组织；操作 ID、幂等标识仅在必要诊断详情中展示，不另建任务中心。本项不新增 API、PG 表或新的调度服务。

**验收：** 正常空间不再显示“查询进度”；创建/删除状态自动更新并在终态停止轮询；页面刷新后能继续查询已知操作；网络错误和后台失败明确区分；未知结果与失败不会自动重提请求；删除过程中不能提前进入或赋权，成功后目录及内容选择器一致刷新。只读恢复、幂等和排空原有回归保持，不把简化 UI 变成简化安全流程。以上为待执行验收，不计入第 8 节已有测试结果。

### 5.2 WS-02：管理与业务统一使用可读 Bank ID（P1，待实施）

**范围修订：以下整体方案仍为候选。最新讨论仅确认 WS-04 的 GET 详情按唯一工作空间名称查询；该 GET 的入参以 workspace_name 为准，不再以本节 bank_id 约定为准。不能因为查询按名称就自动修改原生业务 Bank ID、DELETE、schema 或授权结构。**

2026-10-16，根据原生 Hindsight 和本轮整体走读修订。**本节取代此前“业务用可读 bank_id，管理仍按 UUID 寻址”的建议。当前代码、数据库和部署未变更；现有服务仍使用 workspace_id=bank_id 的32位随机 ID 和 ctxdb_ws_<workspace_id>。**

#### 设计依据与标识关系

原生 Hindsight 的创建、删除、Retain/Recall/Reflect 均按 bank_id 寻址，bank_id 可以是可读字符串，展示名称 name 独立存在。我们的一工作空间一 Bank 模型可以直接复用此能力，不应因第一版代码已使用 UUID 就要求用户理解两套工作空间地址。参考第1.1节原生源码；schema 隔离、权限和生命周期由扩展处理，不能声称原生已经实现本节全部保护。

| 对象 | 新空间示例 | 作用与约束 |
| --- | --- | --- |
| bank_id | jiamu | 对外工作空间标识，同时是原生 Bank ID；管理与业务统一使用，创建后不可修改 |
| name | jiamu 或嘉木知识库 | 展示名称，与调用标识分开；名称变化不应改变调用地址，本轮不新增改名接口 |
| workspace_id | 2a09e7eab17242daca6e67ac276dd2b6 | 内部不可复用身份；权限关联、操作、准入和执行归属使用它，不作为客户工作空间寻址输入 |
| schema_name | ctxdb_ws_jiamu | 由服务端生成并登记；旧空间完全清理后才可复用，不开放任意 schema 输入 |

不增加 slug、别名表、UUID/名称猜测回退或入口路径改写。直接通过原生初始化流程创建 bank_id=jiamu，原生引擎处理的请求目标和响应 Bank ID 都是 jiamu；不是手工 INSERT/UPDATE banks 表。

#### 对外合同

以下均为目标合同，**当前8890尚不支持这些可读路径及新授权字段**：

```text
GET    /ext/contextdb/v1/workspaces/jiamu
DELETE /ext/contextdb/v1/workspaces/jiamu
POST   /v1/default/banks/jiamu/memories
POST   /v1/default/banks/jiamu/memories/recall
POST   /v1/default/banks/jiamu/reflect
MCP    /mcp/jiamu/，或多空间工具参数 bank_id=jiamu
```

- POST /workspaces 接收 name、可选 description 和 bank_id。name 本身符合标识规则时可默认作为 bank_id；中文、空格等名称需另给合法标识，不暗中音译、截断或替换。UI 提交前展示最终标识。创建仍返回202与 operation_id。
- 管理详情、删除路径统一为 /workspaces/{bank_id}；不另增按名称查询接口，也不保留一套按 UUID 的平行详情/删除接口。列表 q 仍是名称包含搜索，不将其当精确身份解析。
- 空间列表/详情返回 bank_id、name、state、version、latest_operation_id 等；workspace_id 可保留为只读内部定位字段，UI 用它区分同名重建的不同对象。操作响应保留 operation_id、原 workspace_id，并带 bank_id 快照；轮询只需要 operation_id。
- 原生业务 REST/SDK/MCP 协议保持，bank_id 只是从 UUID 变为可读值。业务请求按注册 bank_id 查到内部 workspace_id/schema_name，再核验 Key 授权、状态和准入；原生引擎仍使用 bank_id，不改写成 UUID。
- 新建 bank_id 建议匹配 `^[a-z][a-z0-9_]{0,53}$`，长度1～54。PG 默认标识符最多63字节，ctxdb_ws_ 占9字节；超长值提前拒绝，不能依赖 PG 截断。[PG 标识符规则](https://www.postgresql.org/docs/18/sql-syntax-lexical.html#SQL-SYNTAX-IDENTIFIERS) 此限制来自可读 schema 约定，不是原生 Hindsight 的 Bank ID 限制。
- bank_id 与 schema_name 分别有数据库唯一约束；包括 creating、deleting、失败待恢复的空间都继续占用。名称 name_key 的唯一规则与此生命周期协调，不能提前标记 deleted 释放名称。旧 deleted 墓碑需预检、清理，不能仅改索引就声称已满足新规则。
- 创建前校验目标 schema 归属；同名但未注册或归属未知的 schema 不接管。实际 SQL 继续安全引用标识符，不把 URL 直接拼成 SQL。

#### 删除：地址可读，操作仍绑定原对象

仅等待旧 schema 清理完成不能防止迟到的旧删除请求。目标合同增加一个必要条件：**DELETE 必须带详情 GET 返回的 If-Match，ETag 同时绑定内部 workspace_id 和当前资源版本。** 不把 UUID 放回路径，也不新增确认接口或删除 Token。

示例：GET /workspaces/jiamu 返回 `ETag: "w:2a09e7eab17242daca6e67ac276dd2b6:2"`，删除原样传 `If-Match: "w:2a09e7eab17242daca6e67ac276dd2b6:2"`，并带本次 Idempotency-Key。ETag 对客户端为不透明值；同名新空间即使 version 同为2，ETag 也不同。缺失/格式错误返回400，已过期或身份不符返回412；版本应覆盖空间管理快照的变更。成员/Key PATCH 继续使用原来的数字版本 ETag，不把空间格式套到所有资源。

受理顺序必须明确：

1. 认证管理员，校验请求路径与 Header 格式；先按当前实例内的 `(action, Idempotency-Key)` 查管理历史，并核对原始路径、If-Match 及请求指纹。不同请求复用同 Key 返回409；并发受理有数据库唯一约束。
2. 已受理过的请求返回原 operation_id/内部对象结果；空间行已删除也能返回。明确重试 failed 时只允许原对象满足恢复条件，不重新按名字选择对象。该路径不能因空间 version 已变化而把正常重试误判为412。
3. 没有历史命中时，才按 bank_id 解析当前空间、加锁并校验 If-Match；在同一受理事务绑定内部 workspace_id、关闭准入和写入操作。旧请求首次迟到，同名新空间也必须返回412。
4. 执行者始终按已保存的内部身份和执行权工作，不重新解析可复用地址；清理顺序与名称释放遵守 WS-03。Idempotency-Key 不能只在“当前解析出的 workspace_id”范围查重，否则同名重建会漏掉旧历史。

窗口内重试复用全部原始输入，不能先 GET 同名新空间、换成新 ETag 再自动重放旧 DELETE。窗口外没有旧结果恢复承诺，但旧 ETag 仍不能命中新对象。若管理员重新读取新对象并用新 ETag/幂等 Key 删除，这就是一次明确的新操作。客户端丢弃原条件后只发送一个名称，服务端无法判断其真实意图，不能承诺这种请求仍有代际保护。

#### 与逐空间授权一起调整

API-02 的授权对象和逐空间权限继续保留；对外条目从 workspace_id 改为 bank_id：

```json
{
  "name": "订单应用",
  "authorization": {
    "mode": "selected",
    "workspaces": [
      {"bank_id": "mysql", "permission": "read"},
      {"bank_id": "pg", "permission": "read_write"}
    ]
  }
}
```

创建或明确替换授权时，服务端在受控事务中解析 active 空间并将内部 workspace_id 写入关联表；不能只保存 jiamu 字符串作为授权。all 的公开格式不变；默认读写、PATCH 完整替换及显式权限的规则不变。

删除空间时移除旧授权，并在同一管理事务增加受影响 Key 的 version。删除前打开的编辑页面再保存旧授权，If-Match 必须返回412；否则改用可读 bank_id 后会把旧授权悄然绑定到同名新空间。UI 刷新只展示剩余授权，不因为发现同名空间就自动勾选；重新授权属于明确的新编辑。

若最后一项授权被删除，Key 保持 selected 且无权限，不自动升级 all，也不隐式吊销整把 Key。内部约束及读取响应允许清理后的0项；创建和主动替换授权仍要求1～1000个 active 空间。UI 显示“无可用工作空间”，管理员可后续明确重新授权。需区分输入与读取模型，不能继续用输入的 min_length=1 约束读取响应；没有必要新增 Key 状态列或新的接口。

#### 扩展改动与已有体验数据

| 范围 | 调整原则 |
| --- | --- |
| 元数据 | workspaces 增加 bank_id 唯一列；保留内部 ID 外键与实际 schema 映射，调整原 schema 必须等于 UUID 前缀的 CHECK |

第一版尚未发布，可以一次替换实验管理合同，不为保留当前代码维护双路径、双授权字段。全新部署直接初始化目标结构；如保留当前体验数据，离线回填 bank_id=原 workspace_id，保留原 schema/原生内容及授权绑定。旧空间的32位 bank_id 仍是其真实标识，不是通过格式猜测提供 UUID 别名；旧值允许数字开头，新创建规则不追溯拒绝已注册空间。

不通过 UPDATE banks.bank_id 或直接重命名 schema 给已有空间改名；记忆、文档、任务和缓存都可能引用旧值。已有 jiamu 空间不会自动变为可读标识，是否保留、重建体验数据由实施任务明确，不静默删除。schema_name 继续显式保存，不能仅凭新命名公式推导全部旧空间。

本项为中等工作量的扩展、元数据与公开合同调整。WS-02/03 必须联合验收，不因单条可读 URL 能调用就宣称完整完成；不修改 Hindsight 记忆算法。

#### 联合验收要求

- 新建 jiamu 后，原生 Bank 为 jiamu、schema 为 ctxdb_ws_jiamu；管理详情、删除、授权、REST/SDK/单空间及多空间 MCP 都使用同一 bank_id。
- 默认标识、中文展示名、54字符边界、非法字符、重名并发、归属未知 schema、新旧命名并存均符合规则。
- selected/all、差异读写、用户停用与 Key 吊销保持；内部授权不存可复用地址，空 selected 拒绝全部访问但允许明确重新授权。
- 删除需要原 ETag；旧空间 version 与新空间相同也不能误删；并发受理、响应丢失、failed 明确重试、操作历史命中均保持原对象。
- 删除前打开 Key 编辑页，旧 If-Match 返回412；同名重建后旧 selected Key 无新空间权限，Admin/all 按约定可访问。
- 排空、初始化执行者、进程退出及部分清理故障按 WS-03 验收；旧任务不能污染新空间。已受理业务任务仍执行完成后才能销毁。
- 新建和保留体验数据的离线升级均验证；旧 Bank 内容、任务、原生返回结构保持，失败整体回滚。

### 5.3 WS-03：删除工作空间后清理残留表和记录（P1，待实施）

2026-10-16，根据删除行为与幂等保留讨论补充。**本次仅记录优化，未执行任何 DROP、DELETE 或清理操作；当前实现仍保留 deleted 空间记录和原生 schema/表结构。**

**目标：** 删除工作空间不能长期留下整套空业务表和无需继续保留的管理记录。确认任务排空、业务清理成功后删除该空间的业务 schema，清理空间记录和关联授权；终态管理操作在明确的重试/查询窗口后清理。审计独立保留，不把“需要审计/幂等”解释为所有对象必须永久保存。

| 对象 | 优化后的处理 |
| --- | --- |
| 目标空间的业务 schema、表、索引和数据 | 完成准入关闭、任务排空及原生清理后，删除该空间的 schema，不保留整套空表；原生流程负责的附件/外部文件清理也需核对结果 |
| ctxdb_meta.workspaces 中的 deleted 行 | 在确认清理成功、关联依赖处理完毕后删除；执行中、失败待恢复、结果未知时不得提前移除 |
| key_workspace_permissions 等空间关联 | 清理指向旧 workspace_id 的授权并增加受影响 Key 的版本；保留用户及其他空间权限，空 selected 按 WS-02 拒绝全部访问，不继承新空间 |
| management_operations | 未完成、结果未知或仍需恢复的操作保留；终态结果在约定的幂等重试/查询窗口内保留，窗口结束后分批删除，不默认无限保留 |
| request_admissions | 正常完成按既有机制释放；仍有登记或未知执行者时阻止销毁，不能因 TTL 到期或状态显示 deleted 而强行清除 |
| audit_events | 按审计保留策略独立保存；历史对象删除不级联删除审计，审计不承担执行恢复或幂等结果查询职责 |

#### 删除完成与恢复边界

1. 先关闭新请求准入，确认在途 REST/MCP、原生任务和已启动的初始化执行者均已结束；继续保留现有锁、租约及未知执行者保护。
2. 校验 schema 是当前 workspace_id 登记并拥有的目标，再通过受控流程执行原生清理和 schema 删除；遇到未知归属或跨空间依赖不能盲目扩大 CASCADE 范围。归属校验与实际 DDL 之间同样受执行权保护，不能只在开始比较一次 UUID，就假定后来没有旧执行者。
3. 确认 schema 不存在、外部清理已完成且旧执行者不会继续执行；在最终管理事务中清理关联授权、增加受影响 Key 版本、移除空间目录行并记录操作 succeeded，之后才释放标识供同名创建。不能先以 deleted 状态释放名称，再异步继续清理旧 schema。响应仍为202受理，客户端查询终态；不新增“强制删除”入口绕过排空。
4. 中途失败保留足够状态供恢复，重复执行能识别已完成步骤；进程重启后不能把“schema 已删除但元数据未清理”当成不可恢复错误，也不能误清理后续新空间。

当前 management_operations、授权和准入等通过外键引用 workspace。实施时需调整依赖，使终态操作能在空间行移除后独立保留原 workspace_id、bank_id 及必要结果快照；不能简单用 ON DELETE CASCADE 提前删掉窗口内的幂等结果或未完成任务，也不能直接删空间行导致外键失败。管理历史查询和幂等重放都不再以空间行必须存在为前提；执行未完成时仍必须校验真实空间与执行归属。

零剩余授权的 selected Key 按 WS-02 允许保留空范围、拒绝全部空间访问，后续可明确重新授权；不自动改为 all，不自动吊销，不误删成员或其他空间的 Key。当前1～1000项延迟约束和读取模型需一起调整，保留创建/主动编辑至少一项的输入要求。清理与 Key 版本递增在受控事务中完成，避免旧页面提交可读 bank_id 时把授权重新绑定到同名新对象。

#### 保留窗口与幂等承诺

幂等保证应有明确期限，不要求永久保存每个管理操作。实施时统一定义重试/查询窗口及配置，更新 curl、UI 和运维说明；窗口内仍可查原操作、使用原 Idempotency-Key 找到原结果，窗口外不再承诺恢复旧结果。没有定义窗口前，不直接开启历史清理。

UI 保存的恢复意图也受此期限约束；超期不重放旧写请求，应先核对当前资源并由管理员明确发起新操作。服务端和 UI 对期限采用同一交付配置/合同；具体起算点、时长及边界响应须在实施前固定，不能一边按受理时间、一边按终态时间判断。新建同名空间使用新的 Idempotency-Key；旧操作在窗口内的重试先命中历史，只关联原 workspace_id，不能重新操作同名新空间。操作历史清理后，旧 DELETE 的原 If-Match 仍应阻止命中新对象；旧 POST 超出窗口不承诺去重，因此过期创建意图尤其不能重放。审计可保留更久，但不借助普通审计日志恢复原请求结果。

无需新建通用归档或调度平台，优先复用现有生命周期/维护入口做有界分批清理；具体保留时长和触发方式在实施前写清楚，本次未指定未经确认的天数，也未运行清理脚本。

#### 同名重建与可读地址复用

旧空间清理完成后，允许重新创建同名工作空间，并复用 bank_id=jiamu、schema_name=ctxdb_ws_jiamu；新空间为空，分配新的内部 workspace_id。新空间必须作为新的生命周期实例，不恢复旧数据或旧 selected 授权。

复用意味着同一个 /banks/jiamu 地址以后指向新空间，Admin Key 和包含未来空间的 all Key 可访问新空间；接受这个产品语义，不再承诺地址永远对应同一代空间。旧客户端如要求固定到原空间，应使用指定空间授权，不能把 all Key 当成代际隔离。

重新创建只有在旧清理/初始化执行者已确认停止或被可靠隔离、不能继续操作该 schema 后才允许；单纯租约超时不证明这一点。旧后台任务、删除重试和历史清理器必须按旧 workspace_id 和执行归属判断，不能只凭可复用 bank_id/schema_name 删除对象。旧创建幂等记录在保留窗口内返回原操作，不得因空间行不存在就重新初始化。按名称发起的删除还必须遵守 WS-02 的 If-Match 与历史先查规则，不能只依赖后台 UUID 保护。单个字段变成 deleted 不能替代这些确认。

#### 验收要求

- 删除成功后目标 schema、业务表及工作空间目录记录不存在，原生文件清理结果可核对；其他空间不受影响。
- 同名重建前旧 schema 已不存在且旧执行者不会继续执行；重建后 name/bank_id/schema 可相同但 workspace_id 不同，新空间为空，权限不继承。覆盖初始化线程、断连后仍运行的数据库语句和旧清理进程恢复执行，不能只测目录状态。
- 空间有运行任务、异常准入、失联执行者时不能提前销毁；失败、进程退出、部分完成及重试能正确恢复。
- 窗口内删除状态和幂等结果仍可查询，操作历史清理不破坏外键或触发恢复；窗口结束后按合同清理，UI 不自动重提过期意图。
- 新空间建好后，旧 DELETE 首次迟到用原 ETag 返回412，窗口内原幂等重试返回旧操作，历史清理后原条件也不能命中新空间；旧任务和清理器不能删除或污染新空间。Admin/all 的新业务请求按约定访问新空间，selected 无旧授权继承。
- 清理旧空间授权后，其他授权、用户、Key、审计保留正确；空 selected 拒绝所有业务访问、列表仍能读取并允许明确重新授权；受影响 Key 版本增加，旧编辑保存返回412。

以上是待执行验收，不计入既有测试结果。本项与 WS-02 联合实施并更新设计、部署、OpenAPI 和 curl 文档；本次不修改当前运行实例的数据。

## 6. PG 元数据设计

### 6.1 范围与结论

本模块源于 2026-10-16 对 `ctxdb_meta` 的讨论及 PG DBA、PG 内核专家审查。目标是精简独享版元数据，补足可维护性，不建设共享版底座；后续实施状态见第 8 节。

**用户已经同意的原则：** 一实例独享一个 PG 数据库；当前方案不因各表带有实例 ID 就具备共享服务能力，不为未来共享版在每张表保留重复的实例、租户字段。保留必要的成员归属、空间归属和部署一致性检查。

建议落地顺序：

1. 将版本表与实例表合并为单行部署信息，去掉业务表重复实例、租户列及配套冗余索引。
2. 统一受控 ID、名称、状态等字段的约束，补全数据库注释。
3. 将列表索引与用户管理的吊销隐藏、逐空间授权方案一起调整。
4. 实测后再决定使用时间更新节流、任务领取索引和运维保留策略，不先增加复杂基础设施。

最初审查没有执行 DDL。后续已在隔离临时库实现并验证表、注释、索引和有序迁移；原体验库未更改，第 6.2 节保留其优化前快照，最终结构以优化版 schema.sql 为准。

### 6.4 DB-01 合并单行部署信息（P1，已实施）

建议 `deployment_info` 保存：固定单行标识、`instance_id`、`cloud_tenant_id`、`metadata_version`、`format_id`、`installed_at`。

- 用数据库约束保证最多一行，例如布尔主键 `singleton` 同时要求其值为 true；初始化及 API/Worker 仍校验恰好存在一行。
- 优化前结构版本1，优化后有序迁移为2；这是内部结构版本，不是 API v2 或产品名称。`format_id` 区分旧实验库与首发格式，不能删除或只改数字跳过升级。
- 原始初始化时间保持不变；不能仅修改版本数字当作完成升级。
- 合并的是部署信息表，不是各业务 schema 的原生 `alembic_version`。Hindsight 原生迁移继续独立运行。
- 先保留原有管理事务加锁行为。合表与移除全局锁是两项独立变更，不一并悄悄取消并发保护。
- `CREATE TABLE IF NOT EXISTS` 不是结构升级。需要明确新建、存量升级及失败恢复路径：预检查长度、孤儿和重复数据，复制并验证部署绑定，迁移引用外键和查询，再移除旧列/表；迁移成功后更新元数据版本。API/Worker 的版本门禁与升级同步，不通过改版本数字跳过迁移。

### 6.5 DB-02 类型、长度与约束（P1，已实施）

PG 的 `text` 与 `varchar(n)` 对相同短内容没有本质存储优势差别。`Storage=extended` 表示允许 TOAST 压缩/行外存储，不表示这个字段的每个值都已存入溢出页。改类型是为了明确业务约束，不以此宣称性能提升。参考 [字符类型](https://www.postgresql.org/docs/18/datatype-character.html) 和 [TOAST](https://www.postgresql.org/docs/18/storage-toast.html)。

| 字段 | 建议 |
| --- | --- |
| 我们生成的内部 `key_id/user_id/workspace_id/operation_id/admission_id` | 可统一 `varchar(32)`，加 32 位小写十六进制格式检查；不要用补空格的 char，也不为省空间首版整体改 UUID |
| WS-02 对外 `bank_id` | 独立列与唯一约束；新建按1～54位可读标识规则，旧已注册32位值保留。不要让内部 ID 的十六进制校验约束它，也不收窄 Hindsight 原生其他部署的通用 Bank ID |
| 外部 `instance_id/cloud_tenant_id` | `varchar(128)`，与现有部署输入上限一致；目前提供的实例 ID 36 字符、租户 ID 32 字符不是所有未来格式的保证 |
| 面向客户的名称 | `varchar(64)`，保留非空和业务校验；成员/Key 名称拒绝全空白，名称规范化顺序明确 |
| `name_key` | 保留 text 或单独定义足够上限；NFKC/casefold 后可能变长，不能机械套用名称的 64 字符上限 |
| `schema_name` | 保留严格格式和唯一约束，来源为服务端，不能接受客户输入直接作为 SQL 标识符 |
| 状态、权限、模式 | 有界 varchar 或 text 配合明确 CHECK；不为短字符串引入一批 PG ENUM 类型 |
| `digest` | 保持 bytea 及 32 字节检查，不与完整 Key 长度混淆 |
| `request_hash` 等内部摘要 | 按实际编码统一格式，例如 SHA-256 十六进制为 64 字符；不要拿它存完整密钥 |
| 不定长描述、错误信息 | 按业务接口语义决定是否设上限，不为统一而盲目收窄 |
| `metadata` | 保持 JSONB object；非安全扩展用途，不参与任意权限覆盖，不预建 GIN |

当前 `key_id` 已有正则检查，`name` 已有 1～64 字符检查，`digest` 已有 32 字节检查；不能把 text 类型解读为这些字段没有限制。还应核对各内部 ID 的一致约束、版本正数、重试次数非负等基础不变量，先检查存量再补约束。

长度必须分清：`key_id` 为 32 字符，完整业务 Key 为 85 字符、运维 Admin Key 为 86 字符；本地 MaaS 凭据样本为 86 字符。名称允许 64 字符不代表完整 Key 也能限制为 64。库内继续只保存业务 Key 摘要和必要脱敏展示信息，外部模型凭据不放入该表。

空间名称先 NFKC 和去首尾空白，需对规范化后的展示名称再校验长度；再计算 casefold 名称键，并按独立规则约束。相同语义字段在主表、关联表、历史表和接口模型中保持一致，迁移不可静默截断。

逐空间权限若采用 Key—空间关联表，应有唯一 `(key_id,workspace_id)`、有效外键和权限允许值，必要索引围绕实际鉴权路径设置；若有其他存储方案，同样要明确约束和存量转换。新增权限关系不放进任意可写 metadata，也不只依赖前端校验。授权模型已按 UM-05 和 API-02 的 authorization 合同实施；仍不开放任意 metadata 授权写入。

### 6.6 DB-03 注释覆盖（P1，已实施）

新增或保留的 schema、每张表、每个字段都应有数据库注释；非显而易见的约束、部分索引和运行机制也补充用途说明。代码里的 `--` 注释不会自动出现在 `\d+`，需要真正的 `COMMENT ON`。参考 [PG COMMENT](https://www.postgresql.org/docs/18/sql-comment.html)。

注释至少说明：业务用途、ID 的来源和格式、状态含义、空值语义、默认行为、是否会清理，以及字段是否允许客户修改。例如：

```sql
-- 注释用途示意；优化版通过安装/迁移统一写入，原体验库未执行。
COMMENT ON SCHEMA ctxdb_meta IS '独享 ContextDB 实例的管理元数据，与工作空间记忆数据分开存储';
COMMENT ON TABLE ctxdb_meta.api_keys IS '成员业务 API Key 的摘要与授权元数据，不保存完整密钥';
COMMENT ON COLUMN ctxdb_meta.api_keys.user_id IS 'Key 所属成员 ID；成员停用或删除后，该成员的 Key 不再允许新访问';
COMMENT ON COLUMN ctxdb_meta.api_keys.digest IS '完整业务凭据的 HMAC-SHA256 摘要，固定32字节；不是密钥明文';
COMMENT ON COLUMN ctxdb_meta.api_keys.revoked_at IS '吊销时间；NULL表示尚未吊销，仍需结合成员状态判断可用性';
COMMENT ON COLUMN ctxdb_meta.api_keys.last_used_at IS '服务记录的最近使用时间；NULL表示没有已记录的使用时间，不是完整访问审计';
COMMENT ON TABLE ctxdb_meta.management_operations IS '工作空间创建和删除的异步管理任务及幂等结果，由 API 内置生命周期循环执行';
COMMENT ON TABLE ctxdb_meta.request_admissions IS '在途请求或任务提交的持久登记；供在线删除排空判断，不是任务队列';
COMMENT ON TABLE ctxdb_meta.audit_events IS '成功管理变更历史；提交操作成功不代表异步任务已经执行完成';
```

后续若变更名称或授权结构，注释与新结构同步，不能保留描述旧字段含义的注释。AUTH-01 后 users/api_keys 也包含受保护管理员，不能继续注释为只保存业务成员/凭据；WS-02/03 后应说明 bank_id、内部身份、清理和空 selected 的新语义。上方 SQL 是当前结构示例，不是目标变更的完整脚本。注释不包含密码、Key、pepper 或连接凭据。通过部署迁移统一安装，不在 API 每次启动、每个请求中补写；存量库也要有更新路径。

### 6.7 DB-04 索引精简与查询匹配（P1 已实施；P2 待测量）

优先移除独享设计不需要的重复前缀及配套复合唯一约束，再评估新增索引。下表是目标设计建议，**不是可直接执行的 DROP/CREATE 清单**；尤其要先迁移引用外键，再删除其依赖的唯一约束。

| 对象 | 当前索引或查询 | 建议 |
| --- | --- | --- |
| 部署信息 | instances 主键、实例+租户唯一，另有版本主键 | 合表后以固定单行主键为核心，不保留仅为复合外键存在的重复唯一索引 |
| 空间关联 | 空间 ID 主键 + `(instance_id,workspace_id)` 唯一 | 外键改为引用空间主键后，取消复合唯一 |
| 成员关联 | 成员 ID 主键 + `(instance_id,user_id)` 唯一 | Key 改为引用成员主键后，取消复合唯一 |
| 空间名称 | `(instance_id,name_key) WHERE state<>'deleted'` 唯一 | 改为 `name_key WHERE state<>'deleted'` 唯一，保留删除后可重建同名空间的语义 |
| 空间/成员分页 | 实例前缀 + 创建时间 + ID | 去掉实例前缀；可结合正常列表过滤评估部分索引，排序保留时间与 ID |
| 成员下 Key 分页 | `(instance_id,user_id,created_at,key_id)`，当前含已吊销 | 去掉实例前缀；与 UM-06 同步评估 `(user_id,created_at,key_id) WHERE revoked_at IS NULL`；查询和 total 先过滤再分页 |
| 在途登记 | `(instance_id,workspace_id)` | 改为 workspace_id 索引，支持删除检查；保留 admission_id 主键 |
| 管理幂等 | 实例、操作者、动作、目标、幂等 Key 唯一 | 精简固定实例/身份后仍保留同等作用域；不可仅为少字段丢掉幂等唯一约束 |
| 管理任务领取 | `(instance_id,state,lease_until,created_at)`，租约持续更新 | 移除实例前缀；是否改为仅覆盖 pending/running 的部分索引需代表性数据验证 |
| 管理任务按空间检查 | 检查某空间是否有 pending/running 任务，现无相应前导空间索引 | 若历史增多，可评估 workspace_id 上的活动任务部分索引；低频少量任务先不增加 |
| 审计 | `(instance_id,workspace_id,created_at)`，尚无审计读取 API 合同 | 按真实运维查询确定是否保留空间+时间索引；全库时间查询/清理需要另评估，不预建多套索引 |

几点限制：

- 部分索引的谓词必须与查询条件匹配；仅有相似字段不保证被使用。参考 [部分索引](https://www.postgresql.org/docs/18/indexes-partial.html)。
- Key 正常列表部分索引不包含已吊销行；外键维护、历史排查若需要覆盖全部 Key，不能误认为它提供全量 user_id 索引能力。根据明确的物理删除/历史查询需求选择是否保留全量索引，不默认新增两套近似索引。
- 当前名称查询是 `strpos(lower(name),lower(q))>0`，普通 name B-tree 不能直接支撑该包含检索。小目录先顺序扫描，不因为装了 pg_trgm 就加 GIN；有实际规模和查询需求后再修改查询与索引一起验证。
- 不给 metadata、workspace_ids、digest、last_used_at 等“可能以后会查”的字段预先加索引。按 key_id 鉴权已有主键，不需要额外 digest 索引。
- 同一索引在不同排序方向可有复用空间，但不能只按字段重叠就判定冗余；考虑谓词、唯一性、外键、排序和真实查询。

### 6.8 DB-05 高频写与并发（P2，待测量；安全语义先保留）

当前业务鉴权在指定记录使用时间时会无条件更新 `api_keys.last_used_at`。高并发共用同一 Key 时会产生同一行更新争用、WAL 和 MVCC 版本。可先评估有界条件更新，例如距离上次记录超过一个约定间隔才更新，不先引入独立队列或异步缓存系统。间隔、UI 精度和失败处理需要明确，不能把近似使用时间宣传为完整审计。

节流只影响使用时间记录，不能缓存或延迟鉴权；成员停用、Key 吊销和收权仍对后续请求生效。`last_used_at` 当前未建索引，有利于保留 HOT 的机会；是否发生 HOT 还取决于索引涉及列、页内空间等条件，不能只凭“没有索引”保证。参考 [PG HOT](https://www.postgresql.org/docs/18/storage-hot.html)。

管理任务每 10 秒续租更新 `lease_until`，当前领取索引包含此列，会带来索引维护；但空间管理是低频操作，小库不能据此证明瓶颈。调整索引需要比较候选扫描、排序、续租开销和终态历史比例，不为追求 HOT 牺牲任务可领取性。

单行部署信息仍可先承接当前管理事务锁。未来要去掉该全局锁，应先以成员父行等适当锁及一致锁序替代，验证“签 Key 与成员停用/删除”等并发；不能在去掉 instance_id 时同时丢掉保护。

空间删除目前显式取得 `FOR UPDATE`，与准入持有的 `FOR KEY SHARE` 协调。普通状态 UPDATE 往往只取 `FOR NO KEY UPDATE`，不能当作同等替代；精简 SQL 时保留这一差异。准入正常结束删除登记，异常未知工作保留；不可改为 UNLOGGED 表、内存计数或按 TTL 自动清空来实现所谓精简。

### 6.9 DB-06 三张运行记录表与保留策略

后续删除清理目标以 WS-03 为准：移除已清理空间及关联记录，终态操作按明确窗口清理；下文保留原实现职责和清理前提，不再解释为永久保留全部对象。

| 表 | 执行者及生命周期 | 当前建议 |
| --- | --- | --- |
| `management_operations` | 管理 API 插入任务；API 内置 Lifecycle 循环领取和执行 create/delete_workspace，更新状态并保留结果 | 保留必要任务机制，精简字段；终态历史清理需先规定幂等重试与结果查询窗口 |
| `request_admissions` | HTTP/MCP 入口、后台任务提交扩展登记；正常退出删除，无独立调度器 | 保留在线安全删除的持久屏障；不把它说成 Hindsight 的任务队列 |
| `audit_events` | 管理变更事务写入历史，不调度工作 | 独立的追溯能力；保留与否和保留期限是产品取舍，不与任务结果混为一谈 |

原生 Hindsight 的实际异步任务仍由原生 Worker 执行。删除空间时，扩展同时检查原生任务与在途登记，后者覆盖同步调用、任务尚未提交等阶段。管理任务领取租约可过期接续，不代表未知业务执行者也可按超时当作结束。

三者不强行合表：任务需要领取、重试、保留终态，准入正常结束删除，审计保存历史；仅加类型字段合并不会消除不同规则。若以后决定把空间创建/删除收敛为同步或维护期操作，应先修改产品行为和故障恢复约定，再评估减少任务机制；本轮不承诺这个变化。

`target_id` 当前创建任务为空目标，删除任务目标为 workspace_id，参与幂等作用域；不能不改查询就删列。下一轮按 WS-02 明确改为实例内 `(action, Idempotency-Key)` 唯一查重，原请求路径/条件进入指纹、内部对象身份进入操作快照。届时 target_id 是否仍有独立用途应重新判断，不因现有代码用了它就强制保留；相应唯一约束与迁移一起调整。

清理原则：

- 原生任务清理不会清理 ctxdb_meta 管理任务，不能套用其参数声称已经有保留期限。
- 成功/失败管理任务、幂等记录、审计、成员/Key 墓碑分别定义保留需求，不一刀切。
- 没有产品幂等有效期前，不自动清理终态管理记录。未完成任务、异常准入不能作为普通历史删除。
- 本轮不预建分区、归档平台或清理专用索引；有规模与合同后再选简单的分批机制。

### 6.10 对照 Hindsight 原生表的经验

本次对照同一空间的 banks、documents、chunks、memory_units、async_operations、audit_log、alembic_version 共 7 张表的实库结构，并核对相关迁移和查询代码。

| 对照点 | 原生事实 | 对 ctxdb_meta 的启示 |
| --- | --- | --- |
| 类型选择 | Bank/Document 等 ID 和名称大量使用 text；部分记忆及内部 ID 使用 UUID | 类型服务于输入合同；我们受控的 32 字符 ID 可约束，但不能把原生任意 Bank ID 一起收窄 |
| 类型一致性 | `c3e5a7b9d1f4_widen_history_bank_id_to_text.py` 记录原生历史表 varchar(64) 与主表 text 不一致导致迁移失败的修复 | 同语义字段在全部关联、历史表中一致；表结构改动需要迁移，不能只改初建 DDL |
| 索引 | async_operations 有活动任务领取、终态清理等部分索引；memory_units 还有向量、全文与多种检索索引 | 借鉴按生命周期与查询建立索引，不把记忆检索索引搬到低频元数据 |
| 历史清理 | 原生 maintenance 和操作清理迁移提供终态任务清理 | 管理任务可借鉴分批终态清理，但先确定自身幂等语义，不能直接依赖原生清理 |
| 外键删除 | 原生任务/部分附属对象使用 Bank 外键及级联清理 | 当前保留成员软删除和空间墓碑；WS-03 将清理空间行但独立保留窗口内操作与审计，不能照搬 ON DELETE CASCADE 一起删掉 |
| 审计职责 | 原生 audit_log 包含业务调用的 request/response JSONB 等，meta audit_events 仅记录管理变更 | 不重复存业务请求响应，不在管理审计中记录密钥；原生业务审计也不能自动替代成员/Key 管理历史 |
| 版本 | 原生每 schema 有 alembic_version 与有序迁移 | meta 可合并单行版本信息，但不能省略独立的升级步骤及兼容校验 |
| 注释 | 本次抽查的原生 7 表也未发现表/列 COMMENT | 原生没有注释不是我们省略运维元数据注释的理由 |

本轮不修改原生业务表、其索引或 Alembic 版本表。代码定位除本模块前述扩展文件外，还包括 `hindsight-api-slim/hindsight_api/engine/maintenance.py`、`alembic/versions/a8c1e4f7b0d3_add_operation_retention_indexes.py`、`c2d3e4f5g6h7_add_audit_log_table.py`、`c3e5a7b9d1f4_widen_history_bank_id_to_text.py`。
